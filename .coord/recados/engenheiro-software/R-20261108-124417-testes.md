# D-T0107a: pool da API trava com pushes de pedido simultâneos >= pool (carteira pede 2ª conexão dentro da transação)

## Contexto
Carga da T-0107 (PR #110, commit af376bb, tests/carga/t0107/carga-20mil-t0107.test.ts) achou o defeito D-T0107a: pushes de pedido SIMULTÂNEOS em número >= pool da API (10, padrão de `MACUXI_API_POOL`) travam o pool.

Causa: o push abre a transação do pedido (`ctx.comTenant` em `modules/vendedor/api/receber.ts`, função `receberPedidos`) e, já dentro dela, chama `ctx.carteira()` (`apps/api/src/app.ts`, `carteiraDe(token, acesso, ...)`), que pede uma 2ª conexão ao MESMO pool. Com 10 pushes em voo, as 10 conexões ficam "idle in transaction" esperando a 11ª, que nunca vem (as sessões param no `select ... from vendedor.pedido where id = $1`, logo antes do `ctx.carteira()`).

Efeito medido (Postgres 16, pool 10, 100 pushes ao mesmo tempo): só 13 a 18 aceitos e o resto 500 (rodadas: 13/87 e 18/82). No servidor a trava dura até o `idle_in_transaction_session_timeout` (60 s): o Postgres derruba as sessões e o lote volta 5xx (o motor do app reenvia, mas o vendedor espera e a instância fica sem conexões para as outras rotas). Sem `connectionTimeoutMillis` o pool espera para sempre. Toca RN de escrita idempotente/offline-first (regra 4 e 6 do CLAUDE.md): o pedido não se perde, mas a API fica indisponível sob pico.

Prova: caso 6 do arquivo acima, hoje em `it.fails` ("6. D-T0107a: 100 pedidos ao MESMO TEMPO com pool de 10"), sobe uma 2ª instância da API com `connectionTimeoutMillis` para falhar em vez de travar. O caso 3 limita a concorrência a 5 (`MACUXI_CARGA_PEDIDOS_CONCORRENCIA`) só por causa deste defeito.

Como rodar (precisa de Postgres; no PC do dono do produto quem roda é o CI): `pnpm test:tests carga/t0107`; com metas de tempo: `MACUXI_CARGA_MEDIR=1 pnpm test:tests carga/t0107`. A linha `[carga T-0107] D-T0107a pedidos ao mesmo tempo (ms)` mostra aceitos e status.

## O que preciso / o que mudou
Corrigir para que nenhuma requisição segure uma conexão em transação enquanto pede outra ao mesmo pool. A forma da correção é decisão do engenheiro-software com o modulo-vendedor (ex.: resolver `ctx.carteira()` ANTES de abrir a transação, no `receberPedidos` ou na plataforma antes de `prov.receber`; ou ler a carteira pela mesma conexão da transação). Vale procurar o mesmo padrão (consulta que pega 2ª conexão dentro de `comTenant`) nos outros `receber` (visita, promotor, pesquisa).

Depois da correção, me avisem por resposta a este recado: eu (testes) troco o caso 6 de `it.fails` para `it` e subo a concorrência do caso 3 — esses arquivos são meus, não precisam mexer neles.

- O caso 3 roda com concorrência >= 10 (até os 100 ao mesmo tempo) sem 5xx.

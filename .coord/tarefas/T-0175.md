# T-0175 — Vendedor do ERP ligado ao usuário do BKO sem depender do e-mail (A1 + A2)

Origem: R-20261115-070200 (item 3, "Tira essa regra maluca") e R-20261115-073000 (item 6, "A1 + A2 aprovados"), do dono do produto. Primeiro caso: o Anderson (VEN-000034, tenant thathyany).

## Objetivo
Hoje o vendedor do ERP só adota um usuário do BKO quando os e-mails são iguais (`modules/core/api/consumidores-erp-vendedor.ts`). Sem e-mail, a carga cria um usuário provisório (`…@sem-email.invalid`) e a carteira fica com ele. A partir desta tarefa:
- o vínculo passa a ser pelo **Código no ERP** (`external_id`);
- o BKO ganha uma ação que junta o provisório ao usuário real.

## A1 — Código no ERP visível e editável
1. O campo "Código no ERP" (`external_id`) aparece e pode ser editado no cadastro de vendedor e de promotor no BKO, em Novo e em Editar. A gaveta Novo já tem esse campo (RN-CORE-57).
2. Código repetido no tenant: a API responde 409 com uma mensagem que orienta o vínculo. Exemplo: "Este código já é de um usuário provisório. Use Vincular vendedor do ERP." O texto final é do designer-ux.
3. Quando a carga cria um usuário provisório (`@sem-email.invalid`), o admin recebe um aviso no BKO (alertas ou notificações). Sem dado pessoal em log.
4. A lista de Usuários tem busca por código do ERP e o filtro "Provisórios".

4a. **Dois códigos por usuário** (dono do produto, R-20261115-074500, item 8; recebido às 8h05):
   - **Código ERP:** igual ao do ERP; é o `external_id`;
   - **Código FDV:** próprio, para controle.
   O designer-ux propõe na simulação, para o dono do produto aprovar:
   - se o Código FDV é gerado ou digitado;
   - se é único;
   - onde aparece (lista de Usuários, cadastro, app);
   - como os dois aparecem no cadastro e na lista.
   O Código FDV só será implementado depois da aprovação. Até lá, o modulo-core não cria campo nem migração para ele.

4b. **Correção de escopo** (dono do produto, R-20261115-075000, recebida às 8h06). Antes de qualquer PR de tela, vão em SIMULAÇÃO (PNGs do designer-ux) para o ok dele:
   - o aviso de usuário provisório ao admin;
   - o filtro "Provisórios";
   - o botão "Vincular vendedor do ERP";
   - o Código FDV;
   - o vendedor sem filial.

   **Sem esperar o ok:** domain (`planejarVinculoErp`), testes, contrato, API, consumidor da carga e migração.
   **Só depois do ok:** as telas do BKO (`modules/core/web`). Elas saem do PR `nuvem/erp-vinculo-modulo-core` e vão para um branch próprio, que fica parado até a aprovação.

## A2 — Ação "Vincular vendedor do ERP"
5. `planejarVinculoErp` em `modules/core/domain`:
   - é uma função pura, com teste escrito antes e citando a RN-CORE-58;
   - recebe o provisório, o usuário real e as carteiras;
   - devolve o plano: external_id, carteira sem duplicar, referências a corrigir, desativação e eventos.
   Ela recusa (422) quando:
   - o "provisório" não é provisório;
   - o usuário real já tem outro `external_id`;
   - os perfis não são compatíveis (só vendedor → vendedor e promotor → promotor);
   - os dois são o mesmo usuário;
   - os dois são de tenants diferentes.
6. Rota BKO (admin) `POST /v1/core/usuarios/:id/vincular-erp`. O nome final fica com o modulo-core. Tudo em **uma transação**:
   - passa o `external_id` do provisório para o usuário real;
   - transfere a carteira, sem duplicar;
   - corrige as referências (ex.: `core.nota_erp.usuario_id` e as demais do levantamento do banco-dados);
   - desativa o provisório, liberando o `external_id`;
   - grava a auditoria;
   - publica `core.cliente.atualizado@1` por cliente movido.
   A operação é idempotente: repetir não duplica nada.
7. **A carga seguinte não desfaz o vínculo.** O vendedor do ERP com o mesmo `external_id` cai no usuário real. A carga:
   - não recria o provisório;
   - não troca o e-mail real pelo provisório;
   - não move a carteira de volta.
   Isso tem teste no consumidor `consumidores-erp-vendedor`.
8. Permissões e isolamento:
   - só o admin do tenant vincula;
   - o isolamento multi-tenant tem teste;
   - a licença do core é conferida.

## Critérios gerais
9. Lint, typecheck e testes verdes com os scripts do CI.
   - Os testes de banco rodam no CI, sem Docker.
   - Os testes com `crypto.argon2` só passam no Node 24 do CI.
10. Texto das telas revisado pelo designer-ux. Parecer do corretor sem achados.

## Ordem e agentes
1. banco-dados (`nuvem/erp-vinculo-banco-dados`):
   - levantamento das colunas que referenciam `core.usuario` e precisam ir para o usuário real no vínculo;
   - índice de busca por `external_id`;
   - unicidade de `external_id` por tenant, se faltar.
   Migração só se for necessária. O levantamento vai como recado ao modulo-core.
2. modulo-core (`nuvem/erp-vinculo-modulo-core`): domain com teste antes, contrato, API, consumidor da carga e BKO (A1 e A2).
3. testes → corretor-redundancias → engenheiro-software (revisão).

## Premissas do gerente
- Provisório = usuário com e-mail terminado em `@sem-email.invalid`, que é o que `emailDoVendedorErp` gera hoje.
- A adoção por e-mail igual continua como atalho. Deixa de ser a única forma; o caminho principal passa a ser o código do ERP.
- Só o admin vincula. O analista fica de fora até o dono do produto decidir.
- O provisório desativado fica na auditoria e sai da lista padrão.

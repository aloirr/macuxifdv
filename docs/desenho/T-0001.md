## 2. Princípios do mapa origem → destino
1. **Arquivo inteiro, sem reescrever.** A única adaptação permitida na cópia é **caminho de import**
   (`@fv/domain`, `@fv/contracts`, `@/…`, `./money`). Mudança de comportamento = tarefa nova.
2. **Teste acompanha o código** e é movido por blocos inteiros (`describe`/`it`). Partir um arquivo de
   teste só entre `describe`/`it` inteiros — nunca partir linhas de um `it.each` — assim a soma continua 277.
3. **Fronteira manda no destino**: o que dois módulos usam vai para `packages/*` ou para o `contracts`
   do dono; o que é do shell vai para `apps/*`; nada de módulo importar `domain` alheio.
4. **Sem ciclo entre pacotes**: `core` não depende de nenhum módulo; quem compõe dados de dois
   módulos fica no módulo que depende do outro (ou no shell).

## 11. Fronteiras
`packages/config/dependency-cruiser.cjs`, aplicado por `pnpm fronteiras` (parte de `pnpm lint` e do CI):
módulo → outro módulo só `contracts/`; módulo ↛ `apps/`; `packages/` ↛ `modules/`/`apps/`;
`contracts/` e `domain/` ↛ `api|app|web|db` do próprio módulo; `domain/` ↛ módulos do Node;
import `@macuxi/*` não resolvido em módulo = erro (subcaminho fora do `exports`). Inclui `import type`.
Prova: `packages/config/fronteiras.test.ts` roda o CLI nos fixtures — `violacao` sai com **8 erros**
(exit 8), `ok` sai com 0. A2: regra `app-importa-interno-de-modulo` (shell ↛ `domain`/`db` de módulo; exceção
`apps/mock-api`, §15). A config é reutilizável em outra raiz (`require('@macuxi/config/dependency-cruiser')`,
caminhos relativos ao `cwd` do depcruise — é o que o teste faz nos fixtures).

| `syncAll` com 8 passos fixos (`SYNC_STEPS`) | `motor.sincronizar()`: envia a fila → pull das entidades dos módulos efetivos → etapas registradas (`etapasSync`) |
| Cache (me, policy, customers, products, route, goals, orders, mix) | `me`: etapa de plataforma (`mod:core:me`). O resto: `etapasSync` + estado em `motor.armazenamentoDoModulo(m)` de core e vendedor (B2) |
| Pedido (enviar, editar, excluir, duplicar, rascunhos), check-in/checkout, atendimento aberto | `modules/vendedor/app` e `modules/core/app` (B2), com `useMotorSync().motor.enfileirar/alterar/descartar` |
| `lib/outbox.ts` (+6 testes) | copiado para `apps/mobile/src/lib/outbox.ts` (legado; `mergeOrders` e afins migram para vendedor/app na B2) |

### 13.2 Contrato
```
criarMotorSync({ registro, armazenamento, transporte, agora?, online?, etapas?, mensagemDeErro? })
  carregar() · estado() · assinar(fn)
  enfileirar({ id: UUID do aparelho, entidade, operacao?, payload, rotulo?, detalhe? })  // valida entidade, direção e payload
  alterar(id, { payload?, rotulo?, detalhe? }) · descartar(id)
  enviar({ incluirFalhos? })        // FIFO, lotes ≤ 500, uma execução por vez
  sincronizar()                     // enviar → pull (cursor por entidade) → etapas
  aplicarModulosAtivos(ids) · confirmarLimpeza(modulo)   // RN-CORE-02
  linhas(entidade) · armazenamentoDoModulo(modulo)
```
Chaves (o shell já entrega o armazenamento isolado por usuário): `sync:fila`, `sync:modulos`,
`sync:limpeza_pendente`, `sync:sincronizado_em`, `sync:cursor:<entidade>`, `ent:<entidade>` (linhas por id) e
`mod:<modulo>:*` (estado livre do módulo). Desativar um módulo apaga `ent:`/`sync:cursor:` das entidades dele e
todo `mod:<m>:`.

Situação do item: `pendente` (vai no próximo envio) · `falhou` (rejeitado/conflito: o usuário reenvia ou descarta) ·
`modulo_inativo` (rejeitado com `MODULO_INATIVO`: "não enviado — módulo desativado"). Exceção do transporte =
falha de rede/5xx: conta tentativa e **para** (não embaralha a ordem).

### 13.3 RN-CORE-02 (Q4) no aparelho
1. No sync, o shell lê `GET /v1/me/modulos` (licença checada por requisição) e chama `aplicarModulosAtivos`.
2. Módulo que saiu **sem** itens na fila: dados locais apagados na hora.
3. Módulo que saiu **com** itens: o motor tenta enviar; a API devolve `MODULO_INATIVO` por item; a tela de Perfil
   mostra os itens e o card "Módulo X desativado" com **"Entendi, apagar do aparelho"** (`confirmarLimpeza`).
4. Se o módulo voltar antes da confirmação, os itens voltam a `pendente`.

### 13.4 Transportes (`apps/mobile/src/services/transporte.ts`)
- `v1` (`EXPO_PUBLIC_SYNC=v1`): `POST /v1/sync/push { itens }` → `{ resultados }`; `GET /v1/sync/pull?entidade&cursor` (doc 04; `apps/api`, T-0004).
- `fase-m` (padrão): push legado do mock-api (`pedido` → `order`; `visita` → `visit`, ou `checkout` quando o payload
  traz `visit_id` + `outcome`); sem pull genérico — as cargas vêm das `etapasSync` REST dos módulos.

`criarShell` valida no carregamento: `navegacao` declarada em `apps.web.menus` / `apps.<campo|gestao>.abas`;
`caminho` sem barra e único no shell; `acao` declarada em algum `manifest.acoes`; entidade em `manifest.sync`;
dependências obrigatórias instaladas e sem ciclo.

### 14.2 O que o shell faz
- **Web**: `apps/web/lib/modulos.ts` lê `moduloWeb` de cada módulo instalado; menu lateral por grupo
  (`data-testid="nav-<modulo>-<id>"`); `/<caminho>` servido por `app/(bko)/[...caminho]/page.tsx`
  (`data-testid="pagina-<modulo>-<id>"`); página de plataforma `/auditoria` (`nav-plataforma-auditoria`). Perfil
  fora do BKO (vendedor/promotor, Q6) vê aviso. Efetivos: `GET /v1/me/modulos`; 404 (mock-api) → cálculo local com
  `modulosEfetivos` (todos os instalados ativos no tenant + padrão do perfil).
- **App**: `apps/mobile/src/lib/modulos.ts` lê `moduloApp`; abas = "Início" (`tab-inicio`) + páginas com
  `navegacao` (`tab-<modulo>-<id>`, badge = itens do módulo na fila); tela em `/m/<caminho>`
  (`app/(tabs)/m/[...caminho].tsx`, `pagina-<modulo>-<id>`).
- **Telas de módulo** falam com o shell só por `@macuxi/platform-sdk/react`: `usePode('pedido.criar')`,
  `<SePode acao="pedido.criar">`, `useVisaoShell()`, `useMotorSync()`. Nunca importam `apps/*`.
- **Teste de componente**: `<ShellProvider visao={criarShell('campo', [moduloApp]).montar({ perfil, modulosAtivos })} motor={motorDeTeste}>`.

### 14.3 Instalar um módulo no shell
Uma linha em `apps/web/lib/modulos.ts` e `apps/mobile/src/lib/modulos.ts` (import do manifesto + `web`/`app`),
o pacote no `package.json` do shell e, no web, em `transpilePackages`. Feito para core e vendedor; os demais na
T-0004.

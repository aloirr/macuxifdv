**Lacuna estrutural**: no servidor o Vendedor não pode ler `core.*` nem `catalogo.*` (regra 1), mas precisa do preço da tabela do
cliente (Catálogo) e do cadastro do cliente e do produto (Core) para revalidar e guardar o pedido. No aparelho, o Vendedor não pode
importar o `domain` do Catálogo para calcular o preço. A ADR 0012 resolve as duas coisas com **consultas entre módulos**.

## 1. Decisões
| # | Decisão | Onde |
|---|---|---|
| D-1 | A aprovação (estado do pedido, alçada, transição, auditoria, eventos) **mora no Vendedor**. O Gestor fica com a fila e o prazo em dias úteis (Sprint 6), alimentados pelos eventos, e chama a mesma rota do Vendedor para decidir. O app Gestão ganha a aba **Pedidos**, que é tela do Vendedor | ADR 0011 |
| D-2 | **Dentro da alçada o pedido fica `approved` na hora** (aprovação automática, registrada no histórico). Acima, fica `pending_approval` com o nível (supervisor, gerente ou analista). O `received` vira passagem dentro da transação, não estado de descanso. Motivo: só `aprovado` entra na fila do ERP (RN-INT-08) e na base de apuração das metas (RN-CORE-21) | ADR 0011, P-1 |
| D-3 | Estados no banco e no pull continuam `ORDER_STATUSES` (herdados da Fase M). Os **eventos** usam o vocabulário do doc 03 (RN-VEN-30), por uma função pura do domínio (`statusDoContrato`), porque Gestor e Integração já esperam esse vocabulário | ADR 0011 |
| D-4 | Decidir (aprovar/rejeitar) é **online**, por REST, no Gestão e no BKO. A lista e o detalhe são offline (pull). Aprovar offline seria decidir sobre um estado velho (outro gestor pode ter decidido) | ADR 0011 |
| D-5 | O servidor obtém preço e cadastro por **consultas entre módulos**: `catalogo.precos_cliente@1` e `core.cadastro_resumo@1`, com o mesmo contrato no aparelho (o Catálogo calcula o preço offline para o Vendedor) | ADR 0012 |
| D-6 | O pedido guarda um **retrato** do que foi vendido (nome, documento e endereço do cliente; SKU, nome e unidade do produto; nome do vendedor) no momento em que o servidor aceita. Lista, detalhe, BKO e PDF usam o retrato, sem consulta a outro módulo na leitura. O pedido é um documento: renomear o produto depois não muda o pedido | §4, §10 |
| D-7 | **PDF gerado no cliente** (aparelho e navegador) com um único gerador de HTML puro, no `domain` do Vendedor. Sem geração no servidor | §9 |
| D-8 | **Edição de pedido já aceito fica fora da fatia.** Reenvio igual é aceito sem efeito; reenvio com conteúdo diferente volta `conflito`. Para corrigir um rejeitado, o vendedor duplica (UUID novo). O app só edita o que ainda está na fila | §4, P-2 |

## 3. Contratos (`modules/vendedor/contracts`, dono modulo-vendedor)

### 3.1 Push `pedido` — `PedidoPush` (schema da entidade `pedido`)
É o `CreateOrderRequest` atual com campos novos **opcionais** (compatível com a fila dos APKs já instalados):
| Campo | Tipo | Regra |
|---|---|---|
| `id` | uuid | igual ao `id` do item do push; diferente → `PAYLOAD_INVALIDO` |
| `customer_id` | uuid | carteira (RN-CORE-04) |
| `discount_pct` | 0..100, 2 casas | desconto do pedido (RF-VEN-01); desconto por item fica fora (§14) |
| `items[]` | `{ product_id, quantity: int > 0 }`, 1..200 | item repetido soma quantidade (RN-VEN-21) |
| `condicao_pagamento_id` | uuid, **novo** | entre as permitidas ao cliente (RN-VEN-14); ausente → condição padrão do tenant |
| `observacao` | texto ≤ 500, **novo** | |
| `visita_id` | uuid \| null, **novo** | liga o pedido ao checkout com resultado `pedido` |
| `route_stop_id`, `created_offline_at` | já existem | `created_offline_at` vira `criado_no_aparelho_em` |
| `total_cents` | já existe, informativo | o servidor **nunca** usa (recalcula tudo) |
| `payment_terms`, `branch_id` | legados | ignorados quando há `condicao_pagamento_id`; `branch_id` ignorado |

### 3.2 Linhas do pull (`contracts/sync.ts`)
- `PedidoSyncSchema` ganha: `numero` (texto, legível, único por tenant), `cliente_nome`, `vendedor_nome`, `tabela_preco_id`,
  `condicao_pagamento_id`, `condicao_pagamento_descricao`, `nivel_aprovacao` (`supervisor | gerente | analista | null`),
  `motivos_aprovacao` (`desconto[]`, lista para crescer com crédito/estoque), `aprovacao_automatica` (bool), `decidido_por_id`,
  `decidido_em`, `motivo_rejeicao`.
- `PedidoItemSyncSchema` ganha: `produto_sku`, `produto_nome`, `unidade`.
- Novo `PedidoEventoSyncSchema` (entidade `pedido_evento`, já no `sync` do manifesto): `pedido_id`, `de` (status ou null), `para`,
  `autor_id`, `autor_nome`, `autor_perfil`, `motivo`, `nivel`, `acima_do_nivel`, `ocorrido_em`. É a linha do tempo (RF-VEN-05) e
  a auditoria de negócio do pedido.
- Novas entidades de pull do Vendedor: `condicao_pagamento` (`codigo`, `descricao`, `ativo`, `padrao`) escopo `tenant`, e
  `cliente_condicao` (`cliente_id`, `condicao_pagamento_id`) escopo `carteira`. Ambas já estão no `sync` do manifesto.
- Os APKs antigos (b5cf8f9) ignoram as colunas novas (o app não valida a linha em tempo de execução, ADR 0009 §2); os previews
  novos (critério 8) já vêm com elas.

### 3.3 Respostas REST (`/v1/vendedor`)
Reaproveitam `Order`/`OrderDetail`/`OrderItem`/`OrderEvent` (os componentes do BKO e do app já usam esses tipos), com ajustes
compatíveis: `branch_id`/`branch_name` passam a anuláveis; `number` = `numero`; `subtotal_cents` = total pela tabela;
`discount_cents` = tabela − final; `payment_terms` = descrição da condição; `erp_order_code` = `numero_erp ?? ''`;
`pending_reason` = texto do nível ("Desconto de 8,0% acima da alçada de 5,0%: aguardando supervisor").
`OrderDetail` ganha:
- `cliente: ClienteDoPedido` (retrato: `razao_social`, `nome_fantasia`, `documento`, `endereco`, `bairro`, `cidade`, `uf`,
  `codigo_erp`) — é o que o PDF precisa;
- `aprovacao: { nivel, motivos, desconto_efetivo_pct, limite_vendedor_pct, pode_decidir, acima_do_nivel } | null`
  (`pode_decidir` calculado para quem consulta, §5).

Corpos novos: `AprovarPedidoRequest = { comentario?: string ≤ 500 }` e `RejeitarPedidoRequest = { motivo: string ≤ 500 }`
(o mínimo de 3 caracteres é regra de negócio, 422 `RN-GES-08`, não Zod). `OrderListQuery` ganha `q` (cliente ou número),
`cursor` e `limite` (1..200, padrão 50).

### 3.4 Eventos (`contracts/eventos.ts`; registro em `.coord/contratos/eventos.md`)
Status sempre no vocabulário RN-VEN-30 (D-3). Nenhum nome, documento ou endereço no payload (só ids e códigos do ERP).
| Evento | Quando | Payload |
|---|---|---|
| `vendedor.pedido.criado@1` | pedido aceito pela 1ª vez | o espelho do Gestor (`PedidoCriadoV1`): `pedido_id`, `vendedor_id`, `autor_id`, `cliente_id`, `visita_id`, `tipo: 'pedido'`, `total_cents`, `total_tabela_cents`, `criado_em`, `itens[{produto_id, quantidade, total_cents}]`, mais `status` |
| `vendedor.pedido.status_alterado@1` | cada transição (RN-VEN-30): `null → recebido`, `recebido → aprovado / em_aprovacao`, `em_aprovacao → aprovado / rejeitado`, `→ cancelado` | `PedidoStatusAlteradoV1`: `pedido_id`, `vendedor_id`, `de`, `para`, `alterado_em`, `autor_id`, `motivo` |
| `vendedor.pedido.aprovacao_solicitada@1` | entra em `pending_approval` | `AprovacaoSolicitadaV1`: `pedido_id`, `vendedor_id`, `cliente_id`, `solicitada_em`, `nivel`, `motivos`, `desconto_efetivo_pct`, `total_cents`, `credito: null`, `historico: null` |
| `vendedor.pedido.aprovado@1` (**novo**) | vira `approved` (automático ou decisão) | o `PedidoAprovadoParaFila` pedido pelo Hub (R-20261101-044224-3): `pedido_uuid`, `cliente_external_id`, `vendedor_external_id`, `condicao_pagamento_codigo`, `criado_em`, `aprovado_em`, `observacao`, `itens[{sequencia, produto_external_id, quantidade, preco_unitario_cents, desconto_cents, total_cents}]`, `desconto_total_cents`, `total_cents`. Chaves do ERP anuláveis (vêm do `external_id` do Core; o Hub trata a ausência) |

O schema do `aprovado@1` fica no `contracts` do Vendedor (o publicador é dono do formato); o Hub importa de
`@macuxi/vendedor/contracts` ou mantém espelho. Sem consumidor rodando nesta fatia: os eventos ficam na outbox e o despachante
entrega a quem registrar consumidor depois (ADR 0007).

### 3.5 Consultas (ADR 0012)
| Consulta | Dono (contrato + implementação) | Entrada | Saída |
|---|---|---|---|
| `catalogo.precos_cliente@1` | modulo-catalogo (API e aparelho) | `cliente_id`, `produto_ids[]` (≤ 500), `em` (ISO UTC) | `tabela_preco_id \| null` e, por produto, `{ produto_id, preco_cents \| null, motivo_sem_preco \| null }` (RN-CAT-06: fora da tabela do cliente = `null` com "Sem preço para este cliente.", nunca cai na tabela padrão) |
| `core.cadastro_resumo@1` | modulo-core (só API nesta fatia) | `cliente_ids[]`, `produto_ids[]`, `usuario_ids[]` (≤ 500 cada) | clientes `{ id, razao_social, nome_fantasia, documento, logradouro, numero, bairro, cidade, uf, ativo, external_id }`, produtos `{ id, sku, nome, unidade, ativo, external_id }`, usuários `{ id, nome, perfil, external_id }`; id inexistente fica de fora |

No aparelho o Vendedor lê `cliente` e `produto` locais pelo `motor.linhas` com os tipos de `@macuxi/core/contracts` (o Core está
em `depende`, mesma regra das fontes do índice de busca da T-0008 §2.1); por isso a consulta do Core é só de servidor por enquanto.

## 4. Push `receber` do `pedido` (modulo-vendedor, `modules/vendedor/api`)
Antes do módulo, a plataforma já rejeita: módulo inativo (`MODULO_INATIVO`), promotor (`RN-PRO-01`, item rejeitado no push e 403
nas rotas), payload fora do schema (`PAYLOAD_INVALIDO`). O `receber` roda **uma transação por item** (como `visita-push.ts` do Core)
e devolve `em` no aceito (D-3 da ADR 0009):

1. `operacao: 'remover'` → `rejeitado/RN-VEN-31` ("Use cancelar"). `payload.id ≠ item.id` → `rejeitado/PAYLOAD_INVALIDO`.
2. Perfil sem `pedido.criar` no push → `rejeitado/PERFIL_SEM_ACESSO`. Nesta fatia só o perfil `vendedor` cria pelo app (pedido em
   nome, supervisor/gerente, é RF-GES-05, Sprint 6; analista/assistente criam pelo BKO depois).
3. **Idempotência (RN-VEN-33)**: `insert … on conflict (id) do nothing`. Se já existia: mesmo `vendedor_id` e mesmo
   `hash_envio` (sha256 do payload canônico) → `aceito` sem efeito (nada gravado, nenhum evento); mesmo vendedor e hash
   diferente → `conflito` com a linha atual (D-8); outro vendedor → `rejeitado/ID_EM_USO`.
4. **Carteira**: `customer_id ∉ ctx.carteira()` → `rejeitado/FORA_DA_CARTEIRA`.
5. **Cadastro** (`core.cadastro_resumo@1`): cliente inexistente ou inativo → `rejeitado/RN-VEN-13` (cliente inativo só faz
   orçamento; orçamento está fora da fatia); produto inexistente ou inativo → `rejeitado/RN-VEN-01`.
6. **Preço** (`catalogo.precos_cliente@1`) na data do pedido: `em = min(agora, max(criado_no_aparelho_em, agora − 7 dias))`
   (RN-VEN-01; P-4). Algum item sem preço → `rejeitado/RN-CAT-06` com o SKU na mensagem.
7. **Condição** (RN-VEN-14): `condicao_pagamento_id` fora de `cliente_condicao` do cliente (ou da padrão quando o cliente não
   tem lista) → `rejeitado/RN-VEN-14`.
8. **Alçada** (RN-VEN-10): `politicaDosParametros(ctx.parametros())` → `DiscountPolicy`; `validateOrder({ …, credit: null })`
   (crédito fora da fatia, §14, com o mesmo `null` no aparelho). `rejected` → `rejeitado` com o código da 1ª pendência que
   bloqueia (`discount_blocked` → `RN-VEN-10`; `empty_order`/`invalid_quantity` → `PAYLOAD_INVALIDO`); `pending_approval` →
   `pending_approval` com `nivel` (`supervisor → supervisor`, `manager → gerente`, `director → analista`); `ok` → `approved`
   com `aprovacao_automatica = true`. **O total do servidor vale**, mesmo que o aparelho tenha calculado outro (preço mudou).
9. Grava, na mesma transação: `pedido` (com `numero`, retrato do cliente e do vendedor, `hash_envio`, `recebido_em`), itens com
   `sequencia` 1..n (a mesma do `PedidoParaErp`, T-0011) e retrato do produto, `pedido_evento` (`null → received` e
   `received → approved | pending_approval`, autor = vendedor, motivo "Dentro da alçada (5,0%)" ou o `pending_reason`),
   `tx.auditar` (RN-AUD-01) e os eventos da §3.4.

Funções puras novas no `domain` (testes citando a RN): `statusDoContrato`, `nivelDaAlcada`, `politicaDosParametros`,
`resultadoDoRecebimento(validacao) → { status, nivel, motivos, historico[] }`, `dataDoPreco`, `montarPedidoAprovado` (payload do
`aprovado@1`), `textoPendencia`. A transição `received → approved` entra em `transitions` (hoje não existe).

## 5. Aprovação e rejeição (modulo-vendedor)
| Rota | Ação | Corpo | Sucesso |
|---|---|---|---|
| `POST /v1/vendedor/pedidos/:id/aprovar` | `pedido.aprovar` (supervisor, gerente, analista) | `AprovarPedidoRequest` (comentário opcional; aprovar = 1 toque, RN-GES-08) | 200 `OrderDetail` |
| `POST /v1/vendedor/pedidos/:id/rejeitar` | `pedido.aprovar` | `RejeitarPedidoRequest` | 200 `OrderDetail` |

Ordem no `executar`, numa transação com `select … for update`:
1. Pedido fora do escopo de **usuários visíveis** (`vendedor_id ∉ ctx.usuariosVisiveis()`, RN-CORE-04: supervisor = equipe,
   gerente = equipes abaixo, analista = tenant) ou inexistente → 404 `PEDIDO_NAO_ENCONTRADO` (não revela existência).
2. `decidirAprovacao({ status, nivel, perfil, decisao, texto })` (domínio, puro):
   - status já é o destino da mesma decisão → resultado `repetida` (200 com o estado atual, sem evento; idempotente);
   - status ≠ `pending_approval` → 422 `RN-VEN-30` "Este pedido não está aguardando aprovação.";
   - rejeitar com motivo vazio ou < 3 caracteres depois de `trim` → 422 `RN-GES-08`;
   - alçada: supervisor decide nível `supervisor`; gerente decide `gerente` e também `supervisor` (RN-GES-04, `acima_do_nivel`);
     analista decide `analista` (P-3). Fora disso → 422 `RN-VEN-10` "Este pedido precisa de aprovação do nível X.".
3. Atualiza `status`, `decidido_por_id`, `decidido_em`, `motivo_rejeicao`; grava `pedido_evento` (autor, perfil, nível,
   `acima_do_nivel`, comentário/motivo); `tx.auditar` com antes/depois do status (RN-AUD-01); publica `status_alterado@1` e, se
   aprovado, `aprovado@1`.
- O aviso ao supervisor quando o gerente decide o nível dele (RN-GES-04) e a notificação ao vendedor ficam para quando o
  despachante tiver os consumidores de notificação do Core (§14); o `acima_do_nivel` já fica no histórico.
- O promotor recebe 403 `RN-PRO-01` (plataforma); vendedor e assistente, 403 `PERFIL_SEM_ACESSO` (ação).

## 6. Leitura (modulo-vendedor)
- `GET /v1/vendedor/pedidos` (`pedido.ver`): filtros `status`, `seller_id`, `customer_id`, `from`/`to` (datas no fuso do tenant,
  convertidas para UTC), `q`, `cursor` `(created_at desc, id)`, `limite`. **Escopo pela mesma função do pull** (`escopoDoPedido`):
  promotor = clientes da carteira (só leitura, O-3); os demais = `vendedor_id ∈ usuariosVisiveis` (hoje a rota filtra por
  carteira; muda para ficar igual ao pull e à matriz "Ver pedidos: próprios / equipe / tenant"). Resposta
  `{ itens: Order[], proximo_cursor }`.
- `GET /v1/vendedor/pedidos/:id` (`pedido.ver`): `OrderDetail` com itens, histórico, `cliente` e `aprovacao`; fora do escopo → 404.
- `GET /v1/vendedor/alcadas` (`pedido.ver`): a política vigente montada dos parâmetros (só leitura; a página Alçadas do BKO e o
  aparelho mostram o mesmo número). Editar alçadas com auditoria fica fora (§14).
- Provedores de pull novos: `pedido_evento` (mesmo escopo e janela do pedido, por join), `condicao_pagamento` (tenant),
  `cliente_condicao` (carteira). `pedido` e `pedido_item` ganham as colunas da §3.2.

## 7. Perfis, manifesto e shells
**Manifesto do Vendedor** (modulo-vendedor):
- `perfis: ['vendedor', 'supervisor', 'gerente', 'analista', 'assistente', 'admin']` — padrão do perfil (RN-CORE-01). O promotor
  continua fora (RN-PRO-01).
- `apps: { campo: { abas: ['Pedidos'] }, gestao: { abas: ['Pedidos'] }, web: { menus: ['Pedidos', 'Alçadas'] } }`.
- `pedido.ver` ganha `admin` (matriz: admin vê pedidos do tenant e não cria nem cancela). `pedido.aprovar` continua
  `supervisor, gerente, analista`.
- `publica` ganha `vendedor.pedido.aprovado@1`; `usaConsultas: ['catalogo.precos_cliente@1', 'core.cadastro_resumo@1']`
  (campo novo do manifesto, ADR 0012).
- **Catálogo** (modulo-catalogo): `sync` ganha `cliente_tabela_preco`; `ofereceConsultas: ['catalogo.precos_cliente@1']`.

## 9. PDF
- **Um gerador só**: `buildOrderPdfHtml` sai de `modules/vendedor/app/lib/order-pdf.ts` para `modules/vendedor/domain/pdf-pedido.ts`
  (puro, sem React/RN; os testes vão junto). O `domain` entra no `tsconfig` do app e do web, então os dois importam o mesmo arquivo.
  A formatação no fuso (`zonedParts`) passa para `@macuxi/comum` (E5) para o domínio não importar `@macuxi/ui`.
- **Entrada**: um `OrderPdfOrder` montado do `OrderDetail` (BKO e Gestão online) ou das linhas locais (Campo e Gestão offline),
  por uma função pura `pdfDoPedido(detalhe)`. As duas versões do RF-VEN-06 continuam: **cliente** (preço final, sem nenhum `%`) e
  **interna** (tabela, desconto %, alçada, status e histórico).
- **Campo e Gestão**: `expo-print` gera o A4 e `expo-sharing` abre o compartilhar (WhatsApp, e-mail), como já faz o Campo.
- **BKO**: o mesmo HTML num iframe oculto e a impressão do navegador ("Salvar como PDF"; o `<title>` sugere o nome do arquivo).
  A função `imprimirHtml(html, titulo)` vai para `@macuxi/platform-sdk/web` (E6).
- **Por que no cliente e não no servidor**: (1) funciona offline, inclusive com o pedido ainda na fila; (2) um layout só, testado
  em Vitest, para os três canais; (3) gerar PDF no servidor exige Chromium sem interface (centenas de MB na imagem da API) ou uma
  biblioteca de layout própria — dependência pesada, com ADR; (4) nenhum arquivo com dado de cliente fica guardado no servidor.
  Custo: no BKO o usuário confirma "Salvar como PDF" no diálogo do navegador (P-5). Download direto de `.pdf` ou PDF anexado por
  e-mail pelo servidor, se forem pedidos, viram tarefa com ADR (geração no `worker`).

### 11.1 Como usar o que a onda 1 entregou (E1–E7)
- **Contrato da consulta** (dono, no `contracts`): `export const PrecosCliente = definirConsulta({ nome: 'catalogo.precos_cliente@1',
  entrada: z.object({ … produto_ids: z.array(…).max(500), em: … }), saida: z.object({ … }) })`. Manifesto do dono:
  `ofereceConsultas: ['catalogo.precos_cliente@1']`; do consumidor: `usaConsultas: [...]` (dono em `depende`/`opcionais`).
- **API (dono)**: `definirModuloApi({ manifesto, consultas: [implementarConsulta(PrecosCliente, async (entrada, ctx) => saida)] })`;
  `ctx` = `{ db, usuario, requestId, agora, parametros, log }` (mesma transação de quem consulta; SQL só no próprio schema).
  Consulta oferecida sem implementação = a API real não sobe (`consultasSemImplementacao`; fixture de teste que troca o
  módulo monta e a consulta fica `ConsultaIndisponivel`).
- **API (consumidor)**: `ctx.comTenant(async (db, tx) => { const p = await tx.consultar(PrecosCliente, { … }); … })`. Dono inativo →
  `ConsultaIndisponivel` (`ErroHttpModulo` 503 `CONSULTA_INDISPONIVEL`; `ehConsultaIndisponivel(e)`), que o `receber` pode deixar
  subir (o motor reenvia o lote) ou tratar.
- **Aparelho (dono)**: `definirModuloShell({ …, consultas: [implementarConsultaAparelho(PrecosCliente, async (entrada, ctx) => saida)] })`;
  `ctx` = `{ linhas, linhasPorIds, agora, usuario, parametros }` e só lê entidades do próprio módulo.
  **Aparelho (consumidor)**: `useAmbiente().consultar(PrecosCliente, { … })` (offline). Sem implementação no aparelho (ex.:
  `core.cadastro_resumo@1`) → `ConsultaIndisponivel`.
- **Auditoria (E2)**: `tx.auditar({ acao: 'pedido.aprovar', entidade: 'pedido', entidade_id, antes: { status }, depois: { status } })`
  → `plataforma.auditoria` com módulo da rota, usuário, `request_id` e o relógio da requisição; só ids, códigos e status.
- **Parâmetros (E3)**: na API `ctx.parametros()` (módulo da rota/provedor; ex.: `alcada.vendedor_pct`); no aparelho
  `useAmbiente().parametros('vendedor')` ou `useParametros('vendedor')`, guardados do último `GET /v1/me/modulos` (offline).
- **Extensão por app (E4)**: `{ slot: 'cliente.acoes', id: 'novo-pedido', acao: 'pedido.criar', apps: ['campo'], payload }`.
- **Fuso (E5)**: `import { zonedParts, localIsoDate, formatHHMM } from '@macuxi/comum/fuso'` (subcaminho; fora do índice de
  `@macuxi/comum` para não colidir nomes). `@macuxi/ui/mobile` e `/mobile/puro` reexportam o mesmo.
- **PDF no BKO (E6)**: `import { imprimirHtml } from '@macuxi/platform-sdk/web'`; `await imprimirHtml(buildOrderPdfHtml(…), 'Pedido 123 - Cliente')`.
- **Gestão**: nenhum código no shell; o Vendedor aparece lá quando o manifesto tiver `apps.gestao` e supervisor/gerente em `perfis`
  (teste do estado-alvo em `apps/mobile/src/lib/instalados.test.ts`).

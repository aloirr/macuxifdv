## 2. Super-admin (resumo da ADR 0029)
- Perfil **de plataforma, fora dos tenants**: tabela `plataforma.super_admin` (sem `tenant_id`, como `plataforma.tenant`), RLS ligado e forçado
  **sem política** para `macuxi_app` (0 linhas); só funções `SECURITY DEFINER` com `search_path` fixo, uma por operação.
- **Primeiro uso** (Alexandre, sem linha de comando): `/config/primeiro-acesso` pede e-mail, nome, senha e o **código de convite**
  (`MACUXI_SUPERADMIN_CONVITE`, ≥ 32 caracteres, secret do environment `PRODUCAO`/`.env`). Só funciona com **zero** super-admins
  (a função cria com trava e devolve "já existe"); depois disso a rota responde 410 para sempre. Em seguida o cadastro do TOTP é obrigatório.
- **Login em 2 etapas**: senha → desafio (5 min) → código TOTP **ou** código de recuperação → sessão. Sem TOTP confirmado não há sessão.
- **TOTP** RFC 6238 (SHA-1, 6 dígitos, 30 s, janela ±1, sem reuso do mesmo passo), segredo de 20 bytes **cifrado** (AES-256-GCM,
  chave `MACUXI_CHAVE_TOTP`, 32 bytes em base64; formato `v1.<iv>.<tag>.<cifra>`, AAD = id do super-admin). Feito com `node:crypto` (sem
  dependência). **10 códigos de recuperação** de uso único (`XXXXX-XXXXX`, 50 bits), guardados só como SHA-256, mostrados uma vez.
- **Sessão curta**: token JWT com **segredo próprio** (`MACUXI_JWT_SEGREDO_PLATAFORMA`; o token de tenant nunca vale aqui e vice-versa),
  `aud=macuxi-plataforma`, `sub`, `sid`, `amr=["pwd","otp"]`, validade **15 min**, renovado enquanto há uso; teto absoluto **8 h** e
  revogação gravados na sessão, conferidos **a cada requisição** no banco.
- **Bloqueio**: 5 falhas (senha ou código) → 15 min; mais o limite por IP das rotas públicas. Mesma resposta para e-mail inexistente e senha errada.
- **Toda ação auditada** em `plataforma.auditoria_plataforma` (append-only): login, falhas, TOTP, recuperação, e **toda** requisição feita
  com o token do super-admin (gravada pela API no fim da resposta, inclusive as recusadas). Sem dado pessoal: ids, rota (modelo, não a URL),
  status, contagens, `request_id` e o prefixo do IP (/24 ou /48). O fato da tela também vai à `plataforma.auditoria` **do tenant**
  (`tx.auditar`, com `usuario_id` = id do super-admin): o cliente vê o que a Macuxi fez na base dele.
- **Só no host `config.`**: o apps/web serve `/config/*` só no host do portal (nos outros hosts, 404) e guarda o token no `sessionStorage`
  da origem `config.` (o BKO, em outra origem, nunca o vê). Camada extra recomendada, sem código: Cloudflare Access no host `config.`
  com o e-mail do Alexandre (decisão dele; não bloqueia).

## 3. Como uma rota exige super-admin (SDK)
`PERFIS` **não** ganha "super_admin" (o perfil vive dentro do tenant; o super-admin não). Em vez disso:
1. **Rota de módulo com dado de tenant** (cartões, Integração, parâmetros): opção nova `RotaModulo.superAdmin`:
   - ausente (padrão): o token do super-admin **não** vale (401), como hoje;
   - `'aceita'`: vale o usuário do tenant (como hoje) **e** o super-admin;
   - `'exige'`: só o super-admin (usuário do tenant = 403 `PERFIL_SEM_ACESSO`).

   Requisição do super-admin: `Authorization: Bearer <token de plataforma>` + cabeçalho **`x-macuxi-tenant: <uuid>`**. A API
   (`autenticarSuperAdmin` do Core) confere a sessão, o tenant (existe e está ativo; senão 404 `TENANT_NAO_ENCONTRADO`) e monta o usuário
   da requisição: `{ id: <id do super-admin>, tenant_id: <cabeçalho>, perfil: 'admin', modulos: efetivos do TENANT }` e
   `ctx.superAdmin = { id, sessao_id }`. Continua valendo: **licença do módulo no tenant** (403 `MODULO_INATIVO`), Zod, RLS do tenant
   (`comTenant` com o tenant do cabeçalho). Não vale: ação/perfil do manifesto (o `superAdmin` da rota é a autorização) e carteira (`'tenant'`).
   **Regra para quem marca a rota**: a rota não grava o `ctx.usuario.id` em coluna com FK para `core.usuario` (o super-admin não é usuário
   do tenant); `tx.auditar` pode (a coluna não tem FK).
2. **Rotas sem tenant** (listar e criar empresa): são da **plataforma**, montadas pela API em `/v1/plataforma/*` (como
   `/v1/me/modulos`), porque a criação usa o `planoDeOnboarding` sobre **todos** os manifestos (raiz de composição; o Core não importa
   manifesto alheio). Não há tipo de rota novo para módulo.
3. **Autenticação** (primeiro acesso, login, TOTP, renovar, sair): `rotasPublicas` do Core em `plataforma/auth/*`, com limite por IP
   (o Core confere o token sozinho em renovar/sair/regerar códigos, como já faz no refresh).

Tipos novos em `packages/platform-sdk/src/plataforma.ts`: `SuperAdminAutenticado`, `ModoSuperAdmin`, `CABECALHO_TENANT_PLATAFORMA`,
`AUDIENCIA_TOKEN_PLATAFORMA`, `SESSAO_PLATAFORMA`; `ServicosCore.autenticarSuperAdmin?(cabecalhos, banco)`; `RotaModulo.superAdmin?`;
`ContextoBase.superAdmin?` (opcional: os contextos falsos dos testes dos módulos não quebram).

## 4. Contratos das rotas do portal (Zod no SDK, `plataforma.ts`)
| Rota | Dono | Entrada → saída |
|---|---|---|
| `POST /v1/plataforma/auth/primeiro-acesso` | Core (pública, 5/15 min por IP) | `PrimeiroAcessoSchema` `{ email, nome, senha, convite }` → `EtapaLoginSchema` (`etapa: 'cadastrar_totp'`); 410 `PRIMEIRO_ACESSO_ENCERRADO` |
| `POST /v1/plataforma/auth/login` | Core (pública, 10/5 min) | `LoginPlataformaSchema` `{ email, senha }` → `EtapaLoginSchema` `{ etapa: 'segundo_fator' \| 'cadastrar_totp', desafio, expira_em }`; 401 `CREDENCIAIS_INVALIDAS`, 423 `BLOQUEADO` |
| `POST /v1/plataforma/auth/totp/iniciar` | Core | `{ desafio }` (etapa `cadastrar_totp`) → `TotpInicioSchema` `{ otpauth_uri, segredo_base32 }` (o segredo fica cifrado e pendente) |
| `POST /v1/plataforma/auth/totp/confirmar` | Core | `{ desafio, codigo }` → `TotpConfirmadoSchema` `{ codigos_recuperacao: string[10], sessao: SessaoPlataformaSchema }` (códigos **uma vez**) |

## 5. O que cada passo da tela chama
### 5.1 Passo Empresa (por baixo, o `tenant:criar` da T-0083)
`CriarEmpresaSchema`: `codigo` (o mesmo check da 0001), `razao_social`, `cnpj` (14 posições; aceita o CNPJ alfanumérico de 2026; DV pelo
`@macuxi/comum/documento`), `fuso` (padrão `America/Manaus`), `modulos: [{ modulo, licencas | null }]` (core entra sempre; **integracao
entra sempre**, porque o portal carrega as bases pelo Hub), `parametros` (alçadas vendedor/supervisor/gerente em %, `validade_orcamento_dias`,
`aplicacao_no_orcamento_padrao`; padrões do doc 03; alçadas em ordem crescente) e `simular` (o "Conferir" do passo).
A API valida pelo `planoDeOnboarding` (dependências, RN-CORE-03) e grava pela função do banco: `provisionar_tenant` **sem admin** (o admin
do cliente vem na Equipe, com convite) e com as linhas de `plataforma.parametro` do Vendedor (`alcada.vendedor_pct`, `alcada.supervisor_pct`,
`alcada.gerente_pct`, `validade_orcamento_dias`, `aplicacao_no_orcamento_padrao`). **Idempotente pelo `codigo`** (mesma regra da RN-CORE-31: tenant
existente não muda nome/fuso; módulos faltantes entram; parâmetro já gravado não muda). Resposta: `{ tenant_id, codigo, resultado, modulos_adicionados,
parametros_gravados, avisos, simulado }`. Auditoria: `tenant.provisionar` no tenant + a linha da plataforma.
### 5.2 Cartões das bases e aba Integração (modulo-integracao; só `superAdmin: 'aceita'` nas rotas que já existem)
- Importar / Conferir sem gravar / modo delta ou completo: `POST /v1/integracao/cargas-arquivo` (T-0032) e as partes da N3 (`carga-partes`).
- Status, erros por linha, "Baixar erros (.csv)": `GET /v1/integracao/lotes/:id`, `.../lotes/:id/erros` e a versão `.csv` (`tipoConteudo` CSV).
- "Baixar modelo (.csv)" e "Dicionário de campos": rotas da N1 (`modelos/:entidade.csv`, dicionário em JSON) — por isso o SDK aceita o ponto.
- Ordem dos cartões: a ordem de carga do Hub, lida de rota da Integração (o portal não tem lista própria).
- Credencial da API "mostrada uma vez": `POST /v1/integracao/conectores` (ADR 0013; a chave em claro só nessa resposta). Download do
  Conector e documentação: rotas da N2 (OpenAPI 3.1, `openapi.json` + página) e o link do pacote do Conector.
### 5.3 Equipe (fatia E, modulo-core)
Rota do Core com `superAdmin: 'aceita'` (o admin do tenant também usa no BKO), mesmo padrão de cartão (conferir, gravar, erros por linha,
"Baixar erros"), convite de 1º acesso no lugar da senha. Sem envio de e-mail na plataforma: o convite é um link de uso único com prazo, que
o portal lista para copiar (desenho curto do modulo-core).

## 6. Banco (banco-dados) — migração aditiva 0035 (`0035_plataforma_super_admin`; a 0034 é a `marca_nome` da T-0085)
- `plataforma.super_admin`: `id`, `email` (único por `lower`), `nome`, `senha_hash` (argon2id, o check da 0004), `totp_segredo_cifrado`,
  `totp_pendente_cifrado`, `totp_confirmado_em`, `totp_ultimo_passo bigint`, `recuperacao_hashes text[]`, `falhas`, `bloqueado_ate`, `ativo`,
  `created_at`, `updated_at`, `deleted_at`, `external_id`. **Sem `tenant_id`** (exceção da regra 5 pela ADR 0029, como `plataforma.tenant`).
- `plataforma.super_admin_sessao`: `id`, `super_admin_id`, `criada_em`, `ultimo_uso_em`, `expira_em` (teto de 8 h), `revogada_em`, colunas padrão.
- `plataforma.super_admin_desafio` (ou colunas na sessão): desafio da 2ª etapa com prazo de 5 min e uso único.
- `plataforma.auditoria_plataforma` (append-only: sem `update`/`delete` para ninguém além do dono): `id`, `super_admin_id`, `sessao_id`,
  `tenant_id` (nulo fora de tenant), `acao`, `metodo`, `rota`, `status`, `request_id`, `ip_prefixo`, `detalhes jsonb`, `ocorrido_em`.
- Funções `SECURITY DEFINER` (grant só ao `macuxi_app`; nunca ao `macuxi_worker`): `sa_existe()`, `sa_criar_primeiro(...)` (trava consultiva;
  só com 0 linhas), `sa_para_login(email)`, `sa_registrar_falha`/`sa_registrar_sucesso`, `sa_gravar_totp_pendente`, `sa_confirmar_totp`,
  `sa_usar_recuperacao`, `sa_abrir_sessao`/`sa_sessao_valida(sid)`/`sa_renovar`/`sa_revogar`, `sa_auditar(...)`, `sa_listar_tenants(sid)`,
  `sa_tenant_ativo(sid, tenant)` e `sa_provisionar_tenant(sid, p jsonb)` (confere a sessão viva e chama a `provisionar_tenant`).
- `provisionar_tenant`: `admin` opcional quando `p.sem_admin = true` (o comando da T-0083 continua exigindo) e `parametros: [{ modulo, chave, valor }]`
  com `on conflict do nothing`. Testes (CI): 42501 para `macuxi_worker`; `macuxi_app` lê 0 linhas direto nas tabelas; append-only da auditoria.

## 7. Feito nesta rodada (engenheiro-software)
- **Caminho com ponto**: segmento literal com pontos internos (`openapi.json`) e parâmetro com sufixo (`:entidade.csv`); recusa ponto no início,
  no fim e duplo. `:a.csv` e `:b.csv` são a mesma rota; `.json` é outra. RN-PRO-01: `pedidos.csv` continua caminho de pedido.
- **`tipoConteudo`** (lista fechada `TIPOS_CONTEUDO_ROTA`: JSON, CSV, texto, markdown, YAML; sem HTML/JS/SVG porque a API é servida pela origem do
  portal) e **`nomeArquivo`** (fixo ou função da entrada; `NOME_ARQUIVO_ROTA_RE`). A API manda `Content-Type`, `Content-Disposition: attachment`
  e `nosniff`; corpo fora de `string`/`Uint8Array` ou nome fora do padrão = 500 sem cabeçalho de download. Fixture sem `definirModuloApi` também é conferida.
- **Contrato do portal** (`packages/platform-sdk/src/plataforma.ts`): schemas do §4, `CriarEmpresaSchema` (CNPJ com dígitos conferidos,
  parâmetros iniciais com os padrões do doc 03), `linhasDosParametrosIniciais`, `planoDeOnboardingSemAdmin` (`onboarding.ts`);
  `RotaModulo.superAdmin`, `ServicosCore.autenticarSuperAdmin`, `ContextoBase.superAdmin`; rota pública do Core só em `plataforma/auth/*`.
- **API** (`apps/api/src/plataforma.ts` + `app.ts`): modo super-admin do §3 (cabeçalho `x-macuxi-tenant`, `sa_tenant_ativo`, licença do
  tenant, carteira `'tenant'`, sem ação/perfil), `GET|POST /v1/plataforma/empresas` (simular = transação desfeita), auditoria de toda requisição
  do super-admin no `onResponse` (`sa_auditar`, prefixo do IP) e os campos do super-admin nos caminhos redigidos do pino (`config.ts`).
  As chamadas ao banco usam os nomes do §6: até a 0035 chegar, só os testes com fonte falsa provam o fluxo.
- Testes: `packages/platform-sdk/src/{api-conteudo,plataforma}.test.ts`, `apps/api/test/{conteudo-rota,super-admin}.test.ts`.

## 8. Testes pedidos
- modulo-core: vetores do RFC 6238; reuso do mesmo passo recusado; cifra/decifra com AAD trocada falha; códigos de recuperação de uso único;
  bloqueio após 5 falhas; token de tenant recusado em `autenticarSuperAdmin` e token de plataforma recusado no `autenticar`; log sem e-mail/código/segredo.
- engenheiro-software (API): rota sem `superAdmin` recusa o token de plataforma; `'exige'` recusa usuário do tenant; sem `x-macuxi-tenant` = 400;
  tenant inativo = 404; licença do tenant vale; toda requisição do super-admin gera 1 linha de auditoria, inclusive 4xx.
- banco-dados (CI): §6. testes (CI): fluxo dos critérios 1–4, isolamento (super-admin num tenant não vê outro) e varredura do log.

## 3. Backup e restauração (scripts do banco-dados, interface pedida por recado)
**Agendamento (já instalado pelo deploy):** `macuxi-backup.timer`, às 06:15 UTC, roda `/opt/macuxi/backup/backup-dbaas.sh` como o usuário de deploy. A unidade é pulada sem erro enquanto o script não existir.

**De onde vêm os scripts:** o `implantar.sh` copia de `/app/db/backup/` da imagem publicada os arquivos `backup-dbaas.sh`, `ensaio-restauracao.sh` e `contagem.sql`.

**`backup-dbaas.sh`, em `/opt/macuxi`:**
1. roda `dc --profile ferramentas run --rm -T pgcliente pg_dump -d macuxi -Fc -Z 6 --enable-row-security > tmp`. O admin herda o `macuxi_manutencao`, então a política `manutencao` mostra todas as linhas;
2. roda `pg_restore -l` para conferir o dump (pode ser no próprio `pgcliente`);
3. grava a contagem do momento: `contagem.sql` no `pgcliente`, salva ao lado do dump;
4. roda `dc --profile ferramentas run --rm -T backup enviar < tmp`. O bucket é `macuxi-prod`, em `backups/`, e `MACUXI_BACKUP_DIAS=30` já está no compose.

**`ensaio-restauracao.sh [ultimo|<chave>]`:**
1. baixa o dump (sha256 conferido);
2. cria `macuxi_ensaio_<UTC>` no DBaaS e roda `pg_restore --exit-on-error --single-transaction` pelo `pgcliente`;
3. roda o `contagem.sql` na base restaurada e compara com a contagem gravada junto do dump;
4. **apaga a base temporária sempre**, mesmo com falha (trap);
5. termina com a linha `[ensaio] resultado: IGUAL ...` e código 0, ou `[ensaio] resultado: DIFERENTE ...` e código diferente de 0.

O banco `macuxi` nunca é tocado.

**Onde o ensaio roda:** o workflow `producao — ensaio de restauração` e o job `stack-producao` o executam quando o script existir.

## 4. Às 8h de 06/11: o que o Alexandre faz

**1. VM `macuxi-prod-se1`**
- Ubuntu 24.04, br-se1, na **mesma VPC do DBaaS** e com disco de 40 GB ou mais.
- Grupo de segurança só com a porta **22**. O túnel é conexão de saída, então nenhuma outra porta abre.
- Chave SSH **nova, só da produção** (por exemplo `macuxi-prod-deploy`). A pública vai para o `authorized_keys` do usuário `ubuntu`.

**2. DBaaS `macuxi-prod-db`**
- PostgreSQL 16, 2 vCPU e 8 GB, na mesma VPC, com criptografia em repouso.

- Se o console oferecer o **certificado da CA**, baixe o PEM.
- Não crie banco nem papel: o deploy faz isso.

**3. Bucket `macuxi-prod`**
- Bucket privado, em br-se1.
- Crie uma chave de Object Storage com leitura e escrita nele.

**4. Túnel `macuxi-prod` na Cloudflare**

## 5. Depois do aviso: o que o gerente faz

**1. Escolher o commit.** Ele tem de cumprir três condições:
- estar no `main`;
- ter CI verde;
- ter o "demo — publicar" verde, porque é esse workflow que publica a `macuxi-api:<sha>`. O ideal é o commit que está na demo.

**2. Criar e enviar a tag** (o git é só dele):
```
git tag -a v1.0.0 <sha> -m "v1.0.0: primeira produção"
git push origin v1.0.0
```

**3. Acompanhar o run e pedir a aprovação.** Em Actions → "producao — publicar", os jobs `conferir` e `bko` rodam sozinhos. O `deploy` espera a aprovação: peça ao Alexandre.

**4. Conferir o resultado:**
- o resumo do run termina com `publicado: v1.0.0`, `api.macuxifdv.com.br: v1.0.0 no ar` e `bko.macuxifdv.com.br: ok`;
- `https://api.macuxifdv.com.br/v1/saude` mostra `"versao":"v1.0.0"`, `"banco":"ok"` e `"alertas":[]`;
- `https://bko.macuxifdv.com.br/login` e `https://config.macuxifdv.com.br` abrem;
- os avisos (`::warning::`) do log merecem atenção: TLS sem CA, sonda do S3 e backup ainda sem script.

**5. Criar o tenant de teste:** Actions → "producao — criar tenant" → Run workflow. Precisa da aprovação do Alexandre.
- **1ª vez, com `simular` marcado:** o tenant não é gravado. Confira a linha JSON.
- **2ª vez, sem `simular`:** o tenant é criado, e a saída mostra `"resultado":"criado"`. Exemplo de valores: código `teste-macuxi`, módulos `core,catalogo,vendedor,promotor`.

**6. Pedir o APK.** O APK de produção é do engenheiro-apps, com o perfil EAS `production` e a API `https://api.macuxifdv.com.br/v1`. Ele deve entrar no tenant de teste.

**7. Ensaiar a restauração** depois do primeiro backup (06:15 UTC do dia seguinte): Actions → "producao — ensaio de restauração". Precisa do script do banco-dados na imagem publicada.

## 6. Como voltar atrás
- **Automático:** se a versão nova não passa na conferência, o `implantar.sh` volta sozinho e o run sai vermelho com "a produção VOLTOU para a versão anterior". Os sinais de falha são:
  - `/v1/saude` sem `banco ok` ou sem a versão da tag;
  - BKO fora do ar.

  Se a falha acontece **antes** de subir (pull, banco, migração), nada da aplicação mudou.
- **Para uma versão anterior, à mão:** Actions → o run da **tag anterior** → "Re-run all jobs" → aprovação. O workflow publica de novo aquela imagem, pelo mesmo digest.
- **Migrações não voltam sozinhas.** Elas são aditivas, e a versão anterior roda sobre o esquema novo. Desfazer uma migração ou restaurar dados é manual: banco-dados com o Alexandre, partindo do ensaio de restauração.
- **Tirar a produção do ar já:** o Alexandre desliga os hostnames públicos do túnel `macuxi-prod` no painel da Cloudflare. A VM e o banco ficam intactos.
- **VM perdida:**
  1. crie a VM de novo com a mesma chave e rode outra vez o run da tag em uso;
  2. o `preparar-vm.sh` gera senhas novas, e o `migrar up` as grava nos papéis (B0);
  3. o JWT novo obriga os usuários a entrar de novo;
  4. o pepper novo exige reemitir as chaves do Conector.

## 7. Ensaio no CI (job `stack-producao` do `stack-isolado.yml`)
O job usa um Postgres 16 de teste no próprio runner, no lugar do DBaaS:
- **TLS obrigatório:** o `pg_hba` só tem `hostssl`. O certificado é do job, com o IP no SAN, então o teste é `verify-full` de verdade;
- **admin `macuxi_admin_sem_super`:** LOGIN CREATEDB CREATEROLE, membro de `pg_read_all_data`/`pg_write_all_data`, os mesmos atributos do `db/scripts/admin-sem-superusuario.ts`;
- **`vector` no `template1`:** é o equivalente ao `pgextwlist` do DBaaS.

Etapas e o que cada uma confere:
1. **`preparar-vm.sh` duas vezes:** que é idempotente, que os dois timers ficam ativos e que as faixas do Docker foram aplicadas.
2. **1º deploy, com o banco do zero:**
   - banco criado;
   - `vector` instalada;
   - papéis criados pelo B0;
   - herança da 0031;
   - `conferir-rls.sql` com 0 linhas;
   - `/v1/saude` com a versão;
   - sonda do S3 falso.
3. **Conexões:** `macuxi_app` e `macuxi_worker` com `ssl = t`, e a rede do compose em 192.168.200.0/21.
4. **2º deploy:** nada pendente.
5. **Imagem quebrada:** `implantar.sh` sai com 3, a produção fica na versão anterior e o `imagens.env` volta.
6. **`macuxi-alerta.service`:** "Macuxi producao: ... -> ok" no journal.
7. **`tenant:criar`:** `"resultado":"criado"`.
8. **Backup e ensaio:** só quando os scripts do banco-dados estiverem na imagem.

**Pendência:** o `stack-producao` ainda não rodou. Ele roda no 1º push em `verificacao/**` ou PR que mexa em `scripts/deploy/**`. Até lá, os scripts só têm a sintaxe validada (`bash -n`), e o YAML só foi conferido pelo parser.

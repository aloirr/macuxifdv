# T-0038 — Domínio fixo da demo (desenho técnico)

Escopo do engenheiro-software: `scripts/demo/**` e `apps/api`. O mapa de subdomínios está no doc 04 ("Domínio e
endereços"), e a regra das credenciais da Cloudflare, no doc 07.

## 1. Peças
| Arquivo | Papel |
|---|---|
| `scripts/demo/tunel.ps1` | funções compartilhadas (dot-source): achar/instalar o cloudflared, `tunnel list`, config.yml, marcador, abrir o túnel nomeado ou o rápido, escolha com reserva (`Abrir-TunelDemo`) |
| `scripts/demo/configurar-dominio.ps1` | uma vez por PC, depois do `cloudflared tunnel login`: túnel `macuxi-demo`, `route dns` de `api-demo` e `bko-demo`, config.yml, marcador |
| `scripts/demo/subir-demo.ps1` | 7 etapas: Docker, banco, seed, API+worker, `next build`, túnel, `next start` + conferência |
| `scripts/demo/derrubar-demo.ps1` | túnel(is) → BKO → worker → API; órfãos por porta e linha de comando (inclusive o cloudflared da demo) |

## 2. Decisões
1. **Credenciais intocadas**: nenhum script abre `%USERPROFILE%\.cloudflared`. O config.yml **não** tem
   `credentials-file`, e o cloudflared acha o `<id>.json` na pasta padrão dele. Login conferido por `tunnel list` (sem
   cert.pem o comando falha). O config.yml e o marcador `tunel.json` ficam em `.dados\demo\cloudflared\` (git ignora)
   e só guardam o id do túnel, que é público (CNAME `<id>.cfargotunnel.com`).
2. **Idempotência** do `configurar-dominio.ps1`: túnel por nome (`tunnel list --name`, cria só se faltar); `route dns`
   é idempotente no próprio cloudflared ("already configured"). Registro DNS apontando para outro lugar para a
   execução, e só `-SobrescreverDns` (`--overwrite-dns`) troca. O config.yml só é regravado se o texto mudou, e o
   `tunnel ingress validate` confere o arquivo.
3. **Execução pelo id** (`tunnel --config <cfg> run <id>`), e não pelo nome: o id vem do marcador, então a subida não
   chama a API da Cloudflare para resolver o nome nem depende do cert.pem. O túnel é o `macuxi-demo` do mesmo jeito.
   Pronto = linha "Registered tunnel connection" no log (até 2 min).
4. **Reserva**: sem marcador, com `-TunelRapido` ou se o nomeado não conectar, o script abre dois túneis rápidos
   (API e BKO) e avisa que os APKs de preview não conectam por eles (só o build de desenvolvimento, em Avançado).
5. **BKO** (combinado com o engenheiro-apps, R-20261101-173817): `next build` + `next start -p 3100 -H 127.0.0.1`;
   `NEXT_PUBLIC_API_URL=http://127.0.0.1:8100/v1` no build e no start (destino do rewrite `/api-proxy`, do lado do
   servidor); `MACUXI_BKO_ORIGEM` = origem pública do BKO (lida pelo `next.config.ts`). O rewrite vai pelo loopback e
   não pelo `api-demo`, por dois motivos: latência, e o X-Forwarded-For chega intacto (o proxy do Next não acrescenta
   XFF), então o limite de login conta cada navegador.
6. **"Pronto" só depois de conferir**: no PC, `/v1/saude` com `servico = macuxi-api`, `/login` do BKO e
   `/api-proxy/saude`; pela internet, `api-demo/v1/saude` e `bko-demo/login`. Falha local = erro (saída 1). Falha só
   pela internet = "No ar, mas SEM confirmação" (saída 3, processos no ar).

## 3. API
Nada muda no comportamento: **sem CORS e sem cookie, de propósito**. O navegador só fala com o BKO (same-origin), o
proxy do Next fala com a API pelo loopback, e o app usa `Authorization: Bearer`. Liberar a origem `bko-demo` no CORS
abriria superfície sem uso. `MACUXI_TRUST_PROXY=loopback` (T-0026) cobre os dois caminhos (cloudflared → API e
cloudflared → Next → API). Os testes em `apps/api/test/app.test.ts` ("BKO em https://bko-demo...") fixam isso:
chamada com `Origin` do bko-demo aceita, IP do XFF, nenhum `Access-Control-*`, nenhum `Set-Cookie` e preflight recusado.
Se um dia o BKO chamar a API direto do navegador, é ADR nova com allowlist de origens por variável.

## 4. Testes
Com um cloudflared simulado (node, fora do repositório), conferi: sem login (sai 1 e orienta), 1ª execução (cria,
roteia, grava), 2ª execução (não cria nem regrava), DNS de outro dono (para; `-SobrescreverDns` troca), mudança de
porta (regrava); escolha do túnel (sem marcador → rápido; com marcador → nomeado com `--config` e o id; `-Rapido`;
nomeado falha → rápido, com o log do nomeado preservado; marcador inválido ignorado). Os 4 scripts passam no parser
do PowerShell 5.1. A subida completa não foi rodada aqui: ela recria a base demo, compartilhada com outros agentes, e
o túnel de verdade exige a autorização da Cloudflare. Quem valida pelo domínio é o testes (T-0038, passo 3).

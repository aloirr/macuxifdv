## 1. Workspace
- `db` entrou em `pnpm-workspace.yaml` (commit 1672e82) como pacote `@macuxi/db`. Os testes de `db/testes/`
  rodam no `pnpm test` da raiz.
- `turbo.json`: a tarefa `test` declara `env: ["MACUXI_PG_*"]`. Sem isso o modo estrito do turbo 2
  **filtra** as variáveis e `MACUXI_PG_EXIGIR=1` não chega ao vitest (os testes de banco pulariam no CI
  sem erro, conferido em 2026-10-31). `@macuxi/db#test` tem `cache: false`: o resultado depende do
  Postgres estar de pé (e do `.env`, que o turbo não enxerga), então não pode ser reaproveitado do cache.

## 2. Compose da raiz — decisão: só `include`
**Decisão.** `docker-compose.yml` da raiz **não define serviço**; só faz `include: [db/docker-compose.yml]`
com `name: macuxi`. A única definição do Postgres é a do banco-dados (`db/docker-compose.yml`).

- `docker compose up -d` na raiz e `pnpm --filter @macuxi/db banco subir` (que roda
  `docker compose -f db/docker-compose.yml`) resolvem para o **mesmo projeto** `macuxi`, o mesmo contêiner
  `macuxi-postgres` e o mesmo volume `macuxi_macuxi-pgdata` (conferido com `docker compose config` nos dois
  caminhos). Não há como subir dois Postgres.
- O `name: macuxi` da raiz é obrigatório: no `include` o `name` do arquivo incluído é ignorado e o projeto
  passaria a ser o nome da pasta, criando outro volume.
- Requer Docker Compose ≥ 2.20 (local: v5.6.1).
- Atalhos no `package.json` da raiz: `pnpm db:subir`, `pnpm db:derrubar`, `pnpm db:migrar` (delegam ao CLI
  do `@macuxi/db`, que também cria o banco de dev e o papel `macuxi_app`; o `docker compose up` sozinho só
  sobe o contêiner).

**Alternativas descartadas.** (a) Compose próprio na raiz com outro serviço: dois Postgres, portas em
conflito. (b) Nenhum arquivo na raiz: funciona, mas `docker compose up` na raiz falharia sem explicação.
(c) Raiz como fonte e `db/` incluindo a raiz: inverteria o dono do Postgres.

## 4. Conexão da API (T-0003) — contrato
- A API conecta **só** com o papel `macuxi_app` (`urlApp(lerConfig())` de `@macuxi/db`); dado de tenant só
  dentro de `comTenant(pool, tenantIdDoToken, fn)`. O `tenant_id` vem só do token.
- Login: `plataforma.tenant_por_codigo(codigo)` (SECURITY DEFINER) e depois `lower(email)` no contexto.
- O administrador/migrador nunca é usado pela API.

## 5. Despacho da outbox entre tenants (pg-boss) — PROPOSTA (não implementar ainda)
**Problema.** `plataforma.evento` tem `FORCE ROW LEVEL SECURITY` e a política só para `macuxi_app` com
`tenant_id = plataforma.tenant_atual()`. O despachante precisa achar os pendentes de **todos** os tenants
(`where publicado_em is null order by ocorrido_em`), sem abrir acesso aos dados de negócio.

**Proposta (recomendada): papel dedicado `macuxi_worker`, SEM `BYPASSRLS`, com política própria.**
```sql
-- papel do cluster (criado como NOLOGIN na migração; LOGIN e senha pelo executor, como o macuxi_app)
create role macuxi_worker nologin nosuperuser nobypassrls nocreatedb nocreaterole noreplication;
grant usage on schema plataforma to macuxi_worker;
grant select (id, tenant_id, nome, modulo, agregado_id, payload, ocorrido_em, publicado_em, tentativas)
  on plataforma.evento to macuxi_worker;
grant update (publicado_em, tentativas, ultimo_erro) on plataforma.evento to macuxi_worker;
create policy despacho_outbox on plataforma.evento for select to macuxi_worker using (true);
create policy despacho_outbox_marcar on plataforma.evento for update to macuxi_worker using (true) with check (true);
-- nenhum grant em core.*, nos schemas dos módulos nem nas demais tabelas de plataforma
```
- O despachante lê um lote com `for update skip locked` (vários workers sem duplicar), entrega cada
  envelope ao pg-boss (uma fila por consumidor, `singletonKey = evento_id:consumidor`) e marca
  `publicado_em`; falha incrementa `tentativas`/`ultimo_erro`.
- O **handler** do consumidor nunca usa o papel do worker: abre `comTenant(poolApp, envelope.tenant_id, fn)`
  com `macuxi_app` e o RLS normal vale. Consumo idempotente por `evento_id` (doc 04).
- O processo do worker tem dois pools: `macuxi_worker` (só outbox e schema do pg-boss) e `macuxi_app`.
- pg-boss: schema `pgboss` criado pelo migrador (instalação do pg-boss em migração, `migrate: false` no
  runtime), dono o migrador, `usage` + DML para `macuxi_worker`. Tabelas do pg-boss entram em
  `db/src/excecoes.ts` (sem `tenant_id`, como `public.macuxi_migracao`); o tenant viaja no envelope.

**Por que não as outras.**
| Alternativa | Problema |
|---|---|
| `macuxi_worker` com `BYPASSRLS` | `BYPASSRLS` é atributo do papel, vale para **todas** as tabelas; a restrição dependeria só de grants. A política dedicada dá o mesmo resultado sem o atributo (falha fechada continua para todo o resto) |
| Funções `SECURITY DEFINER` (`evento_reservar_lote`, `evento_marcar`) chamadas pelo `macuxi_app` | Rodam como o dono (superusuário local; papel com `BYPASSRLS` em nuvem gerenciada), exigem `search_path` fixo e dão ao papel da API a capacidade de ler eventos de todos os tenants. Aceitável como plano B se a nuvem não permitir criar papel |
| Worker iterando tenant a tenant com `comTenant` | Zero privilégio novo, mas N consultas por ciclo (cresce com os tenants), latência irregular e sem `skip locked` global |

**Testes que o banco-dados escreveria quando implementar** (ids a definir): `macuxi_worker` lê eventos de A e
B; não lê `core.*` nem `plataforma.usuario_modulo` (erro 42501); só atualiza `publicado_em/tentativas/ultimo_erro`;
não tem `BYPASSRLS`; `macuxi_app` sem contexto continua com 0 linhas em `plataforma.evento`.

**Quando.** Implementa quando o pg-boss entrar (primeiro consumidor real de evento). Antes disso: ADR do
engenheiro aprovando esta proposta e pedido ao banco-dados com a migração.

## 1. Onde mora a aplicação (decisão)
- A aplicação é **conteúdo do Catálogo**, não cadastro base do Core. Ela fica na coluna que já existe,
  `catalogo.produto_conteudo.aplicacoes`, que hoje já é o `applications` do contrato `Product`. Não há coluna nova no Core nem
  contrato novo do Core. O mesmo vale para o que a T-0085 traz: referências, oferece junto e etiquetas.
- **Entrada pelo ERP:** o Catálogo já consome `integracao.produto.atualizado@1`, hoje para o nó da árvore (`consumidores-erp.ts`).
  Ele passa a ler também `aplicacao`. O Core continua lendo só o cadastro base.
- **Entrada pelo BKO:** a seção Catálogo do cadastro do produto (rota na T-0085, §4).
- **Nomes:** a coluna continua `aplicacoes`, para não renomear e quebrar seed e fixtures. Nos contratos novos (pull,
  `/integracao/v1`, push e rotas) o campo se chama `aplicacao`. O provedor faz o mapeamento, como já faz com `applications`.

## 3. `expandirAplicacao` (domain do Catálogo, RN-CAT-12)
Arquivo `modules/catalogo/domain/aplicacao.ts`. É uma função pura, a mesma no aparelho (índice FTS5 e ranking) e na API
(`produto_busca` e ranking).

```ts
export interface FaixaAnos { de: number; ate: number; inicio: number; fim: number } // posições no texto original
export interface AplicacaoExpandida {
  anos: number[];        // anos literais + anos gerados por faixa, crescentes e sem repetir
  faixas: FaixaAnos[];   // só as faixas válidas que foram expandidas
  textoIndice: string;   // texto original + " " + anos gerados que ainda não estão no texto
}
export function expandirAplicacao(texto: string | null | undefined, opcoes: { anoAtual: number }): AplicacaoExpandida;
```

### Regras
1. **O que é ano:** 4 dígitos de 1900 a 2099, como palavra inteira. Não vale com dígito, ponto ou vírgula colado seguido de
   dígito: "1.2012" e "12012" não são anos.
2. **Faixa fechada:** `A sep B`, com `sep` ∈ { `–`, `—`, `-`, ` a `, `/` } e espaços opcionais em volta (menos no ` a `, que exige
   os espaços).
   - Com A < B e B − A ≤ 40, gera A..B.
   - A = B vale como ano único.
3. **Faixa aberta:** `A>`, `A >`, `A em diante` e `a partir de A` vão até `anoAtual + 1`, se `anoAtual + 1 − A` estiver entre 0 e 40.
4. **Fica só como texto** (os anos escritos continuam literais e casam, mas sem anos do meio):
   - faixa invertida;
   - faixa com mais de 40 anos;
   - faixa aberta fora do limite;
   - **cadeia de 3 ou mais anos** ligados por `/`, que é lista e não faixa ("2010/2012/2014").
5. **Nunca vira faixa:** número que não tem 4 dígitos ("1.0/1.4", "1.6"), código com letra ("G5/G6", "16V").
6. **`anoAtual`** é o ano civil no fuso do tenant, pelo relógio injetado e nunca `new Date()` (ADR 0015).
   - O índice guarda os anos calculados na hora de indexar. O "+1" dá a folga da virada de ano, sem reindexar em 1º de janeiro.
   - O aparelho reindexa o produto toda vez que ele muda.
7. **Ano de 2 dígitos** ("10/14"): fora da v1. Quando entrar, entra atrás do parâmetro `aplicacao_ano_2_digitos` (padrão
   desligado). Não se cria parâmetro sem efeito agora.

### Casos de teste (`domain/aplicacao.test.ts`, citando RN-CAT-12; `anoAtual = 2026`)

| Entrada | `anos` | Observação |
|---|---|---|
| `"Fiat Uno 1.0/1.4 2010–2014"` | 2010, 2011, 2012, 2013, 2014 | `textoIndice` termina com `" 2011 2012 2013"` |
| `"VW Gol G5/G6 1.0/1.6 2009–2016"` | 2009..2016 | |
| `"1.0/1.4"` · `"G5/G6"` · `"Gol G5/G6 1.6"` | [] | `faixas` vazia, `textoIndice` igual à entrada |
| `"2010-2014"` · `"2010 - 2014"` · `"2010 a 2014"` · `"2010/2014"` · `"2010—2014"` | 2010..2014 | as cinco formas |
| `"Palio 2012>"` · `"2012 em diante"` · `"a partir de 2012"` | 2012..2027 | |
| `"2014–2010"` | 2010, 2014 | invertida: só texto |
| `"1970–2026"` | 1970, 2026 | mais de 40 anos: só texto |
| `"2010/2012/2014"` | 2010, 2012, 2014 | lista, não faixa |
| `"Uno 2010–2014; Palio 2012–2016"` | 2010..2016 | duas faixas, `faixas.length = 2` |

## 4. Ranking (mudanças em `domain/ranking.ts`)
1. `DocBusca` ganha `aplicacao: string` (texto do cadastro; `''` = sem aplicação). O campo `atributos` continua só com os
   atributos: a aplicação sai de lá e de `conteudo`.
2. **Campo novo:**
   - termos = `tokensDeBusca(expandirAplicacao(doc.aplicacao, {anoAtual}).textoIndice)`;
   - peso = `parametros.peso_aplicacao`.
   - `pontuacaoTextual(grupos, doc, opcoes?)` ganha `{ pesoAplicacao, anoAtual }` opcional, com padrão 0,5 e o ano do relógio
     do chamador.
   - `rankear` passa os valores de `entrada.parametros` e de `entrada.anoAtual`, um campo novo e obrigatório.
3. **Ano da consulta como filtro.** A consulta tem um termo de ano Y (1900–2099) e o documento tem `anos` não vazio. Se Y não está
   em `anos` e também não casa em nenhum outro campo, o documento sai (nota 0). Documento sem ano na aplicação não muda de
   comportamento (critério 4).
4. **Nome antes da aplicação.**
   - `ItemRankeado` ganha `so_aplicacao`: true quando todos os grupos que casaram só casaram no campo aplicação.
   - Na ordenação por relevância, depois de `exato`, quem tem `so_aplicacao = false` vem antes.
   - Com `sort` de preço, o preço manda, como hoje.
5. **Custo.** O ranking roda só sobre os candidatos (≤ 400, pré-selecionados pelo FTS em catálogos grandes). Expandir e tokenizar
   400 × 2.000 caracteres por consulta cabe no p95 < 300 ms.
   - Memória por `produto_id` + `updated_at` no app (`lembrar`), nunca pelo texto inteiro no `MEMO_NORMALIZADO`.
   - Prova: a tela de medição com 20 mil produtos (critério 5).
   - **Revisão do critério 5 (2026-11-06, R-20261106-191335):**
     - no campo aplicação o casamento é só exato e prefixo; a tolerância de digitação fica nos campos curtos (nome, marca,
       categoria, atributos). Vale no app e na API, porque o domain é o mesmo;
     - a memória da análise tem teto medido no teste de desempenho: no máximo 2 × `MAXIMO_CANDIDATOS` entradas, chave curta
       (`produto_id`, `updated_at` e ano) e alvo de até 20 MB de heap. A chave pelo texto, com teto de 3.000, mediu 90 MB;
     - o ano das faixas abertas é o ano civil no fuso do tenant, o mesmo no índice e no ranking;
     - o teste de 20 mil é opt-in só por `MACUXI_DESEMPENHO=1` e roda num job próprio do CI, agendado ou manual, fora do
       `ci-ok`. Nunca roda por `CI=true`.

## 5. Trecho "Serve em" (`domain/aplicacao.ts`)
```ts
export function trechoServeEm(aplicacao: string, grupos: readonly (readonly string[])[], opcoes: { anoAtual: number; max?: number /* 90 */ }): TrechoBusca | null;
```
1. Devolve `null` quando a aplicação é vazia ou quando nenhum grupo da consulta casou no campo aplicação. A régua de casar é a
   mesma de `nivelDaPalavra`.
2. **Segmentos:** o texto é partido por `;`, `|`, `•` e quebra de linha.
   - Vale o segmento com mais grupos casados; no empate, vale o primeiro.
   - Um ano da consulta que cai dentro de uma faixa do segmento conta como casado.
3. **Janela:** segmento com até 90 caracteres sai inteiro, sem espaço sobrando nas pontas. Acima disso:
   - a janela de até 90 caracteres fica em volta da primeira marca e é cortada em palavra inteira;
   - leva `…` na ponta cortada (o `…` conta nos 90).
4. **Marcas:** são as palavras do texto original (com acento) cuja forma normalizada casa com um termo da consulta. A faixa inteira
   ("2010–2014") também é marca quando o ano veio dela.
5. **`inclui_ano`:** o primeiro ano da consulta que só casou por faixa. A tela mostra "Serve em: Fiat Uno 1.0/1.4 **2010–2014** ·
   inclui 2012", e o texto "inclui …" fica fora dos 90.
6. **Testes:**
   - "pastilha uno 2012" sobre "Fiat Uno 1.0/1.4 2010–2014; Palio 1.0 2012–2016" devolve o segmento do Uno, com as marcas em "Uno"
     e "2010–2014" e `inclui_ano = 2012`;
   - "Uno … 2010–2014" literal com "2010" na consulta devolve `inclui_ano = null`;
   - texto de 300 caracteres sem separador sai com ≤ 90 e `…`;
   - consulta que só casa no nome devolve `null`.

## 6. Índices
### Servidor (`catalogo.produto_busca`, banco-dados)
- Coluna nova `aplicacao text`. A API do Catálogo grava nela o `textoIndice` (já expandido).
- O gatilho `produto_busca_documento` passa a montar o documento assim:
  - **A:** sku, ean, nome e `referencias` (T-0085);
  - **B:** marca e categoria;
  - **C:** atributos e **aplicacao**;
  - **D:** conteudo, que deixa de levar a aplicação. Quem grava `conteudo` é o modulo-catalogo, que tira `aplicacoes` da junção.
- **Backfill:**
  - na migração: `aplicacao = produto_conteudo.aplicacoes` (sem expansão, para o SQL não depender do JS);
  - depois, a API do Catálogo reescreve o documento expandido. Pode ser na primeira gravação do produto ou num comando de
    reindexação, `pnpm --filter api catalogo reindexar`, dono modulo-catalogo.
  - Até o reindex, "2012" só casa literal no servidor. O aparelho já sai certo.
### Aparelho (FTS5, migração **v3** em `modules/catalogo/db/aparelho.ts`, banco-dados)
- Coluna de FTS5 não se acrescenta: a v3 recria `catalogo__busca_doc`, `catalogo__busca` e `catalogo__busca_vocab`. As colunas
  ficam, nesta ordem: `sku, ean, codigos, nome, marca, categoria, atributos, aplicacao, referencias` (`referencias` é da T-0085).
- O SDK reindexa sozinho: `marcarReindexacaoSeVazio`, com o índice vazio e as fontes com linhas. Não precisa mudar o SDK.
- Índice de expressão `catalogo__produto_referencia_produto` em `ent_produto_referencia` (T-0085).
- `PESOS_BUSCA_CATALOGO` (`app/indice.ts`, modulo-catalogo): `aplicacao: 2` e `referencias: 8`; os outros ficam como estão.
- **Fontes:** ficam `produto`, `produto_atributo`, `produto_conteudo` e `produto_referencia`.
  - Para `produto_conteudo` e `produto_referencia`, o `chaveDe` é `linha.produto_id`.
  - O `documento()` grava `aplicacao = textoIndice`, `referencias` com os códigos crus e `codigos` com o SKU, o `external_id` e
    as referências em `codigoCompacto`.
- **Primeira abertura depois da atualização:** reindexa 20 mil documentos em lotes, cedendo o loop. O engenheiro-apps confere o
  tempo na tela de medição.

## 7. Orçamento e pedido (RN-VEN-19, domain do Vendedor)
`modules/vendedor/domain/aplicacao.ts`:
```ts
/** RN-VEN-19: null se desmarcado ou vazio; senão corta em `max` na última palavra inteira com "…" (o "…" conta). */
export function retratoAplicacao(texto: string | null | undefined, incluir: boolean, max: number): string | null;
```
**Testes:**
- texto ≤ 300 fica igual;
- texto de 301 a 2.000 dá ≤ 300 caracteres, terminando em palavra inteira + `…`;
- palavra única maior que `max` é cortada em `max − 1` + `…`;
- desmarcado dá `null`;
- espaços e quebras nas pontas saem;
- é idempotente: `retrato(retrato(x)) = retrato(x)`.

### Aparelho
- **Lista do seletor:** a busca chama `catalogo.busca_produtos@1` (C9) com os ids do seletor. A lista mostra a aplicação em 2
  linhas, com as marcas do `serve_em`. Sem trecho, mostra o começo da aplicação.
- **Plano B:** se a consulta der `ConsultaIndisponivel`, vale o `searchProducts` atual.
- **Caixa por item:** "Incluir aplicação no orçamento" aparece no item quando o produto tem aplicação. Vem marcada pelo
  `aplicacao_no_orcamento_padrao` e é por item, **não** a chave única do quadro 6b.
- **Retrato:**
  - Tirado ao salvar ou enviar o documento (pedido ou orçamento), a partir da aplicação local (C8): `retratoAplicacao(texto,
    marcado, aplicacao_max_orcamento)`.
  - Na edição de um orçamento, o item que já tem retrato fica com ele. O retrato só muda se o vendedor desmarcar e marcar de novo
    (aí pega o texto atual).
- **Duplicar** tira um retrato novo.

### API (`receber` e `PUT` do orçamento)
- Item com `aplicacao` nula ou ausente grava `null`.
- Texto recebido grava `retratoAplicacao(texto, true, aplicacao_max_orcamento do tenant)`. A API revalida: corta de novo se o
  parâmetro baixou e nunca recusa por tamanho, porque o pedido offline foi feito com o parâmetro que o aparelho tinha.
- A API **não** troca o texto pelo cadastro atual. O retrato é o que o cliente viu no orçamento.
- `pedido_item.aplicacao` (banco-dados): `text null`, `check (char_length(aplicacao) <= 1000)`.

### Saídas
- **Onde aparece "Aplicação: …":** abaixo da descrição do item no detalhe (Campo, Gestão e BKO, pelo C11) e nos dois PDFs
  (`domain/pdf-pedido.ts`).
- **Pedido ao ERP:** leva o campo pelo C13 e pelo C14.
- **Promotor:** nunca vê o pedido (RN-PRO-01). Vê a aplicação só na ficha do Catálogo, em leitura.

- **Item do pedido:** as 2 linhas da aplicação e a caixa "Incluir aplicação no orçamento", por item. O 6b mostra uma chave única
  na folha do PDF; **vale a caixa por item**.
- **Detalhe e PDFs:** "Aplicação: …" abaixo da descrição do item. No PDF, o texto já vem cortado em 300.
- **Ficha:** seção Aplicação com o texto inteiro ("ver mais" acima de 6 linhas).
- **BKO:** campo Aplicação na seção Catálogo (T-0085), com contador "1.234 / 2.000".

## 12. Riscos e premissas
- **Retrato vem do aparelho.** A API corta e revalida o tamanho, mas não confere o texto com o cadastro. O motivo: o retrato é o que
  o cliente viu no orçamento. O risco de texto forjado é baixo: só afeta o próprio pedido e o log não leva o texto.
- **Servidor antes do reindex:** até o comando rodar, o ano dentro de faixa só funciona offline (§6).
- **Memória do Vendedor:** o seletor não carrega 20 mil aplicações. Ele busca pela C9 e lê a C8 só dos itens visíveis, até 500 ids.

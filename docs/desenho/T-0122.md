## Diff 1 — `T-0122-guardiao.diff` (guardião v7)

### 1.a `gh api` só de leitura (`guarda-merge-lib.mjs` + `guarda-bash.mjs`)

**Problema**: o v5/v6 bloqueava todo `gh api` que tivesse `$VAR` ou a palavra "merge" em qualquer argumento, para pegar o
merge pela API (`PUT .../pulls/N/merge`, `mergePullRequest`). Isso barrava leituras comuns
(`gh api repos/aloirr/macuxifdv/pulls/$PR --jq .merged`, `--jq '.[] | select(.merged_at)'`, `GET .../pulls/N/merge`). E a
escrita pela API sem a palavra "merge" (`PUT .../contents/.claude/settings.json`, `DELETE .../git/refs/heads/x`, `POST
.../issues`) passava.

**O que muda**:

- `analisarGhApi(args)` (nova, pura) classifica um `gh api` pelos argumentos, com as regras do próprio gh 2.x:
  - método explícito (`-X`/`--method`, também `-XGET` e `--method=GET`; vale o último) ou implícito: **GET** sem
    `-f/-F/--input`, **POST** com eles;
  - **leitura** = GET ou HEAD; GraphQL (`graphql`) só com um `-f query=...` literal que começa com `query` ou `{`, sem
    `mutation`/`subscription`;
  - **escrita** = POST/PUT/PATCH/DELETE; método incerto (`-X $M`); opção que o guardião não conhece; 2º posicional;
    consulta GraphQL de arquivo (`-F query=@x`) ou de `$VAR`; `mutation` em qualquer campo quando o endpoint é `graphql` ou
    incerto (mesmo com `-X GET`).
- `acharMerges` (v5): o ramo do `gh api` só acusa "merge pela API" quando o pedido **não** é leitura. Leitura com `$VAR` ou
  "merge" deixa de ser "merge escondido". A escrita de merge continua com a mensagem do merge (`BLOQUEADO (gh pr merge)`).
- `conferirGhApi(comando)` (nova): acha cada `gh api` do comando (também depois de `; && || |`, em `$(...)` e com
  `-R x` antes do grupo) e bloqueia o que não é leitura, com a mensagem `[guardião Macuxi] BLOQUEADO (gh api)`. `gh api`
  escondido em `bash -c`, `eval`, `xargs`, here-doc ou `node -e` (o texto cita mais `gh api` do que os visíveis) também é
  bloqueado.
- `guarda-bash.mjs`: chama `conferirGhApi` logo depois da trava do merge, **para toda sessão** (inclusive a manual e a do
  Alexandre, como a trava do merge). Uso manual sem trava: `MACUXI_GUARDA=off`, como hoje.

### 1.b Ferramentas MCP (`guarda-mcp.mjs` + `guarda-mcp-lib.mjs` + `settings.json`)

**Problema**: o Edit/Write passa pelo `guarda-donos`, o Bash pelo `guarda-bash` e o merge pelo MCP pelo
`guarda-merge-mcp` (v6), mas `push_files`, `create_or_update_file` e `delete_file` do MCP do GitHub (e qualquer servidor
MCP de arquivos) gravavam sem passar por guardião. Só o CI da T-0049 pegava depois, e só governança no `main`.

**O que muda**: hook novo no PreToolUse com matcher `mcp__.*` (`node .claude/hooks/guarda-mcp.mjs`). O hook do merge
(`guarda-merge-mcp.mjs`, matcher das ferramentas com "merge") continua igual; nas ferramentas de merge o hook novo passa
direto e quem decide é o v6.

Classes (`classificarFerramentaMcp`, pura):

| Classe | Exemplos | Regra |
|---|---|---|
| `leitura` | `get_*`, `list_*`, `search_*`, `*_read`, `actions_list`, `read_file` | passa |
| `merge` | `merge_pull_request`, `enable_pr_auto_merge` | passa aqui; decide o `guarda-merge-mcp` (v6) |
| `github-arquivo` | `push_files`, `create_or_update_file`, `delete_file` | regras a–d abaixo |
| `github-escrita` | `create_pull_request`, `update_pull_request`, `update_pull_request_branch`, revisão, comentário, issue, `create_branch` | só no `aloirr/macuxifdv` quando o repositório vem na chamada; `create_branch` de `main` não |
| `github-proibida` | `delete_branch`, `create_repository`, `fork_repository`, `run_workflow`, `actions_run_trigger`, `create_release`, `update_ref`, segredos, **nome desconhecido** | BLOQUEADO (falha fechada; é com o Alexandre) |
| `arquivo-local` | outro servidor com verbo de escrita (`write_file`, `edit_file`, `move_file`...) e caminho na entrada | cada caminho dentro do repositório passa pelo `podeAlterar` (as regras do `guarda-donos`); fora dele, só as pastas `somente_leitura` do `donos.json` bloqueiam |
| `outro` | Canva, documentos, `subscribe_pr_activity` | passa |

Regras do `github-arquivo`:

- a) só no `aloirr/macuxifdv` e com **branch explícito diferente de `main`** (sem branch o GitHub grava no padrão): nada vai
  direto ao `main` pelo MCP — vale para toda sessão;
- b) caminho relativo limpo (sem `..`, `.`, `//`, `\` nem absoluto); arquivo em `CAMINHOS_DE_GOVERNANCA` (`.claude/**`,
  `.coord/donos.json`, `scripts/coord*.mjs`, `.github/**`) só pelo Alexandre (`MACUXI_AGENTE=alexandre`) ou sessão manual
  local, e sempre com `Agente: alexandre` no último bloco da mensagem. Agente nunca, nem o dono do `.github/**`: entrega em
  diff, como esta tarefa;
- c) agente do time: cada arquivo passa pelo `podeAlterar` da `coord-lib` (dono do `donos.json`; recado só novo, com o
  próprio nome e o próprio `de:`; diário e lidos só do próprio agente) e a mensagem tem **exatamente um**
  `Agente: <o próprio agente>` no último bloco (o `verificar --por-commit` do CI depende dele). Atualização (`sha` presente)
  conta como Edit e apagar como Delete, então recado existente é imutável também pelo MCP. Subagente fora do time
  (`general-purpose`, sem `agent_type`) e sessão da nuvem sem agente = bloqueado;
- d) sessão manual local (sem agente): só a) e b), como no `guarda-donos`.

Falha fechada: leitura e outro servidor passam **antes** de ler qualquer coisa (um `donos.json` quebrado não trava a
leitura); nas demais classes, entrada ilegível ou erro do hook = BLOQUEADO (exit 2). Sem rede: o hook não consulta o
GitHub. `MACUXI_GUARDA=off` desliga, como nos outros.

### 1.d O que fica mais forte e o que fica mais fraco (para o rito de governança)

- **Mais forte**: `push_files`/`create_or_update_file`/`delete_file` do MCP passam a seguir os donos, nunca vão ao `main` e
  nunca tocam governança por agente; escritas do MCP do GitHub fora da lista aceita são barradas; `gh api` que grava
  (qualquer método ≠ GET/HEAD, GraphQL `mutation`) é barrado para toda sessão, não só o de merge.
- **Mais fraco (de propósito)**: `gh api` de **leitura** com `$VAR` ou "merge" passa (era o falso positivo do backlog). Não
  abre merge: GET/HEAD não gravam, e GraphQL `mutation` continua barrado com qualquer método e endpoint incerto.
- **Pode incomodar**: (1) ferramenta nova do MCP do GitHub cai em `github-proibida` até entrar na lista
  `GITHUB_ESCRITA_ACEITA` (ou ser reconhecida como leitura) — é a falha fechada; (2) quem usava `gh api -X POST` para
  comentar/editar passa a usar `gh pr comment`/`gh pr edit`/`gh issue ...`; (3) na nuvem, o subagente que segura as
  ferramentas do GitHub só grava arquivo pelo MCP se for um agente do time — o caminho normal continua `git push` do branch
  `nuvem/*` (e criar/atualizar o PR pelo MCP continua liberado).

### 1.e Limites conhecidos (não bloqueiam o merge do diff)

- Recado "existente" é conferido no disco local (como no `guarda-donos`): um recado que só existe no branch remoto e não no
  checkout local não é reconhecido como existente pelo MCP. O CI (`verificar` e `brechas-governanca recados`) continua
  pegando alteração de recado no PR.
- Servidor MCP de arquivos com nome de ferramenta sem verbo de escrita, ou com o caminho numa chave fora de
  `path/file_path/source/destination/paths/files/edits...`, passa como `outro`. Hoje o time não usa servidor de arquivos.

## 1. Premissas do gerente — confirmadas
| Premissa | Decisão |
|---|---|
| Árvore em `catalogo` (`catalogo_no`, `produto_no`) | **Confirmada.** É navegação de catálogo (RF-CAT-04); o Core não precisa dela |
| `produto_unidade` e `cliente_endereco` em `core` | **Confirmada.** Cadastro base (ADR 0005); o Vendedor lê pela consulta do Core (§4.3), nunca pela tabela |
| `transportadora` em `vendedor` | **Confirmada.** Só o pedido usa; o BKO de transportadoras é do Vendedor. `cliente_frete` **sai** (rev. 2): o padrão é só o do tenant (RN-VEN-16) |
| Medidas (RN-CORE-19) em `core` (rev. 2) | `core.medida` (sigla + descrição por tenant). **Medida da unidade = `core.produto.unidade`** (coluna que já existe) e **embalagem = `core.produto_unidade` com `fator` > 1** (0013). Não criamos `medida_unidade`/`embalagem_medida`/`embalagem_qtd` no produto: seriam cópia de `produto_unidade`. O BKO edita uma embalagem por produto; o ERP pode mandar mais de uma |
| Custo, preço de venda e desconto máximo (RN-CORE-18, RN-VEN-11) em `core.produto` (rev. 2) | Colunas da 0013 (`custo_cents`, `preco_venda_cents`, `desconto_maximo_pct`). Parâmetro do padrão no **Core**: `produto.desconto_maximo_pct` (doc 03 `desconto_maximo_produto_pct`, 15) |
| RN-VEN-11 (preço mínimo) por item | Confirmada; `pedido_item.preco_minimo_cents` (0013) é o retrato |

## 2. Três regras de modelagem (valem para todos os contratos abaixo)
1. **Quantidade fora do Vendedor é sempre na UNIDADE BASE.** O Vendedor guarda a quantidade na unidade vendida + `fator` +
   `quantidade_base` (0013). Em tudo que sai dele — evento `vendedor.pedido.aprovado@1`, `PedidoParaErp`, `ItemFaturado` do
   retorno, metas — `quantidade` = unidade base, e a unidade vendida vai em campos novos (`unidade`, `fator`,
   `quantidade_venda`). Assim o Conector 1.2.x, que não conhece unidade, grava no ERP uma quantidade **certa** (ADR 0016).
   Consequência no banco: `pedido_item.quantidade_faturada` deve ser **na unidade base** (o ERP fatura 6 UN de uma "CX c/ 12"):
   check `quantidade_faturada between 0 and quantidade_base` (pedido ao banco-dados, §6).
2. **Percentuais seguem como hoje** (`Pct`, número 0–100 com 2 casas, `numeric(5,2)`).
   Dinheiro sempre em centavos inteiros; arredondamento meia para cima **por item** (RN-VEN-02), na unidade vendida.
3. **Desconto OU acréscimo**, nunca os dois, no item e no pedido (check do banco + `superRefine` no contrato + domain).

## 3. Preço (domain do Vendedor, T-0053) — assinatura combinada
```ts

  preco_proprio_unidade_cents?: number | null; desconto_pct: number; acrescimo_pct: number;
  preco_minimo_base_cents?: number | null }                  // RN-VEN-11, por unidade base (null = sem trava)

  quantidade_base: number; preco_minimo_cents: number | null } // preço da CX = UN × fator, salvo preço próprio (RN-VEN-15);
                                                             // preco_minimo_cents = mínimo base × fator (na medida vendida)

  { total_tabela_cents; total_itens_cents; desconto_cents; acrescimo_cents; total_cents; desconto_efetivo_pct }
                                                             // RN-VEN-03; negativo = acréscimo. Frete não tem valor (RN-VEN-16)
export function nivelDeAprovacao(desconto_efetivo_pct, alcadas): NivelAprovacao | null   // RN-VEN-10: só o efetivo; ≤ 0 nunca

// RN-VEN-11 (rev. 2). Arredondamento meia para cima em centavos; null = produto sem preço de venda (não vendável, RN-CORE-18)
export function precoMinimoBaseCents(p: { preco_venda_cents: number | null; desconto_maximo_pct: number }): number | null
// "Desconto máximo deste produto: X%" = maior desconto do item que não fura o mínimo, 2 casas, truncado; 0 se a tabela já
// está abaixo do mínimo. O app trava o campo nesse X; a API recusa acima dele (`preco_abaixo_minimo`)
export function descontoMaximoDoItemPct(preco_tabela_cents: number, preco_minimo_cents: number | null): number | null
// RN-VEN-16: CIF sem transportadora; FOB com cadastrada XOR digitada (nome ≥ 2, CNPJ válido de @macuxi/comum/documento)
export function validarFrete(f: FretePedido): CodigoRecusaPedido | null   // 'transportadora_obrigatoria' | 'transportadora_invalida'
// PDF e detalhe (RN-CORE-19): fator 1 → "UN"; fator > 1 → "CX c/ 12"
export function rotuloMedida(unidade: string, fator: number): string
```
`total_cents` do pedido é o valor do pedido (base da alçada e da meta, RN-CORE-21). **Não há** `frete_cents` nem
`total_a_pagar_cents` (rev. 2: o cliente paga o frete FOB direto à transportadora; no CIF o frete está no preço).
Desconto máximo efetivo do produto = `produto.desconto_maximo_pct` próprio ?? parâmetro do Core `produto.desconto_maximo_pct`
?? 15. Na API ele chega pronto em `core.cadastro_resumo@1` (§4.1); no aparelho o Vendedor resolve com
`ambiente.parametros('core')['produto.desconto_maximo_pct']`.

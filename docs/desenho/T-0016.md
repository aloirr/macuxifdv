  (o Promotor usa `permanencia_s` na RN-PRO-07; o Gestor nos painéis). Publicados com `tx.publicar` na transação do push. Sem consumidor
  rodando até o despachante existir (ficam na outbox — é o comportamento esperado).

### 4.3 Push (receber) — regras do servidor (a API sempre revalida)
**`visita` (check-in)**, numa transação por item:
1. `insert … on conflict (id) do nothing`; se já existe: mesmo usuário e cliente → `aceito` (reenvio); senão → `rejeitado/ID_EM_USO`.
2. Cliente fora do escopo → `rejeitado/FORA_DA_CARTEIRA`. Promotor e vendedor: só a própria carteira (RN-CORE-04).
3. `avaliarCheckin` com a coordenada do cliente no banco: fora do raio sem justificativa → `rejeitado/RN-CORE-10` (o app já exige; só
   acontece com app adulterado). Grava `distancia_m`, `fora_do_raio`, `sugere_coordenada`, `data_local` (fuso do tenant).
4. `resolverCheckin`: fecha a aberta anterior como `auto` (`nao_finalizado`); o índice único parcial "uma aberta por usuário" é a trava
   final (RN-CORE-11).
5. `tx.publicar(core.visita.checkin@1)`.

**`visita_checkout`**:
1. Visita inexistente ou de outro usuário → `rejeitado/VISITA_NAO_ENCONTRADA` (mesmo texto para os dois casos).
2. `visita.checkout_id = id do item` → `aceito` (reenvio). Fechada por outro checkout do usuário → `conflito` (com a linha atual).
   Fechada `auto` pelo servidor → o checkout do usuário **vence** (é o fato real) e substitui.
3. `avaliarCheckout` com os módulos efetivos do usuário (`ctx.usuario` traz os efetivos): `sem_pedido` sem motivo com Vendedor efetivo →
   `rejeitado/RN-CORE-12`; `cliente_fechado` sem foto/motivo do tipo `cliente_fechado` → `rejeitado/RN-CORE-14`.
4. Grava `visita_etapa` (uma por etapa do payload, `unique (visita_id, modulo, etapa)`), `tx.registrarArquivo` da foto
   (`finalidade: 'fachada'`, `cliente_id`), e `tx.publicar(core.visita.checkout@1)`.
- **Etapas obrigatórias de outros módulos no servidor**: na Sprint 1 nenhum módulo tem etapa com estado no servidor (Pesquisa e Promotor
  ainda sem API), então o servidor confere só o que é do Core (motivo, cliente fechado). Fica planejado o slot de servidor
  `visita.etapas_checkout` (cada módulo verifica a própria etapa por contrato) — entra com a primeira etapa real (Pesquisa/Promotor).

## 11. Riscos e premissas
| Risco | Mitigação |
|---|---|
| Offline: o vendedor fecha visita offline e o servidor fechou "auto" antes | checkout do usuário vence o `auto` (§4.3); sobreposição da fila na tela (ADR 0009 §3) |
| Idempotência: lote reenviado depois de timeout | check-in por `visita.id`; checkout por `checkout_id`; leitura por `coalesce`; envio do BKO por `envio_id`; arquivo por `sha256` |
| Cursor do pull × escopo que muda | `versao_escopo` + ressincronização da entidade (ADR 0009 §4); horizonte seguro continua (ADR 0006) |
| Volume da Gestão (supervisor com muitas carteiras) | janelas do §2; se a equipe passar de ~5 mil clientes, títulos/histórico da Gestão viram só online (decisão na medição da T-0008) |
| Fotos: upload falha ou chega antes do push | fila de arquivos separada, depois do push, 409 retentável (ADR 0010); arquivo local mantido 7 dias |
| Fotos: armazenamento em disco não escala / sem backup próprio | porta `ArmazenamentoArquivos`; S3 com ADR quando houver nuvem |
| Push notifications dependem do build EAS (`expo-notifications`, `expo-sqlite` são nativos) | caixa de notificações funciona por sync sem push; E5/P4/P7 entram quando o Alexandre gerar os APKs |
| Sem despachante, eventos ficam só na outbox | esperado; notificação por evento e realizado de venda ficam para a tarefa do despachante |
| Pedido feito offline não sobe até a Sprint 4 | fica `pendente` com mensagem clara (não "falhou"); modo demo continua aceitando |
| T-0015 e E1–E3 nos mesmos arquivos (`apps/api/src/sync.ts`, `api.ts`, `motor-sync.ts`) | E1–E3 só depois do merge da T-0015 |
| Etapas obrigatórias de outros módulos não revalidadas no servidor nesta sprint | nenhum módulo tem etapa com estado no servidor ainda; slot de servidor planejado (§4.3) |
| Relógio do aparelho errado (check-in "ontem") | `recebido_em` do servidor guardado; `data_local` vem do `checkin_em` do aparelho (fato de campo); diferença > 24 h sinalizada ao BKO numa próxima tarefa |

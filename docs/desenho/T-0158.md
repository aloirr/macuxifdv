# Desenho T-0158 — Diagnóstico na nuvem: "Enviar diagnóstico", queda automática, Portal › Diagnósticos e recado automático

- **Autor**: engenheiro-software · **Data**: 2026-11-10 · **Tarefa**: T-0158
- **Origem**: R-20261110-101345-alexandre. O remetente de sistema `diagnostico` foi aprovado em R-20261110-112315-alexandre.
- **ADR**: [0043](../decisoes/0043-diagnostico-do-aparelho-na-plataforma.md). Ela complementa a ADR 0010 (arquivos), a 0029 (super-admin), a 0039 (recados) e a 0042 (`macuxi-saida`).
- **Entregas**:
  - **v1.0.4 (quarta):** botão "Enviar diagnóstico" com protocolo, fila offline, Portal › Diagnósticos (lista e detalhe) e recado automático do envio pelo botão;
  - **v1.0.5:** envio automático da queda na abertura seguinte, com recado.
- **Fora:** Sentry e Crashlytics (avaliar depois do piloto) e Telegram (está no backlog).

## Resumo da decisão
1. **Uma rota da plataforma**, `POST /v1/diagnosticos`, autenticada pela sessão do app, sem licença de módulo, para qualquer perfil e app. Escrita idempotente pelo UUID do aparelho.
2. **Uma tabela `plataforma.diagnostico`**, com RLS por tenant. Guarda só dado técnico: tenant e usuário só por id, e o texto livre passa pela máscara de dado pessoal no servidor.
3. **O print vai pela fila de arquivos da ADR 0010**, sem caminho novo:
   - na mesma transação, a linha `aguardando` em `plataforma.arquivo`, com `modulo = 'plataforma'` e `finalidade = 'print_diagnostico'`;
   - os bytes sobem pelo `PUT /v1/arquivos/:id`;
   - ninguém do tenant lê o print, só o portal.
4. **Leitura só no portal** (`config.macuxifdv.com.br`), só para o **super-admin**:
   - pelas funções `SECURITY DEFINER` `plataforma.sa_*`, no pool `macuxi_portal` da T-0091;
   - "o time" = cada pessoa do time com conta própria de super-admin (ADR 0029);
   - o admin do cliente recebe 403.
5. **Recado automático gravado pelo SERVIDOR (worker):**
   - remetente de sistema `diagnostico`, com token fine-grained só do servidor (nunca no app nem no repositório de código);
   - commit atômico no `aloirr/macuxifdv-recados` como o `coord` (ADR 0039);
   - o recado leva só o protocolo e os dados técnicos curtos, mais o link do portal. Nunca leva o texto livre nem a pilha, porque o repositório de recados é imutável e lá não há expurgo.
6. **Expurgo de 90 dias** feito pelo worker, apagando de fato a linha, o arquivo e os bytes.

## 1. Fluxo
```
Aparelho (Perfil › Diagnóstico)                 API (macuxi_app)                       Worker (macuxi_worker)             GitHub
 "O que aconteceu?" + print opcional
 id = UUID do aparelho ──fila──► POST /v1/diagnosticos ──► insert plataforma.diagnostico
                                  (sessão, Zod, máscara)    + plataforma.arquivo 'aguardando' (se print)
            ◄── { protocolo: 42 } ┘                          alerta = 'pendente'
 "Enviado · nº 0042"
 print ──fila de arquivos──► PUT /v1/arquivos/:id                                   ciclo de 60 s: pendentes ──► createCommitOnBranch
                                                                                     (skip locked, limite)        recados/alexandre/R-...-diagnostico.md
                                                                                     alerta = 'enviado'            recados/engenheiro-apps/R-...-diagnostico.md
Portal › Diagnósticos (super-admin) ──► GET /v1/plataforma/diagnosticos[/:id[/print]] ──► sa_listar_diagnosticos / sa_diagnostico (macuxi_portal)
                                                                                     diário: expurgo > 90 dias (linha + arquivo + bytes)
```

## 2. Contrato (SDK, `packages/platform-sdk/src/diagnostico.ts`; engenheiro-software)
A rota é da plataforma, então o contrato fica no SDK e é exportado para os shells. Todas as datas vêm em UTC (ISO).

`DiagnosticoEnvioSchema` (Zod `.strict()`, corpo de no máximo **32 KB**):

| Campo | Tipo | Observação |
|---|---|---|
| `id` | uuid | Gerado no aparelho. Repetir = mesmo protocolo. |
| `origem` | `'botao' \| 'queda' \| 'erro_tela'` | `botao` = v1.0.4. `queda` (saída do processo, `macuxi-saida`) e `erro_tela` (tela de erro ou erro fatal JS) = v1.0.5. |
| `ocorrido_em` | datetime | Para `botao`, o toque no botão; para queda, o `quando` da saída. |
| `app` | `'campo' \| 'gestao'` | |
| `versao_app` | string 1..20 | Ex.: `1.0.4`. |
| `build` | string 0..60, nulo | `runtimeVersion` ou `nativeBuildVersion`. |
| `aparelho` | `{ fabricante ≤60, modelo ≤80, android ≤20, api ≤ int }` | Só o modelo, nunca IMEI, número de série ou nome do aparelho. |
| `tela` | string ≤200, nulo | Rota do expo-router (`/m/novo-pedido`). Ids na rota são UUID e não são dado pessoal. |
| `motivo` | string ≤60, nulo | `queda`: nome do `REASON_*` (`crash_nativo`, `anr`, `memoria`, `encerrado`...), traduzido pelo `saida-android.ts`. `erro_tela`: a `OrigemDoErro`. `botao`: nulo. |
| `descricao` | string ≤1000, nulo | O "O que aconteceu?". A tela avisa: "Não escreva nome de cliente, telefone ou valores". |
| `erro` | `{ mensagem ≤300, pilha ≤2000 nulo, origem }`, nulo | O "Último erro do app" (`ErroRegistrado`), já mascarado no aparelho. |
| `saida_android` | `{ motivo int, status int, importancia int, pss_kb, rss_kb, descricao ≤300, pilha ≤4000 nulo }`, nulo | A `SaidaAndroid` da T-0144. |
| `sync` | `{ pendentes int ≥0, ultimo_sync_em datetime nulo }`, nulo | Ajuda a diagnosticar "pedido não subiu", sem conteúdo. |
| `print_id` | uuid, nulo | UUID do aparelho para o arquivo do print. |

- **Resposta 201/200:** `DiagnosticoRespostaSchema = { id, protocolo: int, criado: boolean }`. O 201 vem na 1ª vez e o 200 na repetição.
- **Formatação:** `formatarProtocolo(42) = '0042'`, com `padStart(4, '0')`, sem cortar acima de 9999. A função é única no SDK e é usada pelo app e pelo portal.
- **De onde vêm tenant e usuário:** sempre do token, nunca do corpo. O corpo que trouxer `tenant_id`, `usuario_id`, e-mail ou nome é recusado pelo `.strict()`.

**Leitura no portal** (`DiagnosticoListaSchema` e `DiagnosticoDetalheSchema`, também no SDK):
- **Lista:** `{ itens: [{ id, protocolo, recebido_em, ocorrido_em, origem, app, versao_app, aparelho_modelo, android, motivo, tenant_id, tenant_nome, tem_print }], cursor }`;
- **Detalhe:** soma `descricao`, `erro`, `saida_android`, `sync`, `tela`, `build`, `usuario_id`, `perfil` e `alerta` (situação e id do recado);
- **Filtros (query):** `versao`, `modelo`, `tenant_id`, `motivo`, `origem`, `de`, `ate` e `cursor`, 50 por página, do mais novo para o mais antigo.

## 3. API (`apps/api`, engenheiro-software)
| Rota | Quem | O que faz |
|---|---|---|
| `POST /v1/diagnosticos` | Qualquer usuário com sessão do app (`campo` ou `gestao`), qualquer perfil, sem licença de módulo nem carteira. | Valida pelo Zod e passa `descricao`, `erro.*` e `saida_android.descricao/pilha` pela máscara única `mascararDadoPessoal` (`@macuxi/comum/dado-pessoal`; a API sempre revalida). No `comTenant`: `insert ... on conflict (id) do nothing`. Se o `id` já existe no mesmo tenant e é do mesmo usuário, devolve o protocolo dele (200). Se é de outro usuário, ou de outro tenant (invisível pelo RLS), dá 409 `DIAGNOSTICO_JA_EXISTE`. Com `print_id`, cria a linha `aguardando` em `plataforma.arquivo` na MESMA transação. Limite de **20 por usuário por hora** (`criarLimitador`), acima disso 429 `DIAGNOSTICO_LIMITE`. O log só leva `tenant_id`, `request_id`, `origem`, `versao_app` e `protocolo`; nunca a descrição nem a pilha. |
| `PUT /v1/arquivos/:id` (ajuste) | O próprio remetente. | Para `modulo = 'plataforma'` e `finalidade = 'print_diagnostico'`, a checagem de licença de módulo não vale, porque a plataforma não é módulo. O resto da ADR 0010 continua igual (JPEG, tamanho, sha256, mesmo usuário). |
| `GET /v1/arquivos/:id` (ajuste) | — | Arquivo com `modulo = 'plataforma'` dá **404** para qualquer usuário de tenant: o print não aparece no BKO do cliente. |
| `GET /v1/plataforma/diagnosticos` | Portal, só `ator_tipo = 'super_admin'` (o admin do cliente recebe 403). | `sa_listar_diagnosticos(sid, filtro jsonb)`, conferida pelo `DiagnosticoListaSchema`, com auditoria de plataforma como as outras rotas do portal. |
| `GET /v1/plataforma/diagnosticos/:id` | Idem. | `sa_diagnostico(sid, id)`. |
| `GET /v1/plataforma/diagnosticos/:id/print` | Idem. | `sa_diagnostico` devolve a `chave_armazenamento`, e a API lê os bytes pela porta `ArmazenamentoArquivos`, com `cache-control: private, no-store`. Sem URL pré-assinada (ADR 0041 §4). |

**Worker** (`apps/api/src/diagnosticos.ts`, no mesmo processo do despachante, papel `macuxi_worker`):
- **Alerta, a cada 60 s:**
  - pega até 10 linhas com `alerta_situacao = 'pendente'` usando `for update skip locked`;
  - por linha, faz UM commit no repositório de recados com dois arquivos: `recados/alexandre/<id>.md` e `recados/engenheiro-apps/<id>.md`;
  - em seguida grava `alerta_situacao = 'enviado'`, `alerta_recado_id` e `alerta_em`;
  - quando falha, faz `alerta_tentativas + 1` com espera exponencial (1, 2, 4... até 60 min). Na 8ª falha, passa a `falhou` e grava log `warn` (o portal mostra).
- **Contra enxurrada:**
  - **no máximo 12 recados por hora** no total. Passou disso, as linhas viram `agrupado`, e um recado de resumo por hora diz "mais N diagnósticos desde HH:MM", com o link da lista filtrada;
  - **queda repetida:** mesma `versao_app`, mesmo `motivo` e mesmo `aparelho_modelo` em menos de 6 h vira `agrupado`, sem recado novo (o próximo resumo conta).
  - O botão sempre gera recado, dentro do teto de 12 por hora.
- **Sem token (`MACUXI_RECADOS_TOKEN_SERVIDOR` ausente):** `alerta_situacao = 'desligado'`, sem nova tentativa e com um único `warn` por processo. Assim a demo sem o segredo não fica tentando.
- **Expurgo, diário às 07:00 UTC (03:00 em Manaus):**
  - apaga de fato, em lotes de 500, os diagnósticos com `recebido_em` de mais de 90 dias;
  - na mesma transação, apaga as linhas de `plataforma.arquivo` do print;
  - depois do commit, faz o `armazenamento.remover(chave)` (falha de remoção vira `warn` e o próximo ciclo tenta de novo pela chave órfã listada).
  - Também apaga os `aguardando` de print com mais de 7 dias.

**Formato do recado** (o mesmo front matter do `coord`, ADR 0039; id `R-<aaaammdd-hhmmss>-diagnostico`, hora de Manaus como o `coord`):

## O que preciso / o que mudou

## Pronto quando
Informativo (gerado pelo servidor).

- **Cliente HTTP:** `apps/api/src/recados-github.ts`, com o `fetch` nativo e a GraphQL `createCommitOnBranch` com `expectedHeadOid`. Tenta de novo até 6 vezes se o `main` mudar, como o `coord`. Não tem dependência nova.

## 4. Banco (pedido ao banco-dados)
**`plataforma.diagnostico`** (colunas comuns da regra 5; `external_id` sempre nulo):

| Grupo | Colunas |
|---|---|
| Identificação | `protocolo bigint not null unique default nextval('plataforma.diagnostico_protocolo_seq')` (global, começa em 1) · `usuario_id uuid not null` · `perfil text not null` |
| Origem e aparelho | `origem text check in ('botao','queda','erro_tela')` · `app text check in ('campo','gestao')` · `versao_app text not null` · `build text` · `aparelho_fabricante text` · `aparelho_modelo text` · `android text` · `android_api int` · `tela text` · `motivo text` |
| Conteúdo | `descricao text` · `detalhe jsonb not null default '{}'` (`erro`, `saida_android`, `sync`) · `print_id uuid` |
| Datas | `ocorrido_em timestamptz not null` · `recebido_em timestamptz not null default now()` |
| Alerta | `alerta_situacao text not null default 'pendente' check in ('pendente','enviado','agrupado','falhou','desligado')` · `alerta_tentativas int not null default 0` · `alerta_proxima_em timestamptz` · `alerta_recado_id text` · `alerta_em timestamptz` |

- **Índices:** `(recebido_em desc, id)`, `(tenant_id, recebido_em desc)`, `(versao_app)`, `(aparelho_modelo)`, `(motivo)` e um parcial `(alerta_proxima_em) where alerta_situacao = 'pendente'`.
- **RLS (forçado):**
  - `macuxi_app`: `insert` e `select` só no próprio tenant (o `select` serve à repetição idempotente), sem `update` nem `delete`;
  - `macuxi_worker`: `select` e `update` (só as colunas `alerta_*` por grant de coluna) e `delete` em todos os tenants, como o despachante;
  - `macuxi_portal`: nenhum grant direto, só pelas funções.
- **Funções `SECURITY DEFINER`, com EXECUTE só para `macuxi_portal` (T-0091):**
  - `plataforma.sa_listar_diagnosticos(p_sid uuid, p_filtro jsonb) returns jsonb`: só sessão de super-admin válida (cliente = 42501, sessão vencida = 28000). Faz o join com `plataforma.tenant` só para o nome da empresa e pagina por keyset `(recebido_em, id)`;
  - `plataforma.sa_diagnostico(p_sid uuid, p_id uuid) returns jsonb`: o detalhe, com a `chave_armazenamento` do print;
  - as duas entram no teste de conformidade das `sa_*` (`apps/api/test/funcoes-sa.ts`).
- **`plataforma.arquivo`:** `modulo = 'plataforma'` já cabe no formato da chave (`<tenant>/plataforma/<aaaa-mm>/<id>.jpg`). Se houver CHECK de módulo, inclua `plataforma`.
- **Expurgo:** quem apaga é o worker (item 3); o banco só garante os grants e os índices. Documentar em `docs/banco/plataforma.md` e em `docs/banco/lgpd.md` (retenção de 90 dias).

## 5. App (pedido ao engenheiro-apps)
- **Perfil › Diagnóstico** ganha o botão "Enviar diagnóstico", que abre uma folha com:
  - o campo "O que aconteceu?" (até 1000 caracteres, com o aviso de dado pessoal);
  - "Anexar print" (galeria, JPEG 1600 px qualidade 80 como as fotos; opcional; o print só vai se o vendedor anexar);
  - o resumo do que vai junto: versão, aparelho, Android, tela, último erro e fila do sync.
- **Envio:** entra na **fila do aparelho** com o UUID gerado na hora:
  - com sinal, vai na hora e mostra "Enviado · nº 0042";
  - sem sinal, mostra "Na fila. Envia quando tiver sinal" e, depois, o protocolo no histórico do Diagnóstico (os últimos 10 envios com protocolo e data);
  - o print vai pela fila de arquivos (ADR 0010) depois do `POST` aceito.
- **Sem sessão:** a fila espera o próximo login. Isso cobre a queda antes do login, como a da 1ª abertura da v1.0.2. Não há rota sem autenticação, para não abrir porta de abuso.
- **v1.0.5, queda automática:** na abertura seguinte a uma queda, depois do login, a `SaidaAndroid` nova (T-0144, `CHAVE_SAIDA_VISTA`) vira `origem = 'queda'`. O "Último erro do app", a tela de erro e o erro fatal JS viram `origem = 'erro_tela'`. Tudo isso sem toque do usuário e com um id estável por saída (UUID v5 do `quando` + `motivo` com o namespace fixo do app, para não duplicar se o app cair de novo antes de enviar).
- **O que nunca vai:** nome, e-mail, telefone, cliente ou valor; tenant e usuário vão só pelo token.

## 7. Governança do remetente `diagnostico` (patch ao dono do produto, rito da T-0143)
O patch é `docs/desenho/T-0158-governanca.patch`. O engenheiro-software o prepara e o gerente o leva ao Alexandre.
- **`scripts/coord-lib.mjs`:**
  - `REMETENTES_DE_SISTEMA = ['diagnostico']`, que entra em `remetenteDoRecado` e no índice (`caixa` e `fio` mostram "de diagnostico");
  - **não** entra em `PESSOAS`, `AGENTES` nem `DESTINOS`: ninguém manda recado PARA ele, e `coord enviar --de diagnostico` é recusado no PC e na nuvem ("remetente de sistema: só o servidor grava").
- **Guardião e merge (`.claude/hooks/*`):** recado `-diagnostico` nunca autoriza merge nem governança (`lerRecadosDoGerente` só aceita `-alexandre`).
- **Repositório `aloirr/macuxifdv-recados`:**
  - token fine-grained `macuxi-recados-servidor`, só neste repositório, com **Contents: read and write** e validade de 90 dias;
  - fica em secret do environment `demo` e do `producao` (`MACUXI_RECADOS_TOKEN_SERVIDOR`), entra no `.env` da VM pelo deploy e nunca no app nem em log;
  - se houver validação de remetente no repositório de recados, ela aceita `diagnostico` só nos caminhos `recados/alexandre/` e `recados/engenheiro-apps/`.
- **Workflows `demo-publicar.yml` e `producao-publicar.yml`:** repassam o secret ao `.env` (são do engenheiro-software e vão no mesmo patch para ficar num só rito).

## 8. Segurança e LGPD
- **Dados técnicos:**
  - a máscara única roda no aparelho e de novo no servidor;
  - a descrição livre fica só no banco, por 90 dias;
  - o recado (imutável) só leva o protocolo, dados técnicos curtos e os ids.
- **Print:**
  - só com anexo explícito;
  - o tenant não o lê;
  - o super-admin lê pela rota autenticada e auditada (`auditoria_plataforma`);
  - é apagado com a linha em 90 dias.
- **Token do GitHub:**
  - só no processo do worker;
  - fica fora dos logs (o `log-seguro` já censura `authorization`; o cliente nunca registra o corpo da requisição);
  - se vazar, o dano máximo é escrever recados, e o token pode ser revogado no GitHub.
- **Abuso:** sessão obrigatória, 20 por hora por usuário, corpo de até 32 KB, o print com o mesmo limite das fotos e o teto de 12 recados por hora.

## 9. Testes (pedido ao testes; os da API são do engenheiro-software)
- **API, unidade:**
  - Zod recusa campo extra, como `tenant_id` e `email`;
  - a máscara aplica (CPF, telefone e e-mail na descrição viram `***`);
  - a repetição devolve o mesmo protocolo (200), e outro usuário com o mesmo id dá 409;
  - o print cria `aguardando` e o PUT funciona sem licença de módulo;
  - o GET de print por usuário do tenant dá 404;
  - o limite responde 429;
  - o worker cobre: sem token, `desligado`; concorrência no `main`; teto de 12 por hora com resumo; queda repetida agrupada; espera exponencial; `falhou` na 8ª;
  - o formato do recado é lido pelo `coord-lib`.
- **Banco (CI):** RLS entre dois tenants; `macuxi_app` sem `update`/`delete`; `sa_listar_diagnosticos` recusa o admin do cliente; expurgo de mais de 90 dias com o arquivo.
- **Ponta a ponta (v1.0.5):** queda forçada no aparelho de teste vira linha no portal e recado em `recados/alexandre/`.

## 0. Ponto de partida (o que o código faz hoje e por que não escala)

| Chave (interface chave→JSON) | Quem grava | Forma | Problema no volume do doc 04 |
|---|---|---|---|
| `sync:fila` | motor (`gravarFila`) | array inteiro de `ItemOutbox` a cada mudança | tolerável (dezenas/centenas de itens) |
| `sync:modulos`, `sync:limpeza_pendente`, `sync:sincronizado_em` | motor | valores pequenos | nenhum |
| `sync:cursor:<e>` | motor (`puxarEntidade`) | string `(updated_at\|id)` | nenhum |
| `ent:<e>` | motor (`puxarEntidade`) | **mapa inteiro `id → LinhaSync`**, lido e regravado **a cada página** do pull | 20 mil produtos = 20 páginas × regravar 1..20 mil linhas (≈ 210 mil linhas serializadas) e `JSON.parse` de vários MB no thread JS |
| `mod:<m>:*` | etapas (`ctx.armazenamento`) e telas (`motor.armazenamentoDoModulo`) | blobs do módulo (ex.: `mod:vendedor:produtos` = todas as tabelas de preço) | blob de MB no thread JS; AsyncStorage no Android tem teto padrão de 6 MB |

A busca de produto hoje é `searchProducts` (normaliza e faz `includes` em memória sobre `mod:vendedor:produtos`): funciona
offline, mas exige o catálogo inteiro em memória. Clientes (500) são filtrados em memória por `filterCustomers` — barato.

**Conclusão**: o gargalo não é a interface chave→JSON em si, e sim duas coisas: (a) o pull grava a entidade inteira por página;
(b) não há índice textual. A troca resolve as duas sem mudar `criarMotorSync`, `etapasSync` nem os módulos.

## 1. Adaptador de armazenamento

### 1.1 Interface: a mesma de hoje, com extensões **opcionais**
A interface base continua exatamente a de `motor-sync.ts`:

```ts
export interface ArmazenamentoSync {
  ler<T>(chave: string): Promise<T | null>;
  gravar(chave: string, valor: unknown): Promise<void>;   // null/undefined = remover
  remover(chave: string): Promise<void>;
  chaves(prefixo: string): Promise<string[]>;             // ordenadas
}
```

Extensões novas, todas **opcionais** (um adaptador que não as implementa — memória, AsyncStorage, navegador — continua válido e o
motor segue no caminho atual):

```ts
export interface ArmazenamentoSync {
  // ... base acima ...
  /** Gravação por linha das entidades de sync (pull). Sem ela, o motor usa a chave `ent:<e>` (mapa inteiro). */
  linhas?: LinhasSync;
  /** Executa `fn` tudo-ou-nada. Dentro de `fn`, use SÓ o `tx` recebido. Sem ela, o motor executa em sequência (hoje). */
  emTransacao?<T>(fn: (tx: ArmazenamentoSync) => Promise<T>): Promise<T>;
  /** RN-CORE-02: apaga estruturas próprias do módulo (tabelas `<m>__*`, índices de busca, versão de esquema local). */
  removerModulo?(modulo: ModuloId): Promise<void>;
  /** Busca textual (FTS5 no SQLite; varredura em JS no fallback) — ver §2. */
  busca?: BuscaTextoSync;
}

export interface LinhasSync {
  /** Uma página do pull: upsert das vivas, apaga as com `deleted_at`, grava o cursor — atômico. Idempotente. */
  aplicar(entidade: string, linhas: readonly LinhaSync[], cursor: string | null): Promise<void>;
  listar<L extends LinhaSync>(entidade: string): Promise<L[]>;
  porIds<L extends LinhaSync>(entidade: string, ids: readonly string[]): Promise<L[]>;
  contar(entidade: string): Promise<number>;
  /** Linhas + cursor da entidade (usado por `limparModulo`). */
  limpar(entidade: string): Promise<void>;
}
```

Mudanças no motor (mínimas, sem quebrar nenhum chamador):
- `puxarEntidade`: se `op.armazenamento.linhas` existe → `linhas.aplicar(e, pagina.itens, cursor)` por página (nada de reler o
  mapa); senão, o código atual.
- `motor.linhas(e)`: `linhas.listar(e)` se existir; senão o atual. Novo `motor.linhasPorIds(e, ids)` (fallback filtra o mapa).
- `limparModulo(m)`: `linhas.limpar(e)` se existir; depois `removerModulo?.(m)`; tudo dentro de `emTransacao` se existir.
- `confirmarLimpeza(m)`: fila + limpeza + `limpezaPendente` dentro de `emTransacao` se existir.
- `comPrefixo` continua devolvendo **só a base** (o módulo enxerga só a própria chave→valor; nunca linhas nem SQL).

Para provar a extensão sem SQLite, o SDK ganha `comLinhasEmChaveJson(base)`: implementa `linhas` sobre as mesmas chaves
`ent:<e>`/`sync:cursor:<e>` (semântica idêntica, sem ganho de desempenho). A suíte de contrato roda nos dois caminhos.

### 1.2 Tabelas: **híbrido** (decidido)
| Estrutura | Para quê | Por quê |
|---|---|---|
| `kv(chave TEXT PRIMARY KEY, valor TEXT NOT NULL) WITHOUT ROWID` | tudo que a interface base grava: `sync:*` (inclusive `sync:fila` e cursores), `mod:<m>:*` | o motor e as etapas não mudam; cada `gravar` é uma linha atômica |
| `ent_<entidade>(id TEXT PRIMARY KEY, updated_at TEXT NOT NULL, deleted_at TEXT, dados TEXT NOT NULL) WITHOUT ROWID` + índice `(updated_at, id)` | uma tabela **genérica** por entidade de sync **com pull** | o pull precisa de granularidade por linha (upsert/remoção por página) em qualquer entidade, não só nas consultadas; colunas genéricas = nenhuma DDL por entidade |
| índices de expressão em `ent_<e>` (`json_extract(dados,'$.campo')`) | só onde um módulo consulta por campo (ex.: `tabela_preco_item` por `tabela_preco_id, produto_id`; `estoque_saldo` por `produto_id`) | índice só onde há consulta; declarado pelo dono da entidade na migração local do módulo (§1.4) |
| `<modulo>__<nome>` | tabelas próprias de um módulo (ex.: `catalogo__busca_doc`, FTS `catalogo__busca`) | prefixo = dono; RN-CORE-02 apaga por prefixo |
| `_esquema(dono TEXT PRIMARY KEY, versao INTEGER NOT NULL, aplicado_em TEXT NOT NULL)` | versão do esquema local da plataforma (`dono='plataforma'`) e de cada módulo | migração por módulo (§1.4) |
| `_entidades(nome TEXT PRIMARY KEY, modulo TEXT NOT NULL, criada_em TEXT NOT NULL)` | quais `ent_<e>` existem e de quem são | limpar entidade de módulo que nem está mais registrado |

Decisões de detalhe:
- **Outbox fica na `kv` (`sync:fila`, uma linha JSON)** e não em tabela própria nesta tarefa. O motor já mantém a fila em memória
  (`estado.fila`) e regrava o array; uma linha na `kv` é atômica e mantém a interface base. **Gatilho para tabela `_fila`**: p95 da
  fila > 300 itens ou > 1 MB por gravação no aparelho de referência (ver §7). Isso refina o adendo anterior da ADR 0003.
- **Fila nunca fica em tabela de módulo**: apagar/recriar tabelas `<m>__*` (migração, downgrade, RN-CORE-02) nunca perde item
  não enviado.
- **Compatibilidade da chave `ent:<e>`** (para a suíte de contrato e para a migração): no adaptador SQLite, `ler('ent:x')` monta
  o mapa a partir de `ent_x`; `gravar('ent:x', mapa)` substitui o conteúdo em uma transação; `remover('ent:x')` apaga as linhas;
  `chaves('ent:')` lista as entidades não vazias. É caminho de compatibilidade (lento por natureza), nunca o do pull.
- **Um arquivo por usuário**: `macuxi-u-<userId>.db` (o id é UUID; validar `^[0-9a-f-]{36}$` antes de montar o nome). Mantém o
  isolamento que o prefixo `macuxi:u:<id>:` dá hoje, sem coluna de usuário em toda tabela. Trocar de usuário fecha um arquivo e abre
  outro; sair não apaga (a fila offline é preservada).
- `tenant_id`/`created_at`/`external_id` não viram colunas no aparelho: chegam dentro de `dados` (o arquivo já é de um usuário de um
  tenant). A regra 5 do CLAUDE.md vale para o Postgres; aqui valem `id`, `updated_at`, `deleted_at` (cursor e remoção).
- Nomes de tabela vêm de `ENTIDADE_SYNC_RE`/`MODULOS` (snake_case validado) — nunca de texto livre; valores sempre por parâmetro.
- `chaves(prefixo)` usa faixa (`chave >= ? AND chave < ?` com limite superior `prefixo + '￿'`), não `LIKE` (evita escapar `%`/`_`).

### 1.3 Transações, lotes e concorrência
- Escritas **serializadas** numa fila interna do adaptador (cadeia de promessas, como o `writeJson` de hoje faz por chave). Motivo:
  no `expo-sqlite`, `withExclusiveTransactionAsync` abre outra conexão e escritas de fora dela falham com `database is locked`.
  Leituras não entram na fila (WAL permite ler durante a escrita).
- Lote: `linhas.aplicar` divide a página (1.000) em lotes de **500 linhas por transação** (`TAMANHO_LOTE_GRAVACAO = 500`), com
  comandos preparados (`INSERT … ON CONFLICT(id) DO UPDATE`, `DELETE … WHERE id = ?`) reaproveitados no lote e finalizados ao fim.
  O cursor é gravado na transação do **último** lote da página. Se o app cair entre lotes, o cursor antigo faz a página vir de novo
  e o upsert por `id` torna isso inofensivo (idempotente).
- Entre lotes o adaptador **cede o loop** (`await new Promise(r => setTimeout(r, 0))`) para a UI desenhar (a serialização JSON e o
  repasse de parâmetros rodam no thread JS; a execução SQL roda no thread nativo).
- PRAGMAs na abertura: `journal_mode=WAL`, `synchronous=NORMAL`, `busy_timeout=5000`, `foreign_keys=ON`,
  `auto_vacuum=INCREMENTAL` (só tem efeito na criação do arquivo; definir antes da primeira tabela). Gravação de `sync:fila` em
  `synchronous=FULL` (troca de PRAGMA fora de transação, na fila de escrita): pedido "na fila" não pode sumir com queda de energia;
  o restante tolera perder a última transação (vem de novo do servidor).

### 1.4 Migrações de esquema no aparelho
- **Plataforma**: migrações em `packages/platform-sdk/src/sqlite/esquema.ts` (`kv`, `_esquema`, `_entidades`, PRAGMAs). DDL
  especificada pelo banco-dados (§6, P2) e codificada pelo engenheiro.
- **Módulos**: cada módulo que precisa de estrutura local exporta `migracoesAparelho` em `modules/<m>/db/aparelho.ts` (dono:
  banco-dados; só strings SQL, sem dependência) e o `moduloApp` a declara em `definirModuloShell({ ..., migracoesAparelho })`.
  Formato: `{ versao: number; sql: string }[]`, crescente, só para frente.
- **Tabela `ent_<e>`** é criada pelo próprio adaptador na primeira gravação da entidade (DDL fixa) e registrada em `_entidades`.
- **Execução**: na abertura do banco (antes de `motor.carregar()`), para a plataforma e para cada módulo **efetivo**, aplica as versões
  `> _esquema.versao`, cada uma numa transação exclusiva junto com a atualização de `_esquema`. Falha = rollback daquela versão,
  módulo marcado "armazenamento local indisponível" (o módulo continua com o que já tinha; a fila não é afetada).
- **Validação de dono** (teste do SDK, não em produção): aplicar as migrações de cada módulo num banco vazio e conferir em
  `sqlite_master` que todo objeto criado é `<m>__*` ou índice sobre `ent_<e>` de entidade **do próprio módulo**.
- **Versão do aparelho maior que a do app** (downgrade): os objetos daquele módulo são apagados e recriados do zero (são
  reconstruíveis pelo pull); a fila está na `kv` da plataforma e não é tocada.

### 1.5 Apagar dados do módulo desativado (RN-CORE-02)
Texto da regra (doc 03): *"Módulo desativado: some do app no próximo sync, os dados locais dele são apagados do aparelho … Antes de
apagar os dados locais, o app tenta enviar a fila (outbox) do módulo … Os dados locais do módulo só são apagados depois que o
usuário confirma que viu (nada some em silêncio)."* O fluxo do motor não muda (`aplicarModulosAtivos` / `confirmarLimpeza`); muda só
o que "apagar" significa no SQLite, numa transação:
1. `linhas.limpar(e)` para cada entidade do módulo (via registro **e** via `_entidades`, cobrindo entidade que saiu do registro);
2. `DELETE FROM kv WHERE chave` na faixa `mod:<m>:`;
3. `removerModulo(m)`: `DROP` de todo objeto `<m>__*` (inclusive a FTS), `DELETE FROM _esquema WHERE dono = m`;
4. fora da transação: `PRAGMA incremental_vacuum` (devolve o espaço — "nada ocupa espaço sem licença", doc 04).
Reativação recria tudo pelas migrações e pelo pull desde o início (cursor apagado).

## 2. FTS5 para o Catálogo

### 2.1 Quem é dono de quê (ADR 0005 e fronteiras)
| Peça | Onde | Dono |
|---|---|---|
| Capacidade genérica: `BuscaTextoSync`, manutenção do índice no pull, sanitização (`montarConsultaFts`), fallback em JS | `packages/platform-sdk/src/busca.ts`, `src/sqlite/` | engenheiro-software |
| DDL da busca do Catálogo (doc table + FTS5 + vocabulário) | `modules/catalogo/db/aparelho.ts` (`migracoesAparelho`) | banco-dados |
| Declaração do índice (fontes, colunas, pesos, `documento()`), uso nas telas | `modules/catalogo/app/busca.ts` | modulo-catalogo |
| Expansão por sinônimos, correção de digitação, regras de ordenação | `modules/catalogo/domain/busca.ts` (puro, testes citando RN-CAT-*) | modulo-catalogo |

O índice é um **read-model próprio do Catálogo** (doc 04, fronteira 2): as fontes são entidades de sync — `produto` (Core, ADR
0005) e `produto_atributo` (Catálogo) — entregues pelo SDK com os tipos de `@macuxi/core/contracts` e `modules/catalogo/contracts`.
O Catálogo nunca faz SQL sobre `ent_produto`; o SDK chama `documento()` do índice com as linhas afetadas. Fonte de outro módulo só é
aceita se esse módulo está em `depende` do dono do índice (Catálogo `depende: ['core']`) — validado em `criarShell`.
Outros módulos (ex.: Vendedor no seletor de produtos) consomem a busca por um serviço/extensão exposto pelo Catálogo (a desenhar com
o módulo Catálogo/T-0007), nunca pelo id do índice.

### 2.2 Declaração do índice (SDK)
```ts
definirIndiceBusca({
  id: 'catalogo.produto',
  modulo: 'catalogo',
  tabelaDoc: 'catalogo__busca_doc', tabelaFts: 'catalogo__busca',     // criadas pela migração do módulo
  colunas: { sku: 10, ean: 10, codigos: 8, nome: 5, marca: 3, categoria: 2, atributos: 1 },  // ordem = ordem da DDL; valor = peso bm25
  fontes: ['produto', 'produto_atributo'],
  chaveDe: (entidade, linha) => entidade === 'produto' ? linha.id : (linha as ProdutoAtributo).produto_id,
  documento: async (produtoId, ler) => { /* lê produto e atributos por id via `ler.porIds`; devolve colunas ou null */ },
});
```
O SDK valida na abertura (`PRAGMA table_info`) que `tabelaFts` tem exatamente essas colunas, na ordem.

### 2.3 Tabela virtual: **content externo** (decidido)
DDL proposta (o banco-dados finaliza em `modules/catalogo/db/aparelho.ts`):
```sql
CREATE TABLE catalogo__busca_doc (
  rid INTEGER PRIMARY KEY,               -- rowid estável para o FTS
  produto_id TEXT NOT NULL UNIQUE,
  sku TEXT, ean TEXT, codigos TEXT, nome TEXT, marca TEXT, categoria TEXT, atributos TEXT
);
CREATE VIRTUAL TABLE catalogo__busca USING fts5(
  sku, ean, codigos, nome, marca, categoria, atributos,
  content = 'catalogo__busca_doc', content_rowid = 'rid',
  tokenize = 'unicode61 remove_diacritics 2',
  prefix = '2 3'
);
CREATE VIRTUAL TABLE catalogo__busca_vocab USING fts5vocab(catalogo__busca, row);   -- correção de digitação (§2.6)
```
| Opção | Prós | Contras | Decisão |
|---|---|---|---|
| FTS normal (guarda o texto) | simples | texto duplicado (doc + FTS) | não |
| **content externo** sobre `catalogo__busca_doc` | sem duplicar; `'rebuild'` reconstrói tudo de uma vez após a carga; `highlight`/`snippet` funcionam | manutenção explícita (apagar com valores antigos) | **sim** |
| contentless (`content=''`) | menor | sem `rebuild`, sem devolver valores, `delete` exige os valores antigos | não |
| `detail=column/none` | índice menor | perde consulta de frase (sinônimo com duas palavras, código `6203 2rs`) | não (`detail=full`) |

Manutenção (pelo SDK, **sem gatilhos** SQL, para permitir o caminho de carga em massa):
- **Carga em massa** (índice vazio ou página que muda > 2.000 chaves): grava só a `catalogo__busca_doc` e marca o índice "sujo";
  no fim do sync roda `INSERT INTO catalogo__busca(catalogo__busca) VALUES('rebuild')` numa transação.
- **Incremental**: para cada chave afetada, na mesma transação do lote: `INSERT INTO catalogo__busca(catalogo__busca, rowid, …)
  VALUES('delete', rid, <valores antigos>)`, upsert na doc, `INSERT INTO catalogo__busca(rowid, …)`; `documento() = null` remove.
- A cada ~5.000 mudanças incrementais: `INSERT INTO catalogo__busca(catalogo__busca) VALUES('optimize')` fora do horário de uso
  (fim do sync).

### 2.4 Tokenização
- `unicode61 remove_diacritics 2`: minúsculas e sem acento, inclusive nos casos que o valor `1` deixava passar ("ação" = "acao").
  Exige SQLite ≥ 3.27 (expo-sqlite 57 traz 3.50.3; Node 22.23 traz 3.53.4).
- **`tokenchars`: nenhum extra (decidido).** Com `-`/`.`/`/` como separadores, `6203-2RS` vira `6203` + `2rs`. Para achar o código
  digitado de qualquer jeito, `documento()` preenche a coluna `codigos` com a forma compacta (`62032rs`, só `[a-z0-9]`) do SKU, do
  código do ERP e de códigos de aplicação. Consulta `6203-2rs` → `("6203" "2rs" em frase) OR "62032rs"*`. Pôr `-` em `tokenchars`
  faria `2rs` sozinho não achar nada e quebraria nomes compostos ("anti-ruído").
- A normalização em JS da consulta (`normalizarBusca` no SDK: `NFKD`, remove `\p{M}`, minúsculas, separa em `[^\p{L}\p{N}]+`)
  segue a do tokenizer; teste de contrato compara as duas em uma lista de palavras com acento, cedilha, `º`, `ª`, dígitos.

### 2.5 Sinônimos do tenant: **expansão da consulta no domínio** (decidido)
- Fonte: entidade de sync `sinonimo` (Catálogo), poucos milhares de linhas no máximo, mantida em memória pelo módulo.
- `expandirConsulta(texto, sinonimos)` em `modules/catalogo/domain/busca.ts` (puro) devolve uma `ConsultaBusca` estruturada:
  `{ grupos: string[][]; prefixoNoUltimo: boolean; limite?: number }`, um grupo por termo digitado com o termo e seus sinônimos
  (grupos de sinônimos bidirecionais; sinônimo de várias palavras vira frase).
- Alternativa descartada: **expansão no índice** (gravar sinônimos no documento) — cada mudança de sinônimo exigiria reindexar
  20 mil documentos e inflaria o índice; **tokenizer próprio** — impossível no expo-sqlite (exigiria C nativo).

### 2.6 Prefixo, ranking, correção de digitação e filtros
- **Prefixo para digitação**: `prefix='2 3'` cria índices de 2 e 3 caracteres; só o **último** termo (o que está sendo digitado) vai
  com `*` e só se tiver ≥ 2 caracteres. Consulta só com 1 caractere → não consulta (a tela pede "digite ao menos 2 letras").
- **Ranking**: `ORDER BY bm25(catalogo__busca, 10, 10, 8, 5, 3, 2, 1), nome LIMIT ?` (pesos na ordem das colunas: sku, ean,
  codigos, nome, marca, categoria, atributos; `bm25` é menor = melhor). Desempate estável por nome. SKU/EAN idêntico ao digitado vai
  para o topo (regra no domínio, com teste).
- **Correção de digitação** (doc 04): com zero resultados, o domínio busca candidatos no `catalogo__busca_vocab` (mesma letra
  inicial, Damerau-Levenshtein ≤ 1 para termos de 4–7 letras, ≤ 2 a partir de 8, ordenados por frequência) e refaz a consulta
  ("mostrando resultados para …"). Capacidade do SDK: `busca.vocabulario(indice, prefixo, limite)`. Entra com o módulo Catálogo; não
  é critério da T-0008.
- **Filtros** (estoque, tabela de preço do cliente — RN-CAT-01) são aplicados depois, por `produto_id`, sobre as linhas do Catálogo;
  a busca devolve até 200 chaves para sobrar após o filtro e a tela mostra 50.

### 2.7 Sanitização da consulta (no SDK, obrigatória)
`montarConsultaFts(consulta: ConsultaBusca): string | null` — o módulo **nunca** escreve sintaxe FTS:
1. Cada termo passa por `normalizarBusca`; o que sobra só tem letras e dígitos (aspas, `*`, `:`, `^`, `(`, `-`, `NEAR` somem ou
   viram termo comum). Mesmo assim, `"` é duplicado por defesa.
2. Cada termo vira `"termo"`; frase vira `"a b"`; o último grupo ganha `*` (regra do prefixo).
3. Alternativas do grupo unidas por ` OR ` entre parênteses; grupos unidos por **` AND ` explícito** — verificado no SQLite 3.53:
   `"freio" ("disco" OR "tambor")` é erro de sintaxe; `"freio" AND ("disco" OR "tambor")` funciona.
4. Limites: até 8 grupos, 10 alternativas por grupo, 40 caracteres por termo; acima disso corta.
5. A string vai por parâmetro (`MATCH ?`), nunca concatenada no SQL. Erro do FTS vira lista vazia + log sem o texto digitado
   (só o tamanho e o índice).

### 2.8 Enquanto o Catálogo não existe
- Nenhum índice é registrado ⇒ nenhuma tabela FTS é criada; `busca` existe como capacidade, desligada.
- O Vendedor continua com `searchProducts` (em memória, `normalize` + `includes`) sobre `mod:vendedor:produtos`, que no SQLite é uma
  linha da `kv`. Funciona offline e cumpre < 300 ms em 20 mil itens já carregados; o custo é a leitura do blob na abertura — some
  quando produto/preço/estoque vierem pelo pull (T-0004/T-0007) e a busca passar ao Catálogo.
- Fallback da capacidade (adaptador memória/AsyncStorage/navegador): o SDK implementa `BuscaTextoSync` em JS sobre os documentos
  (mesmo `documento()`, mesma `normalizarBusca`, AND dos grupos, prefixo no último, pontuação por soma dos pesos das colunas que
  casaram). O conjunto de resultados é igual ao do FTS; a ordem pode diferir — os testes de contrato comparam conjunto e o primeiro
  lugar só no caso de SKU exato.
- Promotor/Pesquisa/Gestor (só produto do Core, sem Catálogo) não têm FTS: as listas deles são pequenas (mix obrigatório, itens da
  pesquisa) e filtram em memória. Se um tenant só de trade precisar buscar nos 20 mil, o Core ganha um índice próprio
  (`core__produto_busca`) com a mesma capacidade — decisão futura (§7).

## 3. Biblioteca

### 3.1 No aparelho: `expo-sqlite` ~57.0.4
- `apps/mobile` está no Expo **~57.0.0** / RN 0.86.3; a tag `sdk-57` do `expo-sqlite` é **57.0.4** (instalar com
  `npx expo install expo-sqlite`, que fixa `~57.0.4`). Vem com **SQLite 3.50.3 próprio** (não usa o SQLite do Android: FTS5 não
  depende da versão do sistema).
- **FTS5 vem ligado**: `android/build.gradle` acrescenta `-DSQLITE_ENABLE_FTS4=1 -DSQLITE_ENABLE_FTS3_PARENTHESIS=1
  -DSQLITE_ENABLE_FTS5=1` sempre que a propriedade `expo.sqlite.enableFTS` não for `false` (idem no iOS). Mesmo assim declaramos
  `['expo-sqlite', { enableFTS: true }]` em `plugins` do `app.config.ts` para não depender do padrão, e o app confere na abertura
  (`SELECT sqlite_compileoption_used('ENABLE_FTS5')`; falso ⇒ busca cai no fallback JS e registra erro).
- API usada (assíncrona; execução no thread nativo): `openDatabaseAsync(nome)`, `execAsync` (PRAGMAs/DDL), `prepareAsync` →
  `executeAsync`/`finalizeAsync` (comandos preparados), `runAsync`, `getAllAsync`, `getFirstAsync`, `closeAsync`,
  `withExclusiveTransactionAsync(async (txn) => …)` — dentro dela **toda** consulta usa `txn` (outra conexão; a nossa fila de
  escrita impede o `database is locked`). Não usamos `withTransactionAsync` (deixa outras consultas assíncronas entrarem na transação).
- `withExclusiveTransactionAsync` não existe no web: o navegador continua no chave→JSON (o `apps/web` não usa o motor do aparelho).

### 3.2 Nos testes (Node): **`node:sqlite`** (decidido)
| Critério | `node:sqlite` | `better-sqlite3` 13.0.3 |
|---|---|---|
| Instalação | embutido no Node; zero dependência | addon nativo; no pnpm 12 precisa de `allowBuilds`/`onlyBuiltDependencies`; binário pré-compilado por SO/Node (Windows do Alexandre, Linux da nuvem e do CI) |
| Versão | sem flag a partir do Node **22.13** (22.5–22.12 exigia `--experimental-sqlite`); aqui: Node 22.23.4, SQLite 3.53.4; CI: Node 24 | `engines: node >= 22` |
| FTS5, `remove_diacritics 2`, `prefix`, `fts5vocab`, `trigram` | **verificados** neste ambiente (inclusive dentro do Vitest 3.2.7 do repositório) | sim |
| API | síncrona (`DatabaseSync`, `prepare`, `exec`, `isTransaction`) | síncrona, quase idêntica |
| Contras | "experimental" (emite `ExperimentalWarning`; silenciar no setup do Vitest com `--disable-warning=ExperimentalWarning`) | dependência nativa a manter |

Consequência: `engines.node` da raiz passa de `>=20.19` para **`>=22.13`** (engenheiro, P3). Se o `node:sqlite` mudar de API, troca-se
pelo `better-sqlite3` sob o mesmo driver (§3.3) sem tocar no adaptador.

### 3.3 Driver mínimo (o adaptador não conhece a biblioteca)
```ts
export type ValorSql = string | number | null;
export interface DriverSqlite {
  executar(sql: string): Promise<void>;                                        // DDL/PRAGMA, várias instruções
  rodar(sql: string, params?: readonly ValorSql[]): Promise<{ alteradas: number }>;
  todas<T>(sql: string, params?: readonly ValorSql[]): Promise<T[]>;
  primeira<T>(sql: string, params?: readonly ValorSql[]): Promise<T | null>;
  preparar(sql: string): Promise<{ rodar(params: readonly ValorSql[]): Promise<void>; finalizar(): Promise<void> }>;
  transacaoExclusiva<T>(fn: (tx: DriverSqlite) => Promise<T>): Promise<T>;
  fechar(): Promise<void>;
}
```
- `criarArmazenamentoSqlite(driver, opcoes)` em `packages/platform-sdk/src/sqlite/` (TS puro, exportado pelo índice).
- Driver Node em `packages/platform-sdk/src/sqlite/driver-node.ts`, exportado **só** pelo subcaminho
  `@macuxi/platform-sdk/sqlite-node` (o Metro nunca o vê).
- Driver Expo em `apps/mobile/src/services/sqlite-expo.ts` (shell); `armazenamento.ts` passa a escolher SQLite ou AsyncStorage
  (`EXPO_PUBLIC_ARMAZENAMENTO=sqlite|asyncstorage`, padrão `sqlite` após a P8).

### 3.4 Mesma suíte do motor nos dois adaptadores
- Os casos de `motor-sync.test.ts` e `motor-sync.fase-m.test.ts` passam a ser uma **suíte de contrato parametrizada**
  (`describe.each`) sobre fábricas de armazenamento: (a) `criarArmazenamentoEmMemoria()` (sem extensões — caminho de hoje);
  (b) `comLinhasEmChaveJson(memória)`; (c) `criarArmazenamentoSqlite(driverNode(':memory:'))`. Os títulos dos casos não mudam

- Os casos que hoje leem `armazenamento.ler('ent:pedido')` continuam válidos graças à compatibilidade da chave `ent:<e>` (§1.2).
- Suíte do adaptador (`armazenamento.contrato.ts`): semântica da base (`null` remove, `chaves` ordenadas por prefixo, cópia
  profunda no `ler`), `linhas.aplicar` idempotente, cursor atômico com a página, RN-CORE-02 (`sqlite_master` sem `<m>__*`,

## 4. Desempenho

### 4.1 Carga de 20 mil SKUs e 500 clientes sem travar a UI
- Pull em páginas de 1.000 (`TAMANHO_PAGINA_SYNC`), gravadas em lotes de 500 por transação exclusiva, com comandos preparados
  reaproveitados no lote e `setTimeout(0)` entre lotes; a tela de sync mostra progresso por entidade (já existe `estado.progresso`).
- Índice FTS: na primeira carga, só a `catalogo__busca_doc`; `'rebuild'` uma vez no fim. Depois, incremental.
- WAL + `synchronous=NORMAL` (fila em `FULL`, §1.3); leitura das telas não espera a carga (WAL).
- Nada de `motor.linhas('produto')` em tela: telas usam `busca`, `linhasPorIds` e consultas paginadas.
- Medição de referência (Node 22.23.4, `node:sqlite`, VM de 4 vCPU, este ambiente): 20 mil produtos gravados em lotes de 500 com
  doc de busca = **0,85 s**; `'rebuild'` do FTS = **0,16 s**; 300 consultas típicas (prefixo curto, duas palavras, OR de sinônimos)
  com `bm25` e `LIMIT 50` = **p50 4,3 ms, p95 10,6 ms**.

### 4.2 Metas e orçamentos
| Medida | Aparelho de referência | CI (Node) — orçamento com margem |
|---|---|---|
| Gravar 20 mil SKUs + 500 clientes (sem rede, a partir de páginas prontas) | ≤ 30 s | ≤ 5 s |
| Maior bloqueio do thread JS durante a carga | ≤ 200 ms (nenhum lote acima) | — |
| Quadros perdidos na tela de sync durante a carga (`dumpsys gfxinfo`) | < 10 % | — |
| `rebuild` do FTS com 20 mil | ≤ 3 s | ≤ 1 s |
| `buscar()` (consulta + 50 resultados), p95 de 300 consultas | **< 300 ms** (critério da T-0008) | ≤ 30 ms (10× de margem para o aparelho) |
| Abrir o app com a base carregada (até a primeira tela com dados) | < 2 s (doc 04) | — |

### 4.3 Como medir
- **Aparelho**: build de perfil EAS (`perfil`: release, `EXPO_PUBLIC_MEDIR=1`) que grava marcas `performance.now()` por lote, por
  página, no `rebuild` e em cada `buscar()` num anel em memória, exibido numa tela oculta de diagnóstico e exportável (sem dado
  pessoal: só tempos, contagens e nome da etapa). Quadros: `adb shell dumpsys gfxinfo <pacote> reset` antes e leitura depois.
  **Aparelho de referência**: Android de entrada (Android 10+, 2–3 GB de RAM, ex.: linha Galaxy A0x/Moto E) — premissa até o
  Alexandre indicar o modelo. Dados: gerador determinístico de 20 mil SKUs e 500 clientes (mesmo do CI) servido pelo transporte
  simulado ou pelo mock-api.
- **CI**: `tests/carga/sqlite-aparelho.test.ts` (dono: testes) com `node:sqlite`, o adaptador real e o motor real sobre
  `criarServidorSyncSimulado` (páginas de 1.000). Roda num job próprio (`pnpm test:carga`), fora do `pnpm test` padrão, com uma
  repetição em caso de estouro antes de falhar. Orçamentos da tabela acima.

## 5. Migração do chave→JSON (AsyncStorage) para SQLite sem perder a fila
Roda por usuário, no shell (`apps/mobile/src/services/migracao-armazenamento.ts`), **antes** de `criarMotorSync` (o motor não
existe durante a migração ⇒ ninguém escreve). Tela "Atualizando os dados do aparelho…" com progresso.

Marcador na `kv` do SQLite: `_migracao:asyncstorage` = `{ estado: 'copiando' | 'concluida', iniciada_em, concluida_em?,
contagens: { fila, chaves, linhas } }`.

1. Abrir o SQLite do usuário e aplicar as migrações de esquema (§1.4).
2. Ler o marcador. `concluida` ⇒ **nunca** copiar de novo (o SQLite pode ter fila mais nova); ir ao passo 7.
3. Marcador ausente ou `copiando` (queda no meio) ⇒ apagar o que uma tentativa anterior deixou (`kv` exceto o marcador, `ent_*`,
   `_entidades`) — a origem está intacta, então recomeçar é seguro (reentrada idempotente). Gravar `copiando`.
4. Listar as chaves `macuxi:u:<id>:*` do AsyncStorage. Nenhuma ⇒ gravar `concluida` com contagens zero e ir ao passo 7.
5. **Fila primeiro**: ler `sync:fila` do AsyncStorage, gravar na `kv` (com `synchronous=FULL`), **reler do SQLite e comparar**:
   mesma quantidade, mesmos `id` na mesma ordem e o mesmo JSON. Diferença ⇒ abortar: a sessão segue com o adaptador AsyncStorage
   (nada se perde), erro registrado, nova tentativa na próxima abertura.
6. Restante, em lotes de 500 por transação: `sync:modulos`, `sync:limpeza_pendente`, `sync:sincronizado_em`, `mod:*` → `kv`;
   cada `ent:<e>` → `ent_<e>` **na mesma transação** do seu `sync:cursor:<e>` (linhas e cursor nunca descasados). Conferir as
   contagens e, na transação do último lote, gravar o marcador `concluida` com as contagens.
7. **Apagar o antigo só depois**: as chaves `macuxi:u:<id>:*` do AsyncStorage são removidas quando o marcador está `concluida`
   **e** já houve um sync completo com sucesso depois da migração (ou 7 dias) — permite voltar à versão anterior do app sem perder
   a fila nesse intervalo. Remoção idempotente (reexecutada a cada abertura até não sobrar chave).
- Fora da migração: chaves globais do shell (`fv:settings`, `fv:session`, `fv:offline`) continuam no AsyncStorage.
- Falha em qualquer passo antes do `concluida` ⇒ AsyncStorage continua sendo a fonte na sessão; o usuário trabalha normalmente.
- Teste (P4): AsyncStorage simulado em memória + driver Node; injetar falha em cada passo (exceção, "app morto" entre lotes, fila
  divergente) e provar: nenhum item de fila perdido nem duplicado; reentrada converge; após `concluida`, AsyncStorage nunca mais é
  lido como fonte.
- Observação: o `writeJson` atual engole erros de gravação (`.catch(() => {})`); a verificação do passo 5 é o que garante que a
  fila migrada é a que o usuário viu.

## 7. Riscos e premissas

### Riscos
| Risco | Mitigação |
|---|---|
| `node:sqlite` ainda "experimental" (aviso; API pode mudar) | driver isolado; troca por `better-sqlite3` sem tocar no adaptador |
| SQLite do Node (3.53) ≠ do Expo (3.50) | usar só recursos ≤ 3.45; teste de contrato roda no Node e o roteiro P7 no aparelho |
| `database is locked` com `withExclusiveTransactionAsync` (outra conexão) | toda escrita pela fila interna; `busy_timeout=5000` |
| Fila como uma linha JSON cresce (muitos pedidos offline com itens) | medir no P7; gatilho para tabela `_fila` (> 300 itens ou > 1 MB) com ADR |
| Blob `mod:vendedor:produtos` continua grande até T-0004/T-0007 | transitório; medido no P7; se passar de 2 s na abertura, antecipar o pull de produto |
| Motor publica o estado antes de gravar (`gravarFila` chama `mudar` antes do `await gravar`) — em erro de disco, a tela mostra algo que não foi salvo | P1 avalia inverter a ordem (gravar e só então publicar); não muda contrato |
| `synchronous=NORMAL` perde a última transação em queda de energia | fila em `FULL`; o resto volta do servidor |
| Manifesto do Catálogo ainda lista `produto` em `sync` e o do Core não (contraria ADR 0005) | corrigido na T-0007; o índice usa a entidade `produto` de quem for o dono no registro |
| Dados no aparelho sem criptografia (igual ao AsyncStorage de hoje) | fora do escopo; `expo-sqlite` aceita SQLCipher (`useSQLCipher`) — avaliar em ADR própria (LGPD) |
| Tenant só de trade marketing precisa buscar nos 20 mil sem Catálogo | índice `core__produto_busca` com a mesma capacidade (decisão futura) |
| Downgrade do app após a migração | AsyncStorage só é apagado após sync bem-sucedido ou 7 dias (§5, passo 7) |

### Premissas assumidas
1. Expo continua no SDK 57 durante a T-0008; `expo-sqlite` entra como `~57.0.4` (sem nova ADR: a dependência já foi autorizada no
   adendo "Troca do armazenamento" da ADR 0003).
2. Node ≥ 22.13 nas máquinas locais (Windows do Alexandre a confirmar) e Node 24 no CI (`.github/workflows/ci.yml`).
3. Aparelho de referência: Android 10+ de entrada (2–3 GB de RAM); modelo exato a definir pelo Alexandre.
4. Volumes do doc 04 (20 mil SKUs, 500 clientes); atributos por produto ≤ ~20; sinônimos do tenant ≤ alguns milhares.
5. "Busca < 300 ms" = tempo do `buscar()` (consulta + leitura dos 50 primeiros), p95, sem contar o atraso de digitação da tela.
6. "Sem travar a UI" = nenhuma tarefa no thread JS acima de 200 ms durante a carga e < 10 % de quadros perdidos na tela de sync.
7. O navegador (`apps/web`) não usa o motor do aparelho; segue com chave→JSON se precisar.
8. Isolamento por arquivo por usuário é suficiente (sem coluna de usuário/tenant nas tabelas do aparelho).

> dependência nova; a tela do admin da plataforma, que pediria ADR, fica de fora, §8).

## 1. Decisão: comando, não tela
**Comando** `pnpm --filter api tenant criar ...` (atalho na raiz: `pnpm tenant:criar`), arquivo `apps/api/src/cli/tenant.ts`.
- Fica no `apps/api` porque é a raiz de composição que já conhece **todos os manifestos** (`apps/api/src/modulos.ts`): os perfis
  padrão de cada módulo (`manifest.perfis`) e as dependências saem de lá, sem uma segunda lista para desatualizar.
- Conecta com a **conexão de administração** do banco (as mesmas variáveis `MACUXI_PG_ADMIN_*` do `migrar`), **nunca** como
  `macuxi_app`: o app não tem `insert` em `plataforma.tenant` e assim continua. Na demo:
  `docker compose run --rm -e MACUXI_PG_ADMIN_SENHA api pnpm tenant criar ...` (a API em serviço segue sem a senha de admin).
- **Tela do admin da plataforma: fora** (§8). Ela exige uma identidade de operador fora de qualquer tenant (token sem `tid`,
  caminho que atravessa o RLS) — decisão de segurança com ADR própria.

## 2. Regra proposta — RN-CORE-31 Onboarding de tenant
1. Cria, numa transação: o tenant (`codigo` único, sem diferenciar maiúsculas; nome; documento opcional; fuso IANA, padrão
   `America/Sao_Paulo`; plano, padrão `piloto`; status `ativo`), as **licenças** dos módulos pedidos (`plataforma.tenant_modulo`,
   ativo, com teto de licenças opcional por módulo), os **módulos por perfil** padrão (`plataforma.perfil_modulo` =
   `manifest.perfis` de cada módulo; o Promotor nunca recebe o Vendedor, RN-PRO-01, já garantido pelos manifestos) e o **admin inicial**
   (perfil admin, ativo, sem equipe).
2. **Core sempre** entra. Módulo pedido sem a dependência na lista = recusa com a dependência que falta (não liga sozinho).
3. **Parâmetros padrão = nenhuma linha**: o padrão do doc 03 vale enquanto o tenant não gravar o seu (convenção já usada nas
   T-0013/T-0073). Motivos de sistema e medidas padrão vêm dos gatilhos que já existem em `plataforma.tenant`
   (`tenant_semear_core`, 0006; `tenant_semear_medidas`, 0018). Equipes, usuários de campo, carteira e ERP: pelo BKO e pelo Hub.
4. **Idempotente pela chave `codigo`**: rodar de novo não duplica nada. Tenant existente: nome/fuso/plano **não mudam** (aviso);
   módulos faltantes são **acrescentados** com os perfis padrão; módulo já existente e perfis já gravados **não mudam** (o tenant pode
   ter personalizado); nunca desativa módulo (isso é do BKO de licenças, com RN-CORE-02). Admin com o mesmo e-mail no tenant:
   mantido, **senha intacta**, salvo `--redefinir-senha`.
5. **Senha**: só pela variável `MACUXI_TENANT_ADMIN_SENHA` (no `.env` ou na linha do `docker compose run -e`) ou digitada com eco
   desligado; **nunca** em argumento (fica no histórico e na lista de processos). Política `validarSenhaInicial` do Core
   (≥ 8 caracteres, diferente do e-mail). O hash argon2id é feito no Node (`hashSenha` de `modules/core/api/seguranca.ts`); ao banco
   só vai o hash. Nada de senha, hash ou e-mail em claro na saída nem no log: a saída mostra o e-mail mascarado (`a***@dominio`).
6. **Auditoria**: uma linha `plataforma.auditoria` `tenant.provisionar` no tenant novo (ator nulo = operação da plataforma), com os
   módulos e o resultado; sem dado pessoal (`antes`/`depois` sem e-mail).

## 3. Uso
```
MACUXI_TENANT_ADMIN_SENHA=... pnpm tenant:criar --codigo distribuidora-x --nome "Distribuidora X" [--documento 00000000000000] \
  [--fuso America/Manaus] [--plano piloto] --modulos core,catalogo,vendedor[,promotor,...] [--licencas vendedor=20,promotor=5] \
  --admin-email admin@x.com.br --admin-nome "Fulana" [--redefinir-senha] [--simular]
```
Saída (stdout, uma linha JSON): `{ tenant_id, codigo, resultado: 'criado'|'atualizado'|'sem_mudanca', modulos_adicionados: [...],
admin: 'criado'|'existente'|'senha_redefinida', admin_email: 'a***@x.com.br', avisos: [...] }`. `--simular` valida e mostra o plano
sem gravar (transação com rollback). Código de saída ≠ 0 em erro, mensagem em português.
Trava de ambiente: fora do Postgres local, exige `--confirmar <codigo>` (evita criar tenant em produção por engano de `.env`).

## 5. Migração (banco-dados) — `plataforma.provisionar_tenant(p jsonb) returns jsonb`
Entrada: `{ codigo, nome, documento, fuso, plano, modulos: [{ modulo, licencas, perfis: [...] }], admin: { email, nome, senha_hash },
redefinir_senha }`. Faz o §2 itens 1, 4 e 6 numa chamada: `insert ... on conflict (lower(codigo)) do nothing`; `tenant_modulo` e
`perfil_modulo` com `on conflict do nothing` pelos índices únicos que já existem; admin por `(tenant_id, lower(email))`
(`usuario_email_uk`); confere o formato do hash (o check `usuario_senha_argon2id` já existe). Devolve o resumo do §3.
`SECURITY INVOKER`, `search_path` fixo, `revoke all from public`, **sem grant** ao `macuxi_app` e ao `macuxi_worker` (teste: 42501).
Sem log de comando na transação, como em `garantirPapel` (`db/src/papeis.ts`), porque leva o hash. Down: `drop function`.
Por que função e não SQL no TS: atomicidade e a mesma porta para a futura tela do operador.

  licenças, parâmetros e auditoria; com o token de A, nada de N; `tenant_por_codigo` só devolve o próprio.

# T-0143 — Desenho: recados direto no GitHub, sem sincronização pelo PC

- **Decisão:** [ADR 0039](../decisoes/0039-recados-direto-no-github.md) (altera a [ADR 0035](../decisoes/0035-recados-em-repositorio-proprio.md) §2, §4 e a volta).
- **Patch de governança:** [T-0143.patch](T-0143.patch), aplicável com `git apply` sobre o `main` (9d097404). Os arquivos são do dono do produto; o gerente aplica com `Agente: alexandre`, pelo rito de governança.
- **Módulos, contratos, eventos, sync e banco:** nenhum. A mudança é só de coordenação, guardião e CI.

## Caminho escolhido
**API do GitHub (GraphQL `createCommitOnBranch` com `expectedHeadOid` para gravar; REST `compare` + GraphQL em lote para ler), chamada pelo `fetch` do Node, com o token do ambiente ou do `gh`.**

Por quê:
- **Atômico e sem sobrescrever** numa chamada: um commit com todos os destinos, só se o `main` ainda estiver no commit que o `coord` leu. A Contents API faria um commit por arquivo (sem atomicidade), e a Git Data API, 4 ou 5 chamadas.
- **Concorrência resolvida no servidor**: 7 agentes, o formulário e o Telegram gravam no mesmo `main` sem `index.lock`, rebase nem clone compartilhado.
- **Igual no PC, na nuvem e no CI**: só HTTPS para `api.github.com` com um token. Sem clone, sem credencial de git, sem `gh` obrigatório.
- O clone com commit e push síncronos foi descartado: disputa do clone entre 7 processos, `pull` antes de cada leitura e nenhuma saída para a nuvem (ADR 0039, alternativas).

## Fluxos

### `enviar` (modo github)
1. Valida os argumentos e a autoria (`regraDoRecadoNovo`, `--de alexandre` só na sessão dele), como antes.
2. Atualiza o índice (`compare` desde o commit do cache, mais os blobs novos). **Exige o GitHub**: sem ele, sai 1 com "recado NÃO enviado (nada foi gravado): sem acesso ao GitHub (...)".
3. Confere `--responde-a` e escolhe o id livre contra aquele commit.
4. `createCommitOnBranch` com `expectedHeadOid` = o commit lido, título `recados: <id>`, corpo `de X para Y`.
5. O `main` mudou: o GitHub recusa; o `coord` relê e volta ao passo 2 (até 6 vezes).
6. Resposta perdida: confere o arquivo no topo pelo hash do git. É o nosso: "confirmado na conferência". Não respondeu: "NÃO foi confirmado ... confira com `ler <id>`".
7. Só então imprime `Recado <id> enviado para ... (GitHub aloirr/macuxifdv-recados@abc1234)`.

### `lido`
Lê `lidos/<agente>.txt` no topo (uma consulta, com o commit), acrescenta só os ids que faltam e grava com `expectedHeadOid`. Recusado: relê e regrava. Nenhuma linha de outro processo se perde, e marcar de novo não grava nada.

### `caixa`, `pendencias`, `ler`, `fio`
Índice do `main` na hora: sem mudança, 1 chamada; com mudança, 2 ou 3. Sem GitHub, a cópia local com a linha "Atenção: sem o GitHub agora ...". Os textos do cache valem só se o hash do git bater.

### Guarda do merge
`lerRecadosDoGerente` lista `recados/gerente-projetos` direto do GitHub (nunca do cache) e baixa só `R-...-alexandre.md`. Texto do cache só com o hash certo. Sem GitHub: nenhuma autorização.

## Concorrência (critério 2)
- Escrita: concorrência otimista no servidor (`expectedHeadOid`). Não há trava no PC.
- Teste com processos de verdade: 4 agentes enviando e 3 `lido` no mesmo arquivo ao mesmo tempo, contra o servidor de mentira que recusa como o GitHub. Resultado: 7 commits, nenhum recado e nenhuma linha perdidos.
- O `merge=union` do `.gitattributes` continua no repositório de recados. Não é mais necessário para o `coord`, mas protege quem ainda usar git (a volta).

## PC, nuvem e CI (critério 4)
| Ambiente | Token | HTTP |
|---|---|---|
| PC | `gh auth token` (já logado) ou `MACUXI_RECADOS_TOKEN` de usuário (recomendado: fine-grained, só este repositório, e 1 a 5 s mais rápido) | worker thread |
| Nuvem (claude.ai/code) | `MACUXI_RECADOS_TOKEN` nas variáveis do ambiente | processo filho com `NODE_USE_ENV_PROXY=1` (proxy da sessão) |
| CI | `MACUXI_RECADOS_TOKEN` dos secrets, só no passo que precisar | worker thread |

Sem token: "sem token do GitHub: no PC, entre no gh (gh auth login); na nuvem e no CI, defina MACUXI_RECADOS_TOKEN (...)". Na nuvem sem token, continua valendo a seção "Recados para o time" no corpo do PR.

## Corte (passo a passo para o gerente, com o ok do dono do produto)
1. **Conferir a árvore local.** O patch é contra o `main` (9d097404), e `git apply --check docs/desenho/T-0143.patch` passa no índice e também na árvore de hoje (conferido em 09/11 às 13h). Mas a árvore local está atrás do `main` em `.claude/`: o guardião v7 da T-0122 não está no disco (`guarda-mcp*.mjs` apagados, `settings.json` e `guarda-merge-lib.mjs` antigos). Recomendo alinhar antes (`git restore --source=HEAD -- .claude .github/workflows/carga-t0107.yml`), se o dono do produto confirmar que essas diferenças não são dele.
2. Pausar os agentes locais (o fim da rodada basta).
3. `git apply docs/desenho/T-0143.patch`. Daqui em diante, todo `coord.mjs` do PC grava e lê no GitHub.
4. `node scripts/recados/subir-pendentes.mjs --simular` e, se o plano estiver certo, `node scripts/recados/subir-pendentes.mjs`. Saída 0 = tudo no GitHub; 1 = conflito listado (nada sobrescrito; comparar à mão).
5. Junções e clone (PowerShell, nunca `Remove-Item -Recurse` na junção):
   ```powershell
   cmd /c rmdir C:\macuxifdv\.coord\recados
   cmd /c rmdir C:\macuxifdv\.coord\lidos
   Rename-Item C:\macuxifdv-recados C:\macuxifdv-recados-arquivo-20261109
   powershell -File C:\macuxifdv\scripts\recados\agendar-sincronizacao.ps1 -Remover   # se a tarefa existir
   ```
6. Conferir: `node scripts/coord.mjs caixa gerente-projetos` (sem "Atenção"), um `enviar` de teste ao próprio gerente e o `lido` dele.
7. Commit com `Agente: alexandre` no branch de verificação, CI verde, depois o `main` (rito de governança). O CI roda os 19 testes novos.
8. Gerente: doc 07 (§ recados: escrita direta, sem Agendador; nuvem com `MACUXI_RECADOS_TOKEN`), `CLAUDE.md` (bloco "Recados no repositório próprio") e quadro.
9. Opcional, do dono do produto: criar o token fine-grained e a variável de usuário `MACUXI_RECADOS_TOKEN` no PC e nas variáveis do ambiente da nuvem.

| # | Decisão |

| P1 A | Cliente inadimplente vai para aprovação **mesmo no pagamento à vista** (muda a RN-VEN-13). |
| P2 B | Dois parâmetros: "Quem aprova crédito" e "Quem aprova inadimplência". |

## 1. O motivo `inadimplencia` nos contratos
- **Domínio:** `MOTIVOS_APROVACAO` (`modules/vendedor/domain/aprovacao.ts`) passa a `['desconto', 'credito', 'inadimplencia', 'estoque', 'preco_minimo']`. O dono do contrato é o **modulo-vendedor**; o Gestor só lê.
- **Evento novo:** `vendedor.pedido.aprovacao_solicitada@2`.
  - Precisa de versão nova porque o `@1` tem `motivos` como enum fechado. Leitura tolerante não aceita valor novo de enum, então um consumidor do `@1` lançaria erro e o evento pararia na outbox (é o alerta OUTBOX_PARADA).
  - Payload do `@2`: o `@1` mais `aprovacoes: [{ motivo, nivel, texto }]` (uma por motivo). O `credito` passa a vir preenchido (`CreditoClienteEvento`, hoje sempre `null`) e entra `inadimplencia: { maior_atraso_dias, vencidos_cents } | null`.
  - O `nivel` da raiz continua sendo o **maior** nível entre as aprovações pendentes, para quem só precisa de um número.
- **Evento novo:** `vendedor.pedido.aprovacao_decidida@1` = `{ pedido_id, vendedor_id, ciclo, motivo, decisao: 'aprovada'|'rejeitada'|'devolvida'|'encerrada', autor_id, decidida_em, texto }`. Sai um por aprovação que muda de estado. O Gestor usa esse evento para a projeção da tela Aprovações.
- **Troca do `@1` para o `@2`:** o servidor publica só o `@2`, a partir do deploy da v1.0.15.
  - Os consumidores atuais do `@1`, o Core (`consumidorPedidoParaAprovar`, notificação) e o Gestor (projeção `aprovacoes`), ganham um consumidor do `@2` **no mesmo lote**.
  - Os consumidores do `@1` ficam para o histórico que ainda está na outbox.
  - O registro vai em `.coord/contratos/eventos.md`. A mudança é incompatível, então está na **[ADR 0062](../decisoes/0062-aprovacao-do-pedido-por-motivo.md)**.
- **Sem mudança:** `status_alterado@1` e `aprovado@1`. O `cancelado` já existe no `STATUS_CONTRATO`.

## 2. Modelo: uma aprovação por motivo
Tabela nova, no schema do Vendedor: **`vendedor.pedido_aprovacao`**.
- **Colunas padrão:** `id`, `tenant_id`, `created_at`, `updated_at`, `deleted_at` e `external_id`, com RLS.
- **Colunas próprias:**
  - `pedido_id` (FK para `vendedor.pedido`);
  - `ciclo int`: começa em 1 e cresce a cada reenvio depois de uma devolução;
  - `motivo` (check com os `MOTIVOS_APROVACAO`);
  - `nivel` (`supervisor` | `gerente` | `analista`);
  - `estado` (`pendente` | `aprovada` | `rejeitada` | `devolvida` | `encerrada`);
  - `texto_pendencia`, `decidida_por`, `decidida_em`, `texto_decisao`.
- **Chave única:** `(tenant_id, pedido_id, ciclo, motivo)`. Índice para a fila do aprovador: `(tenant_id, estado, nivel) where estado = 'pendente'`.
- **`vendedor.pedido` continua como resumo:**
  - `motivos_aprovacao` ganha `inadimplencia` (o check muda);
  - `nivel_aprovacao` passa a ser o maior nível pendente. A constraint `pedido_pendente_com_nivel` segue valendo e o app v1.0.13 continua lendo.
- **Regras** (domínio puro, modulo-vendedor, teste antes):
  - **Entrar em aprovação:** no recebimento (`receber.ts`) o servidor calcula os motivos (§5) e cria uma linha `pendente` por motivo, no ciclo atual. O pedido vai a `pending_approval`.
  - **Aprovar:** a linha vira `aprovada`. O pedido vai a `approved` quando todas as linhas do ciclo estão `aprovada` (P7).
  - **Rejeitar:** a linha vira `rejeitada` e as outras pendentes viram `encerrada` (P8). O pedido vai a `cancelled`, que é final.
  - **Devolver:** a linha vira `devolvida` e as outras pendentes viram `encerrada`. O pedido vai a `rejected`. O reenvio pelo vendedor abre um ciclo novo e o servidor recalcula todos os motivos.
  - **Concorrência:** cada decisão trava a linha do pedido com `for update`. Repetir a mesma decisão devolve `repetida`, sem efeito (idempotente).

## 3. As decisões do aprovador e a permissão
- **Rotas** (Vendedor, ação `pedido.aprovar`, a mesma de hoje):
  - `POST /v1/vendedor/pedidos/:id/aprovar` com o corpo `{ motivo? }`;
  - `POST .../rejeitar` com `{ texto, motivo? }`, que **continua levando a `rejected`** e passa a ser a **Devolver ao vendedor**. Assim o app Gestão v1.0.13 segue funcionando com o sentido que ele já mostra;
  - `POST .../recusar` com `{ texto, motivo? }`, **rota nova**, leva a `cancelled`. É o botão **Rejeitar** das telas novas (P6).
  - Texto obrigatório na devolução e na recusa, com mínimo de `MOTIVO_REJEICAO_MIN` (RN-GES-08).
- **Sem `motivo` no corpo** (app antigo ou "aprovar tudo"): a decisão vale para todas as aprovações pendentes que o usuário pode decidir.
  - Se sobrar alguma que ele não pode decidir, aprovar fica parcial e devolve 200 com as pendentes que restam.
  - Para recusar ou devolver, basta uma aprovação que ele possa decidir (P8).
- **Quem pode:** `decidirAprovacao` passa a receber a aprovação, não o pedido.
  - Pode quem tem nível igual ou acima do nível da linha (`quemDecide`, como hoje).
  - O promotor continua recusado (RN-PRO-01, 403).
  - A decisão `recusar` entra no tipo (`'aprovar' | 'devolver' | 'recusar'`).
  - A transição `pending_approval → cancelled` entra na tabela da RN-VEN-30.
- **Auditoria:** `pedido.aprovacao_decidida`, só com ids, motivo e decisão. O texto vai na linha da aprovação, não no log.

## 4. Parâmetros › Pedidos (#412)
- **Onde ficam:** `plataforma.parametro` do módulo `vendedor`, lidos por `ctx.parametros()` como as alçadas:
  - `aprovacao.credito_nivel`;
  - `aprovacao.inadimplencia_nivel`.
- **Valores e padrão:** `supervisor` | `gerente` | `analista`. **Padrão `gerente`** (P5), inclusive quando o parâmetro está ausente ou inválido.
- **Prazo do atraso:** o limite de atraso (padrão 5 dias, RN-VEN-13) continua no parâmetro existente, lido por `tituloVencidoDias`.
- **Função pura:** `niveisDosParametros(p)` no domínio, ao lado de `politicaDosParametros`.
- **Leitura:** `GET /v1/vendedor/alcadas` passa a devolver `aprovador_credito` e `aprovador_inadimplencia`, campos aditivos. O app usa a mesma política offline.
- **Tela:** BKO › Parâmetros › Pedidos, no bloco das Alçadas (`modules/vendedor/web/pages/alcadas-page.tsx`), conforme a prancha `01-bko-parametros-pedidos`.

## 5. De onde vem o crédito (RN-VEN-12) e a inadimplência (RN-VEN-13)
- **Fonte:** o ERP pela Integração (`integracao.cliente.atualizado@1`, `limite_credito_cents`) vai ao Core (`cliente_financeiro` e `titulo`). O Vendedor lê pela consulta `core.financeiro_cliente@1`, que já está no `usaConsultas` dele. Nada novo no BKO, e não há limite configurável.
- **Crédito disponível:** `(credito_disponivel_erp_cents ?? limite_cents − saldo_aberto_cents)` menos os pedidos do cliente em `approved`, `sent_to_erp` ou `integrated` ainda não faturados. A soma é feita pelo Vendedor, na mesma transação.
- **Motivos:**
  - `credito`: só a prazo, quando o disponível é **menor** que o total do pedido. Igual ao total passa, então um centavo a menos já vai para aprovação.
  - `credito` também quando não há limite informado (P4): `financeiro: null` ou limite não informado.
  - `inadimplencia`: `maior_atraso_dias` acima do parâmetro, **com qualquer forma de pagamento** (P1). O `exigeAprovacaoPorVencido` (`domain/pagamento.ts:140`), que hoje exige prazo médio maior que 0, deixa de olhar o prazo. Isso vale também para o alerta `vencidosComEfeito` e para a tela de novo pedido.
  - `desconto`: segue as alçadas (RN-VEN-10 e RN-VEN-11a).
- **Limite não informado:** hoje o `limite_cents` da consulta é `int` não nulo. Se o Core gravar 0 quando o ERP não manda o limite, "sem limite" e "limite zero" se confundem. **Pedido ao modulo-core:** campo aditivo `limite_informado: boolean` (opcional, compatível com o `@1`). Sem o campo, o Vendedor trata `financeiro: null` como sem limite.
- **Offline e revalidação:** o app calcula os mesmos motivos com o financeiro do pull e avisa "vai para aprovação". **Quem decide é o servidor**, ao receber o pedido: a lista de motivos do servidor prevalece. Não há perda nem envio em dobro, pela idempotência do `receber` (RN-VEN-33).

## 7. Contratos e schema exatos (cada dono trabalha sem perguntar)
### 7.1 `modules/vendedor/contracts` (modulo-vendedor)
- **Domínio, reexportado pelo contracts:**
  - `MOTIVOS_APROVACAO = ['desconto', 'credito', 'inadimplencia', 'estoque', 'preco_minimo']`;
  - `ESTADOS_APROVACAO_MOTIVO = ['pendente', 'aprovada', 'rejeitada', 'devolvida', 'encerrada']`;
  - `DECISOES_APROVADOR = ['aprovar', 'devolver', 'recusar']`.
- **`AprovacaoMotivo`:** `{ motivo, nivel, estado, texto_pendencia: string, decidida_por_id: uuid|null, decidida_em: iso|null, texto_decisao: string|null }`.
- **Detalhe do pedido** (`GET pedidos/:id` e a linha da tabela do BKO): campo aditivo `aprovacoes: AprovacaoMotivo[]`, só as do ciclo atual. Vem vazio se o pedido nunca foi para aprovação.
- **Corpos das rotas:**
  - `aprovar`: `{ motivo?: MotivoAprovacao }`;
  - `rejeitar` (devolver ao vendedor): `{ texto: string ≥ 3, motivo? }`;
  - `recusar`: `{ texto: string ≥ 3, motivo? }`.
  - **Resposta:** `{ status, aprovacoes: AprovacaoMotivo[] }`.
- **`AlcadaApi`:** campos aditivos `aprovador_credito: NivelAprovacao` e `aprovador_inadimplencia: NivelAprovacao`.
- **Eventos** em `contracts/eventos.ts`:
  - `AprovacaoSolicitadaEventoV2`, que é o `@1` com o enum novo, mais `aprovacoes: [{ motivo, nivel, texto }]` e mais `inadimplencia: { maior_atraso_dias: int ≥ 0, vencidos_cents: int ≥ 0 } | null`. Exporta `EVENTO_PEDIDO_APROVACAO_SOLICITADA_V2 = definirEvento('vendedor.pedido.aprovacao_solicitada@2', …)`.
  - `AprovacaoDecididaEvento = { pedido_id, vendedor_id, ciclo: int ≥ 1, motivo, decisao: 'aprovada'|'rejeitada'|'devolvida'|'encerrada', autor_id: uuid|null, decidida_em, texto: string|null }`. Exporta `EVENTO_PEDIDO_APROVACAO_DECIDIDA = definirEvento('vendedor.pedido.aprovacao_decidida@1', …)`.
  - No `encerrada`, o `autor_id` é o de quem rejeitou ou devolveu.
- **Manifesto:** `publica` ganha os dois eventos novos. O `@1` sai do `publica` só depois que os consumidores migrarem; no mesmo lote, ele fica na lista.

### 7.2 `modules/gestor/contracts` (modulo-gestor)
- **`base.ts`:** `MotivoAprovacao` ganha `inadimplencia`.
- **`aprovacao.ts`:**
  - `DECISOES_APROVACAO = ['aprovar', 'devolver', 'rejeitar']`. O `devolver` chama a rota `rejeitar` do Vendedor; o `rejeitar` chama a rota `recusar`.
  - O comentário obrigatório (RN-GES-08) vale para `devolver` e `rejeitar`.

  - `ItemFilaAprovacao` ganha `aprovacoes: { motivo, nivel, estado, pode_decidir: boolean }[]` e `inadimplencia: { maior_atraso_dias, vencidos_cents } | null`.

### 7.3 Banco (banco-dados, S5): uma migração

  id uuid primary key,
  tenant_id uuid not null references plataforma.tenant(id),

# Desenho T-0174 — Fotos dos produtos em lote por ZIP

- **Autor**: engenheiro-software · 2026-11-15 (Manaus) · decisão: [ADR 0054](../decisoes/0054-fotos-em-lote-por-zip.md)
- **Regras**: RN-CAT-14 (lote), RN-CAT-04 (quem consulta e quem enriquece), RN-CORE-02/05 (licença e isolamento).
- **Requisito**: RF-CAT-07.
- **Decidido pelo dono do produto (R-20261115-074500, 8h05 de Manaus)**: JPEG, PNG e WEBP, com decodificadores em JS puro
  (ADR 0036); o nome do arquivo também pode ser o EAN (código exato → código sem diferenciar maiúsculas → EAN); galeria no
  app na 2ª etapa (agora grava todas as fotos com ordem; o app segue só com a foto de ordem 1).

## 0. Fluxo em uma tela

```
BKO                      API (plataforma)                API (catalogo)                 worker
POST fotos-lote ─────────────────────────────────────▶ cria lote aguardando_envio
                                                        + tx.registrarArquivo(zip)
PUT arquivos/:z/partes/1..n ─▶ grava parte (8 MiB)
POST arquivos/:z/concluir ───▶ confere partes → recebido
POST fotos-lote/:id/enfileirar ──────────────────────▶ lote enfileirado
                                                        + publica foto_lote.enfileirado@1
                                                                                         despachante → plataforma.trabalho
                                                                                         laço de trabalhos → executarFatia
                                                                                           1ª fatia: conferência (SHA, diretório,
                                                                                           itens pendentes) · depois: itens
                                                                                           fim: concluido@1, apaga as partes
GET fotos-lote/:id (a cada 2 s) · GET itens · GET relatorio.csv
```

## 1. Contratos

### 1.1 Plataforma (`packages/platform-sdk`) — dono: engenheiro-software

`src/arquivos.ts`
- `TIPOS_ARQUIVO = ['image/jpeg', 'image/png', 'image/webp', 'application/zip'] as const` (o `TipoArquivo` acompanha).
  A rota antiga `PUT /v1/arquivos/:id` continua só JPEG até 2 MB; PNG e WEBP entram só pelo trabalho (foto do lote).
- `EXTENSAO_POR_TIPO = { 'image/jpeg': 'jpg', 'image/png': 'png', 'image/webp': 'webp' }` (chave do original).
- `PARTE_ENVIO_BYTES = 8 * 1024 * 1024`; `PARTES_ENVIO_MAX = 63` (63 × 8 MiB ≥ 500 MB).
- `ConcluirEnvioSchema = z.object({ partes: z.number().int().min(1).max(PARTES_ENVIO_MAX), tamanho_bytes: z.number().int().positive() }).strict()`.
- `UrlEnvioSchema = z.object({ url: z.string().url(), metodo: z.literal('PUT'), expira_em: z.string().datetime() }).strict()`.
- `CODIGOS_ARQUIVO` ganha `parteInvalida: 'PARTE_INVALIDA'` (400), `envioIncompleto: 'ENVIO_INCOMPLETO'` (409),
  `urlAssinadaDesligada: 'URL_ASSINADA_DESLIGADA'` (404).
- `InfoArquivo = { id; tipo: TipoArquivo; situacao: 'aguardando' | 'recebido'; tamanho_bytes: number | null; entidade; entidade_id; enviado_por }`.

`src/imagens.ts` (novo)
- `TIPOS_IMAGEM = ['image/jpeg', 'image/png', 'image/webp'] as const`; `TipoImagem`.
- `detectarTipoImagem(cabeca: Uint8Array): TipoImagem | null` — JPEG `FF D8 FF`, PNG `89 50 4E 47 0D 0A 1A 0A`,
  WEBP `RIFF....WEBP`. Só reconhece; aceitar é decisão do chamador.
- `dimensoesImagem(bytes, tipo): { largura; altura } | null` — sem decodificar: JPEG (SOF, `dimensoesJpeg`), PNG (IHDR),
  WEBP (`VP8 `, `VP8L` ou `VP8X`). O decodificador confere o teto de 30 MP **antes** de alocar os pixels.

`src/zip.ts` (novo, funções puras)
- `LimitesZip = { bytesZipMax; arquivosMax; bytesEntradaMax; razaoMax; bytesDescompactadosMax }`;
  `LIMITES_ZIP_TETO = { bytesZipMax: 500 MiB, arquivosMax: 10_000, bytesEntradaMax: 8 MiB, razaoMax: 20, bytesDescompactadosMax: 1 GiB }`;
  `ENTRADAS_BRUTAS_MAX = 20_000`.
- `MOTIVOS_RECUSA_ZIP = ['zip_grande', 'muitos_arquivos', 'descompactado_grande', 'zip_invalido', 'zip64_nao_suportado', 'zip_incompleto'] as const`.
- `MOTIVOS_RECUSA_ENTRADA = ['caminho_invalido', 'criptografado', 'compressao_nao_suportada', 'arquivo_vazio', 'foto_grande', 'compressao_suspeita', 'entrada_corrompida', 'tipo_nao_aceito', 'foto_ilegivel'] as const`.
- `EntradaZip = { indice: number; caminho: string; pasta: boolean; metodo: number; criptografada: boolean; compactado: number; descompactado: number; crc32: number }`
  (`caminho` decodificado: UTF-8 com o bit 11, senão CP437; normalizado NFC).
- `classificarEntradaZip(e, limites): { acao: 'ignorar' } | { acao: 'recusar'; motivo: MotivoRecusaEntrada } | { acao: 'aceitar'; nomeBase: string }`, nesta ordem:
  1. `\` → `/`; começa com `/`, `^[A-Za-z]:`, ou algum segmento `..` → `recusar caminho_invalido`;
  2. pasta, segmento `__MACOSX`, segmento começando com `.`, nome-base `Thumbs.db`/`desktop.ini` (sem diferenciar maiúsculas) → `ignorar`;
  3. caractere de controle no nome → `recusar caminho_invalido`;
  4. criptografada → `criptografado`; método ∉ {0, 8} → `compressao_nao_suportada`;
  5. `descompactado === 0` → `arquivo_vazio`; `> bytesEntradaMax` ou `compactado > bytesEntradaMax + FOLGA_COMPACTADO_BYTES` (64 KiB; A-T0174-1) → `foto_grande`; `descompactado / max(compactado, 1) > razaoMax` → `compressao_suspeita`;
  6. senão `aceitar` com o nome-base (último segmento).

### 1.2 Rotas da plataforma (`apps/api/src/arquivos.ts`) — dono: engenheiro-software

| Rota | Corpo / resposta | Regras |
|---|---|---|
| `PUT /v1/arquivos/:id/partes/:n` | `application/octet-stream`, ≤ `PARTE_ENVIO_BYTES` → `200 { n, tamanho_bytes }` | sessão antes do corpo (`onRequest`); linha `application/zip`, `aguardando`, `enviado_por` = usuário (senão 409 `ARQUIVO_SEM_REFERENCIA`/404); licença do módulo da linha (403); `n` de 1 a `PARTES_ENVIO_MAX` (400 `PARTE_INVALIDA`); corpo > 8 MiB → 413; reenviar a mesma parte sobrescreve (idempotente) |
| `GET /v1/arquivos/:id/partes/:n/url-envio` | `200 UrlEnvioSchema` | mesmas regras; só com driver `s3` e `MACUXI_ENVIO_URL_ASSINADA=1`, senão 404 `URL_ASSINADA_DESLIGADA`; validade 900 s |
| `POST /v1/arquivos/:id/concluir` | `ConcluirEnvioSchema` → `200 InfoArquivo` | `tamanho(chave)` de cada parte: 1 a n−1 com exatamente 8 MiB, a última de 1 a 8 MiB, soma = `tamanho_bytes` (senão 409 `ENVIO_INCOMPLETO` com `detalhes.partes_faltando`); soma acima do teto da categoria → 413 com `codigo` da RN (`TETO_POR_CATEGORIA` ganha `catalogo/foto_lote` = 500 MiB, `RN-CAT-14`); marca `recebido`, `tamanho_bytes`; repetir com tudo igual → 200 |
| `GET /v1/arquivos/:id` e `/miniatura` | — | `application/zip` → 404 (o ZIP nunca é servido) |

Chaves no armazenamento: partes do ZIP em `<tenant>/<modulo>/<aaaa-mm>/<id>.p<NNN>.zip`; original da foto em
`<id>.jpg|.png|.webp` (pela `EXTENSAO_POR_TIPO`); miniatura sempre `<id>.m320.jpg` (o `CHAVE_ARQUIVO_RE` ganha os formatos).
O `GET /v1/arquivos/:id` responde com o `content-type` do `tipo` da linha. A porta `ArmazenamentoArquivos` ganha `tamanho(chave): Promise<number | null>` (disco: `stat`;
S3: `HEAD`) e, no S3, `urlEnvio(chave, validadeS)` (PUT pré-assinado).

## 2. Banco (`db/`) — dono: banco-dados

Migração nova `0070_catalogo_foto_lote` (up/down), RLS ligado e forçado com a política padrão de tenant em toda tabela
nova, `updated_at` pelo trigger `plataforma.definir_updated_at`, grants do `macuxi_app` como nas tabelas do Catálogo.

**`plataforma.arquivo`**
- `arquivo_tipo_valido`: `tipo in ('image/jpeg', 'image/png', 'image/webp', 'application/zip')`.
- `arquivo_tamanho_faixa`: `tamanho_bytes is null or (tipo in ('image/jpeg', 'image/png', 'image/webp') and tamanho_bytes between 1 and 8388608) or (tipo = 'application/zip' and tamanho_bytes between 1 and 524288000)`.
  (A rota antiga continua só JPEG e 2 MB no código; só a foto do lote chega a 8 MB e a PNG/WEBP.)
- `arquivo_recebido_completo`: o ZIP vira `recebido` no `concluir` **sem** `sha256` (o SHA é calculado no trabalho e fica no
  lote): `situacao <> 'recebido' or (recebido_em is not null and tamanho_bytes is not null and chave_armazenamento is not null
  and (sha256 is not null or tipo = 'application/zip'))`. A `chave_armazenamento` do ZIP é a da parte 1 (`<id>.p001.zip`),
  gravada na 1ª parte recebida; as outras saem dela.

**`plataforma.trabalho`** (novo)
`id uuid pk, tenant_id uuid not null fk tenant, modulo text, nome text, alvo_id uuid, evento_id uuid,
situacao text check in ('pendente','em_execucao','concluido','falhou'), tentativas int default 0, fatias int default 0,
proxima_em timestamptz default now(), travado_ate timestamptz, travado_por text, ultimo_erro text (só código, ≤ 100),
concluido_em timestamptz` + colunas padrão.
- Único `(tenant_id, modulo, nome, alvo_id) where deleted_at is null`; índice `(situacao, proxima_em)`.
- `macuxi_app`: `insert ... on conflict do nothing` e `select` do próprio tenant (o consumidor da plataforma roda em `comTenant`).
- Funções `SECURITY DEFINER` (dono migrador, `EXECUTE` só para `macuxi_worker`), só tenants `ativo`:
  - `plataforma.trabalho_reservar(p_processo text, p_trava_s int) returns table(id, tenant_id, modulo, nome, alvo_id, tentativas, fatias)` —
    um por chamada, `(situacao = 'pendente' and proxima_em <= now()) or (situacao = 'em_execucao' and travado_ate < now())`,
    `order by proxima_em`, `for update skip locked`; marca `em_execucao`, `travado_ate = now() + p_trava_s`, `travado_por`.
  - `plataforma.trabalho_devolver(p_id uuid, p_processo text, p_resultado text, p_erro text, p_espera_s int) returns boolean`
    (`false` = a trava não é mais deste processo; nada muda) — `continua` → `pendente`, `fatias + 1`, `proxima_em = now()`;
    `concluido` → `concluido`; `adiar` (módulo sem licença no tenant) → `pendente` daqui a `p_espera_s`, sem contar tentativa;
    `erro` → `tentativas + 1`, `ultimo_erro = p_erro` (só código), `pendente` daqui a `p_espera_s` ou, com `p_espera_s` nulo,
    `falhou` (o worker decide o fim pelas `TENTATIVAS_TRABALHO_MAX` do SDK). Sempre limpa a trava.
  - `plataforma.trabalho_renovar(p_id uuid, p_processo text, p_trava_s int) returns boolean`.

## 3. Catálogo (`modules/catalogo/**`) — dono: modulo-catalogo

### 3.1 `domain/fotos-lote.ts` (puro, teste antes, cada teste cita RN-CAT-14)
- `limitesFotoLote(parametros): LimitesZip` — `min(parâmetro, teto)`; `razaoMax` e `bytesDescompactadosMax` do SDK.
- `interpretarNome(nomeBase): { ok: true; interpretacoes: { codigo: string; ordem: number }[] } | { ok: false; motivo: 'nome_invalido' }` —
  tira a última extensão; código de 1 a 100 caracteres. Sempre `{ codigo: radical, ordem: 1 }`; se o radical termina em
  `_N` (N de 1 a 99), soma `{ codigo: radical sem _N, ordem: N }`. Ex.: `A1_2.jpg` → `[A1_2/1, A1/2]`.
- `casarCodigo(codigo, produtos)` — em três passos, e o primeiro que acha decide: exato (`sku === codigo`) → 1 produto;
  senão `lower(sku) === lower(codigo)` → 1 = casou, ≥ 2 = `ambiguo` com os códigos; senão `ean === codigo` → 1 = casou,
  ≥ 2 = `ambiguo`; 0 = nada. A consulta `core.produtos_por_sku@1` já devolve os candidatos dos três passos.
- `resolverItem(interpretacoes, produtos): { situacao: 'ligar'; produto; ordem } | { situacao: 'sem_produto' } | { situacao: 'ambiguo'; codigos }` —
  nenhuma casa → `sem_produto`; uma casa → liga; alguma ambígua ou mais de uma interpretação casa (ex.: existem `CX` e
  `CX_12`, arquivo `CX_12.jpg`) → `ambiguo`.
- `csvRelatorioFotos(itens, rotulos): string` — `BOM_CSV` + `celulaCsv` de `@macuxi/comum` (anti-fórmula `=`, `+`, `-`, `@`,
  tab, CR), `;`, CRLF; colunas: Arquivo · Resultado · Motivo · Código no nome · Produto · Ordem. Rótulos pt-BR do
  designer-ux em `contracts` (`ROTULO_SITUACAO_ITEM`, `ROTULO_MOTIVO_ITEM`).

### 3.2 `api/miniatura.ts` — função única
```ts
export interface FotoNaOrdem { id: string; ordem: number; arquivoId?: string | null; url?: string | null; titulo?: string | null; hashConteudo?: string | null }

export async function definirFotosProduto(t: { db: ClienteSql; publicar: TransacaoTenant['publicar'] }, tenantId: string, produtoId: string,
  fotos: readonly FotoNaOrdem[], origem: OrigemFoto): Promise<ResultadoFoto[]>;
export async function removerFotosProduto(t, tenantId, produtoId, ordens: readonly number[]): Promise<void>;
```
- Por foto: `hashConteudo` igual a uma viva do produto → `repetida` (nada muda, mesmo em outra ordem); senão aposenta a
  viva da mesma ordem (`foto.removida@1`, `substituida`), insere com `principal = (ordem === 1)` (`foto.definida@1`).
  Um `tocarConteudoPelaMidia` no fim se algo mudou. `definirFotoPrincipal`/`removerFotoPrincipal` delegam (ordem 1,
  `origem: 'ficha'`) e passam a receber `{ db, publicar }`; o teste que trava escrita direta em `produto_midia` fora do
  arquivo continua.
- Quem grava fotos chama `esquecerRetratoCatalogo(tenant)` como hoje.

### 3.3 `api/fotos-lote.ts` (rotas da §1.3) e `api/trabalho-fotos-lote.ts` (`definirTrabalho`)
`processar_foto_lote`, `disparadoPor: EVENTO_FOTO_LOTE_ENFILEIRADO`, `alvo: p => p.lote_id`:
1. **Conferência** (lote `enfileirado`): `abrirZip(arquivo_id, limitesFotoLote(ctx.parametros()))`; recusado → lote
   `recusado` + motivo, `concluido@1`, `descartar`. Com o SHA: outro lote vivo com o mesmo SHA → `duplicado`,
   `duplicado_de`, `concluido@1`, `descartar`. Senão, numa transação: `sha256`, `total`, `iniciado_em`, situação
   `processando` e um `foto_lote_item` por entrada não ignorada (`insert ... on conflict (tenant_id, lote_id, indice) do nothing`),
   com `arquivo_id`/`midia_id` novos; entrada `recusar` já nasce `recusado` com o motivo; `aceitar` com nome inválido →
   `recusado nome_invalido`. (`muitos_arquivos`, `descompactado_grande`, `zip_grande`, ZIP64 e ZIP inválido/incompleto já
   chegam como recusa de `abrirZip`: a plataforma conta os considerados e soma os declarados antes de devolver o ZIP.)
   Cada fatia abre o ZIP de novo (o temporário do processo é reaproveitado) e chama `zip.fechar()` no fim.
2. **Itens** (lote `processando`): pega até 100 `pendente` por `indice`; uma `consultar(CONSULTA_PRODUTOS_POR_SKU)` com os
   códigos de todas as interpretações; para cada item, até `deveParar()`:
   `resolverItem` → `sem_produto`/`ambiguo` gravam direto; `ligar` → `zip.ler(indice, { tipos: TIPOS_FOTO_LOTE })`
   (recusa → `recusado` + motivo + `tipo_detectado`) → `hash` já vivo no produto → `repetido` (sem gravar bytes) →
   `guardarImagem({ id: item.arquivo_id, bytes, tipo })` (fora da transação; `foto_ilegivel` → `recusado`) → transação:
   `registrarArquivo({ id: item.arquivo_id, finalidade: 'foto_produto', entidade: 'produto', entidade_id: produto,
   cliente_id: null, tipo, enviado_por: lote.enviado_por, recebido })` +
   `definirFotosProduto(..., [{ id: item.midia_id, ordem, arquivoId, hashConteudo }], { tipo: 'lote', loteId })` +
   `update foto_lote_item set situacao = 'ligado' | 'repetido' ... where id = $1 and situacao = 'pendente'`.
   Violação do único `ordem_repetida_no_lote` → `recusado ordem_repetida_no_lote`; violação do único de hash → `repetido`.
3. **Fim**: nenhum `pendente` → `concluido`, `concluido_em`, `concluido@1` com os totais; depois do commit, `descartar`.
4. `aoFalhar` → `falhou` + `concluido@1`.

Manifesto: `publica` + 4 eventos; `consome` + `catalogo.foto_lote.enfileirado@1`; `usaConsultas` + `core.produtos_por_sku@1`.

### 3.4 `web/` — página **Catálogo → Fotos em lote** (`web/pages/fotos-lote`)

## 7. Pendências e premissas
- **Premissas aceitas pelo gerente (15/11)**: código do produto = `core.produto.sku` (ou o EAN); produto inativo também
  casa (só o removido fica de fora); `SKU_1` vale como ordem 1 (repete `SKU` → `ordem_repetida_no_lote`); a foto nova da
  mesma ordem **substitui** a anterior; existindo `CX` e `CX_12`, o arquivo `CX_12.jpg` é **ambíguo**; reenviar o mesmo
  ZIP sobe de novo, mas não reprocessa (`duplicado`). Demais: a foto da ficha não tem `hash_conteudo` (não vira repetido
  do lote); limites são parâmetros do tenant que só baixam o teto; o original PNG/WEBP fica guardado como veio, e a
  miniatura é sempre JPEG.
- **Infra (engenheiro-software/engenheiro-apps)**: confirmar que o `/api-proxy` do BKO aceita 8 MiB por pedido
  (`proxyClientMaxBodySize` do Next, padrão 10 MB) e que o túnel aceita pedidos de alguns minutos; o worker precisa de
  ~600 MB livres no temporário.

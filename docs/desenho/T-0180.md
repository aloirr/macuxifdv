# T-0180 — desenho técnico: alertas de produtividade e Parâmetros › Alertas (v1.0.13)

Autor: engenheiro-software, 15/11/2026 (Manaus). Decisões: ADR 0059. Tarefa: `.coord/tarefas/T-0180.md` (D1 a D6).

## 1. Fluxo dos dados (sem ler tabela de outro módulo)
```
Campo (offline)  ── pull `parametro` (core) ──> alertas.produtividade + inicio.parado_min + almoço do usuário ──> lembretes locais
Aparelho ── GET /v1/sync/novidades | POST /v1/sync/push ──> API (plataforma) ── contatoDoAparelho(ctx core) ──> core.usuario_contato
BKO Parâmetros › Alertas ── GET|PUT /v1/core/parametros/alertas-produtividade (JSON alertas) ──> plataforma.parametro (core)
                         ── GET|PUT /v1/core/parametros/parado-min (só inicio.parado_min) ─────> plataforma.parametro (core)
                         ── PUT /v1/gestor/parametros/alertas (regras da equipe, sem permanência) ─> plataforma.parametro (gestor)
GET /v1/gestor/alertas?produtividade=1 ── tx.consultar(core.produtividade_equipe@1, { usuario_ids }) ──> avaliarAlertas(produtividade, contatos, parado_min, almoço)
                                       ── reconciliarAlertas (chave produtividade:<usuario_id>) ──> gestor.alerta (alerta_vivo_uk)
```

## 3. Testes que fecham a tarefa
- Gestor (domain): a chave dos dois tipos é a mesma; "sem check-in" aberto e depois "parado" = encerra um e abre o outro; contato
  anterior ao checkout não abre; o "parado" desconta o almoço (intervalo antes, durante e atravessando o almoço); sem
  `produtividade` nada abre; regra desligada encerra (`regra_inativa`).
- Gestor (API): sem `produtividade=1` a lista omite os tipos novos; `PUT alertas/regras/parado_entre_visitas` é recusado antes do banco.
- Core: contrato da consulta (entrada estrita, 1 a 500 ids, ids de outro tenant somem), padrão D6 com chave ausente ou inválida, PUT
  idempotente e auditado, `inicio.parado_min` gravado só pelo `PUT parametros/parado-min` (o PUT do Início não o grava);
  `contatoDoAparelho` não anda o `updated_at` do usuário.
- Banco: `core.usuario_contato` com RLS (B não vê A) e o upsert com trava.

## 4. Ordem de merge
banco-dados (a migração dos alertas (#395), com `usuario_contato`) → Core → Gestor. Este branch (SDK/API) é independente e pode entrar primeiro:
sem o Core declarar o gancho, nada muda.

Depois do merge deste branch, o Core troca o spread isolado (`...({ contatoDoAparelho: ... } satisfies Record<string, unknown>)`,
`modules/core/api/index.ts`) pela propriedade tipada `contatoDoAparelho: registrarContatoDoAparelho`; o spread passa no typecheck
com qualquer assinatura. Antes deste branch no `main`, a API não chama o gancho: `core.usuario_contato` fica vazia, o
`ultimo_contato_em` vem nulo e nenhum alerta de produtividade abre (a condição de contato do §5 da ADR segura).

## 5. Compatibilidade com os apps instalados (revisão final, rodada 2)
- Pull `parametro`: saem `produtividade.almoco_corte` e `produtividade.almoco_janela` e entram `jornada.almoco_padrao` e
  `alertas.produtividade`. O Campo e o Gestão até a v1.0.12 não quebram: a linha é `{modulo, chave, valor}` com `valor` JSON
  livre, e a Produtividade local (`performance-local.ts`) trata chave ausente ou inválida como padrão. A linha antiga já guardada
  no aparelho fica como estava (o pull só deixa de mandá-la); a conta local do aparelho antigo pode divergir da do servidor no
  almoço até a atualização, sem erro.
- `usuario` no pull: `almoco_inicio_min` e `almoco_fim_min` são aditivos (padrão nulo); a migração dos alertas (#395) não anda o `updated_at`, então
  ninguém puxa de novo por causa dela.
- `PUT /v1/core/parametros/inicio` estrito sem `parado_min`: rota só do BKO (`superficie: 'bko'`), nenhum app chama. Aba do BKO
  aberta antes do deploy recebe 400 até recarregar.
- `GET /v1/core/usuarios` com `almoco_padrao` opcional: só o BKO lê.
- `GET /v1/gestor/alertas`: sem `produtividade=1` os tipos novos não vêm (ADR 0059 §1). O BKO (`modules/gestor/web/lib/queries.ts`)
  e o Gestão v1.0.13 (`modules/gestor/app/lib/cache.ts`) precisam pedir com `produtividade=1`; sem isso os alertas abrem no banco
  e ninguém os vê.

## 6. Decisões do gerente-projetos depois da rodada 2 (15/11/2026)
- **`GET /v1/core/parametros/parado-min`** (Core, ação `parametro.alertas_produtividade`, mesmo público do PUT): devolve
  `{ parado_min }` (`ParametroParadoMinSchema`; chave ausente ou inválida = padrão 60). A tela Parâmetros › Alertas do BKO lê o
  "parado" por essa rota, não pelo `GET /v1/core/parametros/inicio` (que continua devolvendo o valor só para o Gestão já instalado).
- **O "Parado entre visitas" vale com ou sem rota do dia**, no lembrete do Campo e no alerta do Gestor: o que conta é o último
  checkout e o contato do aparelho (ADR 0059 §5), não haver roteiro planejado. Mesma regra nos dois lados (RN-CORE-26).
- **BKO e Gestão v1.0.13 pedem `GET /v1/gestor/alertas?produtividade=1`** (`modules/gestor/web/lib/queries.ts` e
  `modules/gestor/app/lib/cache.ts`); sem o parâmetro os tipos novos ficam de fora (§5 e ADR 0059 §1).

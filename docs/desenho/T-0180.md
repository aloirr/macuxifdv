Autor: engenheiro-software, 15/11/2026 (Manaus). Decisões: ADR 0059. Tarefa: `.coord/tarefas/T-0180.md` (D1 a D6).

## 1. Fluxo dos dados (sem ler tabela de outro módulo)
```
Campo (offline)  ── pull `parametro` (core) ──> alertas.produtividade + inicio.parado_min + almoço do usuário ──> lembretes locais
Aparelho ── GET /v1/sync/novidades | POST /v1/sync/push ──> API (plataforma) ── contatoDoAparelho(ctx core) ──> core.usuario_contato
BKO Parâmetros › Alertas ── PUT /v1/core/parametros/alertas-produtividade (parado_min + alertas) ──> plataforma.parametro (core)
                         ── PUT /v1/gestor/parametros/alertas (regras da equipe) ──────────────> plataforma.parametro (gestor)
                         ── rota do Promotor (permanência mínima, RN-PRO-07) ───────────────────> plataforma.parametro (promotor)
GET /v1/gestor/alertas?produtividade=1 ── tx.consultar(core.produtividade_equipe@1, { usuario_ids }) ──> avaliarAlertas(produtividade, contatos, parado_min)
                                       ── reconciliarAlertas (chave produtividade:<usuario_id>) ──> gestor.alerta (alerta_vivo_uk)
```

## 3. Testes que fecham a tarefa
- Gestor (domain): a chave dos dois tipos é a mesma; "sem check-in" aberto e depois "parado" = encerra um e abre o outro; contato
  anterior ao checkout não abre; sem `produtividade` nada abre; regra desligada encerra (`regra_inativa`).
- Gestor (API): sem `produtividade=1` a lista omite os tipos novos; `PUT alertas/regras/parado_entre_visitas` é recusado antes do banco.
- Core: contrato da consulta (entrada estrita, ids de outro tenant somem), padrão D6 com chave ausente ou inválida, PUT idempotente
  e auditado, `inicio.parado_min` gravado pelo PUT novo; `contatoDoAparelho` não anda o `updated_at` do usuário.
- Banco: `core.usuario_contato` com RLS (B não vê A) e o upsert com trava.

## 4. Ordem de merge
banco-dados (0085 e `usuario_contato`) → Core → Promotor → Gestor. Este branch (SDK/API) é independente e pode entrar primeiro:
sem o Core declarar o gancho, nada muda.

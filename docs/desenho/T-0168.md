# T-0168 — Limite de desconto por item e por pedido (RN-VEN-11a): desenho técnico

Origem: R-20261112-080845 (dono do produto); v1.0.5 (R-20261112-121131). Regras: RN-VEN-03, RN-VEN-10, RN-VEN-11, **RN-VEN-11a**.
Implementação só depois da aprovação da simulação (`docs/design/telas/T-0168-campo.html`). Os textos finais são os da simulação aprovada.

## 1. Onde mora o dado (core.usuario)

Três colunas novas em `core.usuario` (dono do schema: banco-dados; migração seguinte à 0062):

| Coluna | Tipo | Padrão | Regra |
|---|---|---|---|
| `desconto_limita_item` | `boolean not null` | `true` | "Limitar desconto por item" (RN-VEN-11 ligada) |
| `desconto_limita_pedido` | `boolean not null` | `false` | "Limitar desconto por pedido" |
| `desconto_maximo_pedido_permil` | `integer null` | `null` | décimos de % (‰): 8,0% = 80; 7,5% = 75; faixa 0..1000 |

- **Nome com `_permil`, não `_pct`** (premissa do engenheiro): no repositório `_pct` é sempre % decimal (`desconto_maximo_pct` do produto = 15). Um `_pct` com 80 para 8% vira defeito. O valor é o pedido pelo gerente (inteiro em décimos de %).
- Constraints: `usuario_desconto_pedido_permil_faixa check (desconto_maximo_pedido_permil is null or desconto_maximo_pedido_permil between 0 and 1000)` e `usuario_desconto_pedido_com_limite check (not desconto_limita_pedido or desconto_maximo_pedido_permil is not null)`.
- `add column ... not null default` preenche quem já existe sem reescrever a tabela (PG ≥ 11): todo usuário antigo fica "por item" ligada e "por pedido" desligada, o comportamento de hoje.
- Desligar "por pedido" **mantém** o número gravado (religar devolve o valor).
- O `updated_at` já sobe pelo gatilho `usuario_updated_at` (o sync puxa a linha de novo).
- **Carga do ERP e CSV da Equipe não tocam nas 3 colunas**: o upsert do `integracao.vendedor.atualizado@1` no Core e a importação por CSV só gravam os campos que já gravam; usuário novo nasce com o padrão.
- Seed da demo: sem mudança (padrão).

## 2. Contratos (Zod)

### 2.1 Core — campos comuns (`modules/core/contracts/usuarios.ts`, dono modulo-core)

```ts
/** RN-VEN-11a (T-0168): funções e limite de desconto do usuário. Décimos de % (‰): 8,0% = 80. */
export const DESCONTO_PEDIDO_PERMIL_MAX = 1000;
export const LimiteDescontoSchema = z
  .object({
    desconto_limita_item: z.boolean(),
    desconto_limita_pedido: z.boolean(),
    desconto_maximo_pedido_permil: z.number().int().min(0).max(DESCONTO_PEDIDO_PERMIL_MAX).nullable(),
  })
  .strict();
export type LimiteDesconto = z.infer<typeof LimiteDescontoSchema>;
/** Padrão de usuário novo, de usuário antigo e de quem não recebeu os campos (servidor/APK antigo). */
export const LIMITE_DESCONTO_PADRAO: LimiteDesconto = { desconto_limita_item: true, desconto_limita_pedido: false, desconto_maximo_pedido_permil: null };
/** "Por pedido" ligada exige o número. */
export function limiteDescontoCompleto(l: LimiteDesconto): boolean {
  return !l.desconto_limita_pedido || l.desconto_maximo_pedido_permil !== null;
}
```

Um só lugar para o padrão: a vendedor/domain importa `LIMITE_DESCONTO_PADRAO` e o tipo daqui (`@macuxi/core/contracts`).

### 2.2 Core — BKO do usuário (mesmo arquivo)

- `UsuarioItemSchema` ganha os 3 campos **obrigatórios** (o servidor sempre lê das colunas `not null`): `...LimiteDescontoSchema.shape`.
- `CriarUsuarioRequestSchema` ganha os 3 **opcionais com padrão** (`.default(true)`, `.default(false)`, `.default(null)`), com `superRefine(limiteDescontoCompleto)`.
- `EditarUsuarioRequestSchema` ganha os 3 **opcionais** (ausente = mantém). O servidor junta com o gravado e confere `limiteDescontoCompleto`.
- Recusa: 422 `USUARIO_DADOS_INVALIDOS` (código que já existe), `mensagem` "Informe o desconto máximo do pedido.", `detalhes.campo = 'desconto_maximo_pedido_permil'`. Sem código novo.
- Rotas: as de hoje, `POST /v1/core/usuarios` e `PUT /v1/core/usuarios/:id`, com a ação `usuario.editar` de hoje (sem ação nova; premissa). Auditoria (RN-AUD-01): os 3 campos entram no antes/depois.
- Tela: aba **Parâmetros** do perfil do usuário com as duas funções e "Desconto máximo do pedido (%)" (1 casa). O web converte % ↔ ‰ (`Math.round(pct × 10)` / `permil ÷ 10`); a API só fala ‰.

### 2.3 Core — usuário no sync (`modules/core/contracts/sync.ts`, entidade nova `usuario`)

Hoje não há entidade de usuário no sync. Entra a entidade **`usuario`** (pull, `servidor_vence`, escopo `usuarios`), só com o que o aparelho precisa (sem nome, e-mail nem senha):

```ts
/** RN-VEN-11a (T-0168): funções e limite de desconto. O app usa a linha do usuário da sessão; sem linha = LIMITE_DESCONTO_PADRAO. */
export const UsuarioSyncSchema = z
  .object({
    ...Base,
    desconto_limita_item: z.boolean().default(true),
    desconto_limita_pedido: z.boolean().default(false),
    desconto_maximo_pedido_permil: z.number().int().min(0).max(1000).nullable().default(null),
  })
  .strict();
export type UsuarioSync = z.infer<typeof UsuarioSyncSchema>;
```

- Compatível: entidade nova (APK antigo não pede); campos futuros entram opcionais com padrão, na mesma versão.
- Provedor (`modules/core/api/sync.ts`): `tabela` = subconsulta de `core.usuario` com `id as usuario_id` para o filtro `colunaUsuario: 'usuario_id'`; `colunas` = só as 3. O vendedor recebe a própria linha; o gestor recebe a dele e a da equipe visível (só flags). **A linha do próprio usuário tem de vir sempre** (conferir que `usuariosVisiveis()` inclui o próprio id; teste).
- `manifest.sync += 'usuario'` no Core; registro no `app/index.ts` do Core (vale para Campo e Gestão).

### 2.4 Core — consulta para a API do Vendedor (`core.cadastro_resumo@1`, aditivo, mesma versão)

`CadastroResumoSaida.usuarios[]` ganha os 3 campos **opcionais** (`LimiteDescontoSchema.partial().shape`). Emissor antigo sem os campos continua válido; o consumidor completa com `LIMITE_DESCONTO_PADRAO`. O `receber` do Vendedor já pede o autor em `usuario_ids` (`[eu]` ou `[eu, donoId]`).

### 2.5 Vendedor — código de recusa (`modules/vendedor/contracts/index.ts`, dono modulo-vendedor)

## 3. Domínio (`modules/vendedor/domain/limite-desconto.ts`, dono modulo-vendedor)

Funções puras, com teste antes, citando RN-VEN-11a:

```ts
import { LIMITE_DESCONTO_PADRAO, type LimiteDesconto } from '@macuxi/core/contracts';
export const CODIGO_DESCONTO_PEDIDO_ACIMA_LIMITE = 'desconto_pedido_acima_limite';

/** Ausente, parcial ou inconsistente (servidor/APK antigo) → padrão campo a campo; "por pedido" sem número = desligada. */
export function limiteDoUsuario(u: Partial<LimiteDesconto> | null | undefined): LimiteDesconto;
/** "Por item" desligada: o item não tem mínimo (RN-VEN-11 não vale). Ligada: o mínimo do produto de hoje. */
export function minimoDoItem(minimo_base_cents: number | null, l: LimiteDesconto): number | null;
/**
 * v2 (R-20261112-183709, decisão 5): o desconto do pedido em décimos de % (‰) EXATAMENTE como a linha "Desconto (%)" dos
 * Totais mostra (`linhasDosTotais` → `pctExibicao(total_tabela − total, total_tabela)`, 1 casa, metade para cima), em
 * inteiro. `pctExibicao` passa a ser `permilDoDescontoExibido(...) / 10` (uma fórmula só). Acréscimo (total > tabela) → ≤ 0.
 */
export function permilDoDescontoExibido(t: { total_tabela_cents: number; total_cents: number }): number;
/** v2: trava pelo VALOR EXIBIDO. ‰ exibido > limite ‰ (inteiros; sem float). ≤ 0 (acréscimo) nunca trava. */
export function pedidoAcimaDoLimite(desconto_exibido_permil: number, l: LimiteDesconto): boolean;
// = l.desconto_limita_pedido && l.desconto_maximo_pedido_permil !== null && exibido > 0 && exibido > l.desconto_maximo_pedido_permil
/** Frase única aprovada (RD-0196), igual no Campo, no Gestão, na API, no detalhe e na lista: "Pedido acima do desconto máximo (8,0%)". */
export function mensagemPedidoAcimaDoLimite(permil: number): string;

export type TravaDesconto =
  | { codigo: 'preco_abaixo_minimo'; skus: string[] }
  | { codigo: 'desconto_pedido_acima_limite'; limite_permil: number };
/** RN-VEN-11/11a + RN-VEN-10: travas primeiro; com trava, sem alçada (nível nulo, sem linha de alçada). Orçamento nunca trava. */
export function decisaoDoDesconto(e: {
  tipo: 'pedido' | 'orcamento';
  limite: LimiteDesconto;
  /** skus que furam o mínimo do produto (`itemRespeitaPrecoMinimo`), calculados SEM olhar a função */
  skus_acima_do_maximo: readonly string[];
  /** RN-VEN-10: a ALÇADA continua pelo valor nominal exato */
  desconto_efetivo_alcada_pct: number;
  /** RN-VEN-11a v2: a TRAVA do limite pelo valor exibido (`permilDoDescontoExibido`) */
  desconto_exibido_permil: number;
  policy: DiscountPolicy;
  vendedor_id: string;
}): { travas: TravaDesconto[]; nivel: NivelDePreco | null; pode_enviar: boolean };
```

Ordem: orçamento → `{ travas: [], nivel: null, pode_enviar: true }`. Pedido → travas na ordem item, pedido. Com trava: `nivel = null`, `pode_enviar = false`. Sem trava: `nivel = nivelDeAprovacao(...)` (RN-VEN-10). O bloqueio de `alcada.acima_gerente = bloquear` segue no `bloqueadoPelaAlcada`/`validateOrder` de hoje.

**Comparação da trava (v2, 13/11, decisão do dono do produto R-20261112-183709, item 5; substitui a premissa "valor exato" da v1):**
- A trava do limite do pedido compara o **valor exibido, com 1 casa**: 8,04% aparece "8,0%" e **não** trava num limite de 8,0%; 8,05% aparece "8,1%" e trava.
- "Valor exibido" = o número da linha **"Desconto (%)"** dos Totais (Resumo, detalhe, PDF), que é `pctExibicao(total_tabela_cents − total_cents, total_tabela_cents)`. A trava usa **o mesmo cálculo, com as mesmas entradas**, por `permilDoDescontoExibido` (inteiro). Assim a tela e a trava nunca discordam: o vendedor vê "8,0%" ao lado de "(8,0%)" e envia.
- **Não** usar `permilExibido(desconto_efetivo_alcada_pct)` (arredondar o valor nominal da alçada): o nominal e os Totais em centavos podem diferir por arredondamento da linha. Exemplo a testar: 1 item de R$ 10,00 com desconto de 8,05% no item; se a linha fecha em R$ 9,20, a tela mostra "Desconto (%) 8,0%" e a trava **não** pode disparar, embora o nominal seja 8,05%.
- Em inteiros (‰), nunca `pct × 10` em float (1,1 × 10 = 11,000000000000002).
- A **alçada** (RN-VEN-10) **não muda**: continua pelo valor nominal exato, sem folga. Um pedido com 8,04% e limite 8,0% envia e vai para a aprovação do supervisor (casos 5 e 5b).

## 4. Quem chama

> **v2 (13/11):** nos dois canais, a trava recebe `permilDoDescontoExibido({ total_tabela_cents, total_cents })` dos mesmos totais que alimentam `linhasDosTotais` (app: `calcularPedido`; API: `totaisDoPedido` no `revalidarPedido`). A alçada segue com `desconto_efetivo_alcada_pct`. A frase é a única aprovada, sem "do vendedor"/"do gestor".

- **App (offline), modulo-vendedor**: `lerLinhas` lê `usuario` e pega a linha do usuário da sessão (`limiteDoUsuario`). `calcularPedido` (`app/lib/novo-pedido.ts`) usa `minimoDoItem` no lugar do mínimo direto e `decisaoDoDesconto` no fim: pendência `desconto_pedido_acima_limite` (alvo `pedido`) na área Alertas (RN-VEN-42), `botoes-resumo` trata como "só orçamento" (como o `itens_acima_do_maximo`), `motivoDaRecusa`/`abaDaCorrecao` reconhecem o código (aba Resumo). No Gestão o usuário da sessão é o gestor: o limite é o dele sem código extra.
- **API, modulo-vendedor**: `revalidarPedido` ganha `tipo` e `limite?: LimiteDesconto` (ausente = padrão). Item: `preco_minimo_base_cents` passa por `minimoDoItem`. Pedido: depois de `totaisDoPedido` e **antes** do `validateOrder`, `pedidoAcimaDoLimite` → `{ ok: false, codigo: 'desconto_pedido_acima_limite', http: 422, mensagem }`. O `receber` (`calcularDocumento`) passa o limite do **autor** (`ctx.usuario.id`, linha de `cad.usuarios` da `core.cadastro_resumo@1`). Vale no envio, na correção do pedido e no **Transformar** (pedido com `orcamento_origem_id`); a edição do orçamento (`orcamentos.ts`, `tipo = 'orcamento'`) não trava.
- **Conferir junto (modulo-vendedor)**: hoje o `calcularDocumento` monta o mínimo do item também para `tipo = 'orcamento'`, então o `revalidarPedido` parece recusar `preco_abaixo_minimo` num orçamento, contra a RN-VEN-11 ("só Salvar como orçamento"). Escrever o teste; se recusa, a mesma mudança (`tipo`) corrige.
- **Gestor, modulo-gestor**: pedido em nome usa o limite do autor (app: usuário da sessão; API: `ctx.usuario.id`). Conferir que o Gestão sincroniza `usuario` e testar os casos 19–20 no fluxo da ficha.
- **Detalhe e lista**: a frase vem da recusa gravada (`mensagem`), como a da RN-VEN-11; o app recalcula para o orçamento aberto com a própria linha.

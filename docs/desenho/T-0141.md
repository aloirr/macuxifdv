# Desenho T-0141 item C — Endereço de entrega editável só no pedido (RN-VEN-17)

- **Autor**: engenheiro-software · **Data**: 2026-11-09 · **Tarefa**: T-0141 (item C)
- **Origem**: decisão do dono do produto R-20261109-054659 item 3; RN-VEN-17 reescrita pelo gerente em 09/11
  (`docs/produto/03-regras-de-negocio.md`). Tela: `docs/design/pedido-v3.md` §C (designer-ux; a implementação espera a
  aprovação da imagem pelo dono do produto, critério 2 da tarefa). Este desenho não depende da imagem.
- **Resumo da decisão**: o retrato do endereço no pedido **já existe ponta a ponta** (T-0061). Falta o vendedor poder
  mandar um endereço digitado e o retrato dizer de onde veio (`origem: 'erp' | 'editado'`). **Tudo aditivo**: nenhum
  contrato muda de versão e não há ADR nova.

## 1. Como está hoje (conferido no código em 09/11)
| Ponto | Onde | O que faz |

| Regra | `modules/vendedor/domain/preco-pedido.ts` (`resolverEnderecoEntrega`) | sem escolha = principal; escolha tem de ser endereço ativo do cliente, senão `endereco_invalido` |
| Gravação | `modules/vendedor/api/receber.ts` (passo 4b) e `api/orcamentos.ts` (edição) | grava `endereco_entrega_id` e o **retrato** `endereco_entrega` (jsonb) do endereço do Core no aceite |
| Banco | `db/migrations/0013_catalogo_vendedor_prevenda.up.sql` | `vendedor.pedido.endereco_entrega_id uuid` (sem FK, fronteira) e `endereco_entrega jsonb` (check: objeto) |
| Pull | `contracts/sync.ts` (`PedidoSyncSchema.endereco_entrega: record`) | o retrato desce inteiro ao aparelho |
| Detalhe e PDF | `contracts/frete.ts` (`EnderecoRetrato`), `api/mapeamento.ts` (`enderecoDoPedido` → `delivery_address`) | Campo, Gestão, BKO e PDFs leem o retrato |
| Evento | `contracts/eventos.ts` (`EnderecoEntregaEvento` em `vendedor.pedido.aprovado@1`), `api/aprovado-erp.ts` | o retrato vai ao Hub |

Conclusão: **não precisa de coluna nova**. O retrato jsonb já é "o endereço do pedido"; ele só passa a poder nascer do
que o vendedor digitou.

## 2. Contrato do endereço do pedido (dono: modulo-vendedor, `modules/vendedor/contracts/frete.ts`)
O UF e o CEP vêm do `@macuxi/comum/endereco` (novo, engenheiro-software, já entregue: `UFS_BRASIL`, `ehUf`,
`normalizarCep`, `cepValido`, `formatarCep`, com testes RN-VEN-17), para que contrato, domain, Core e tela usem a mesma lista.

```ts
import { UFS_BRASIL } from '@macuxi/comum/endereco';

/** RN-VEN-17: limites do endereço DIGITADO no pedido = limites da NF-e (tag entrega) e cabem no EnderecoEntregaErp do Hub. */
export const LIMITES_ENDERECO_PEDIDO = { logradouro: 60, numero: 20, complemento: 60, bairro: 60, cidade: 60 } as const;
export const ORIGENS_ENDERECO_PEDIDO = ['erp', 'editado'] as const;
export type OrigemEnderecoPedido = (typeof ORIGENS_ENDERECO_PEDIDO)[number];

/** Endereço que o vendedor digitou SÓ para este pedido (RN-VEN-17). Não muda o cadastro do cliente. */
export const EnderecoEditadoPedido = z
  .object({
    logradouro: z.string().trim().min(2).max(60),
    numero: z.string().trim().min(1).max(20),          // aceita "S/N"
    complemento: z.string().trim().max(60).nullable().optional(),
    bairro: z.string().trim().min(2).max(60),
    cidade: z.string().trim().min(2).max(60),
    uf: z.enum(UFS_BRASIL),                              // o aparelho manda em maiúscula
    cep: z.string().regex(/^\d{8}$/),                    // só dígitos; a máscara 00000-000 é da tela
  })
  .strict();

/** Retrato gravado em vendedor.pedido.endereco_entrega (jsonb): o EnderecoRetrato de hoje + a origem. */
export const EnderecoEntregaPedido = EnderecoRetrato.extend({
  /** ausente = 'erp' (linhas e eventos anteriores à T-0141) */
  origem: z.enum(ORIGENS_ENDERECO_PEDIDO).optional(),
});
```

**Por que esses limites** (e não os da spec do designer, 60/10/40/40/40): o endereço de entrega vai para a NF-e (tag
`entrega`: logradouro, número, complemento, bairro e município até 60) e tem de caber no `EnderecoEntregaErp` do Hub
(160/20/80/80/80). O número fica em 20 (limite do Hub; "S/N", "1234-A", "KM 12"). A spec do designer diz que o contrato
prevalece; aviso enviado ao designer-ux para alinhar a tabela de C.3. O endereço que **vem do ERP** não é revalidado
(entra como veio, como hoje); só o digitado passa por estes limites.

### 2.1 Retrato por origem
| Campo do retrato | `origem: 'erp'` (escolhido da lista) | `origem: 'editado'` (digitado) |
|---|---|---|
| `id` | id do `core.cliente_endereco` | `null` |
| `external_id` | o do ERP | `null` (não existe no ERP) |
| `tipo`, `descricao` | do Core | ausente / `null` |
| `logradouro … cep` | do Core | o digitado, normalizado (§3) |
| `principal` | do Core | `false` |
| coluna `endereco_entrega_id` | o id escolhido | `null` |

## 3. Regra no domain (dono: modulo-vendedor, `modules/vendedor/domain/`, teste antes citando RN-VEN-17)
Funções puras, as mesmas no formulário do app (C.3) e na API (que sempre revalida):
1. `normalizarEnderecoEditado(e)`: `trim` e espaços repetidos viram um; `uf` em maiúscula; `cep` só dígitos
   (`normalizarCep`); complemento vazio vira `null`.
2. `validarEnderecoEditado(e)` → `null` ou `{ codigo: 'endereco_invalido', campos: [...] }` com os campos com erro
   (obrigatório, tamanho, `cepValido`, `ehUf`). A tela usa `campos` para a borda e o texto ("Obrigatório", "CEP com 8
   números"); a API usa só o código. **Sem o conteúdo do endereço em log nem na mensagem** (pode ser de pessoa física).
3. `enderecoDoPedido({ editado, escolhido_id, enderecos })` → `{ ok, retrato, endereco_id }`:
   - com `editado` (não nulo): valida; se for **igual** (campos normalizados, sem diferenciar maiúscula) a um endereço
     ativo do cliente, vira `origem: 'erp'` daquele endereço (não marca "Editado neste pedido" à toa e, sendo o principal,
     não exige Conector 1.3.0); senão `origem: 'editado'`. Com `editado`, o `escolhido_id` **é ignorado** e nunca recusa:
     o pedido feito offline não cai porque o endereço do ERP que serviu de base foi desativado depois;
   - sem `editado`: exatamente o `resolverEnderecoEntrega` de hoje, com `origem: 'erp'`.

## 4. Push, API e sync (dono: modulo-vendedor)
- **`PedidoPush`** ganha `endereco_entrega_editado: EnderecoEditadoPedido.nullable().optional()` (aditivo). Ausente ou
  nulo = comportamento de hoje (o aparelho que ainda manda só o id continua igual). `EditarOrcamentoRequest` herda.
- **Receber** (`api/receber.ts`, passo 4b), **edição do orçamento** (`api/orcamentos.ts`) e **Transformar**: trocam
  `resolverEnderecoEntrega` por `enderecoDoPedido`; gravam o retrato (§2.1) e a coluna. Recusa com o código de hoje,
  `endereco_invalido` (já em `CODIGOS_RECUSA_PEDIDO`; 422 nas rotas diretas), mensagem: "Endereço de entrega
  incompleto. Confira CEP, rua, número, bairro, cidade e UF." (a do designer, se ele propuser outra).
- **Transformar orçamento em pedido**: sem endereço no corpo, o pedido herda o retrato do orçamento (editado continua
  editado). **Editar** reabre com o retrato. **Duplicar** copia o retrato (o vendedor troca se quiser) — premissa, §9.
- **Rascunho e fila no aparelho** (RN-VEN-38/39): o endereço editado mora no rascunho e na fila como os outros campos
  do pedido; offline funciona igual (sem busca de CEP, premissa do designer).
- **Pull**: `PedidoSyncSchema.endereco_entrega` continua `record` (sem mudança); o app lê com
  `EnderecoEntregaPedido.safeParse` e trata `origem` ausente como `'erp'`.
- **Detalhe** (`Order.delivery_address`): passa a `EnderecoEntregaPedido` (aditivo); `enderecoDoPedido` em
  `api/mapeamento.ts` devolve `origem` (`'editado'` só quando o retrato diz; senão `'erp'`). Campo, Gestão e BKO mostram o
  selo "Editado neste pedido" (`docs/design/pedido-v3.md` §C.4).
- **PDFs** (pedido e orçamento, app e BKO): "Endereço de entrega:" com o retrato, **sem marca** de editado (§C.4).

## 5. Evento e devolução ao ERP
- **`vendedor.pedido.aprovado@1`** (modulo-vendedor, `contracts/eventos.ts`): `EnderecoEntregaEvento` ganha
  `origem: z.enum(['erp', 'editado']).optional()` (aditivo, mesma versão). `api/aprovado-erp.ts` copia do retrato
  (ausente → `'erp'`); no editado vão `external_id: null` e `principal: false`. Registro atualizado em
  `.coord/contratos/eventos.md`.
- **Hub** (modulo-integracao, `modules/integracao/contracts/pedido.ts`): `EnderecoEntregaErp` ganha
  `origem: z.enum(['erp', 'editado']).nullish()` (aditivo no `v1`, `VERSAO_CONTRATO` não muda). `domain/pedido-fila.ts`
  já repassa o objeto; conferir que o schema tolerante do consumo não descarta `origem`. `exigeConector` **não muda**: o
  editado tem `principal: false`, logo já exige o Conector ≥ 1.3.0 (o 1.2.x descartaria o endereço; o pedido espera
  na fila, como hoje). OpenAPI (`docs/openapi-hub-v1.json`), `guia-api-hub.md`, exemplo e coleção Postman ganham o
  campo e um exemplo de endereço editado; doc 06, linha "Pedidos aprovados", cita o endereço editado (pedido ao gerente).
- **Regra para o SQL do Conector no ERP** (guia do Conector, modulo-integracao): **`endereco_entrega.external_id` nulo =
  usar os campos de texto** (logradouro, número, complemento, bairro, cidade, UF, CEP). A regra se apoia no
  `external_id`, não em `origem`, de propósito: o Conector 1.3.x já instalado não conhece `origem` (descarta o campo) mas
  recebe os textos e o `external_id` nulo. O SQL que só usa o `external_id` levaria a entrega para o principal **sem
  avisar**: a implantação confere isso no roteiro do Conector.

## 6. Banco (dono: banco-dados)
**Sem coluna nova.** Migração pequena (próximo número livre) só de defesa:
- `pedido_endereco_entrega_origem`: `endereco_entrega is null or coalesce(endereco_entrega->>'origem', 'erp') in ('erp', 'editado')`;
- `pedido_endereco_editado_sem_id`: `coalesce(endereco_entrega->>'origem', 'erp') <> 'editado' or endereco_entrega_id is null`;
- `.down.sql` que as remove; `docs/banco/vendedor.md` com o formato do retrato (§2.1);
- seed demo: um pedido aprovado com endereço editado (e2e do testes, PDF e devolução).
Linhas antigas sem `origem` continuam válidas (= `'erp'`); sem migração de dados.

## 7. Compatibilidade
| Aparelho | API | Resultado |
|---|---|---|
| APK atual (manda só o id) | nova | igual a hoje; retrato com `origem: 'erp'` |
| APK novo com endereço editado | nova | retrato `origem: 'editado'` |
| APK novo com endereço editado | **antiga** | o `PedidoPush` não é `strict`: a API antiga **descarta** o campo e grava o endereço do id — perda calada. **Ordem obrigatória: API e migração no ar antes de distribuir o APK** (regra do build; o gerente confere no roteiro do Campo-Demo) |
| — | Conector 1.2.x | editado = não principal → pedido espera na fila até o 1.3.0 (ADR 0016, sem mudança) |
| — | Conector 1.3.x sem `origem` | recebe os textos com `external_id` nulo; o SQL do ERP segue a regra do §5 |
| Consumidores do `aprovado@1` | — | tolerantes (`.coord/contratos/eventos.md`): campo novo opcional não quebra |

**Versões**: `PedidoPush` (sem versão, aditivo) · `vendedor.pedido.aprovado@1` (continua @1) · contrato do Hub `v1`
(continua) · `PedidoSyncSchema` (sem mudança). Nenhuma mudança incompatível → **sem ADR** (regra 3 do CLAUDE.md).

## 8. Testes (critérios para o testes e para a revisão final)
1. Domain (modulo-vendedor, RN-VEN-17): normalização; cada campo obrigatório e cada limite; CEP 7/9 dígitos e zeros;
   UF inexistente; editado igual ao principal → `erp`; editado com id de endereço desativado → aceito como `editado`.
2. API: push com editado grava retrato e coluna nula; push só com id (APK atual) igual a hoje; editado inválido → recusa
   `endereco_invalido` sem o endereço no log; Transformar herda; Editar reabre; Duplicar copia.
3. Evento: `aprovado@1` com `origem` e `external_id` nulo; payload antigo (sem `origem`) segue válido no Hub.
4. Hub: `PedidoParaErp` com `origem: 'editado'` válido; `exigeConector` = 1.3.0; payload do pedido antigo idêntico (hash).
5. Telas e PDFs (testes, valor × regra): o mesmo endereço no Resumo, no detalhe (Campo, Gestão, BKO), nos 2 PDFs e
   no payload do Conector; selo "Editado neste pedido" só no editado e nunca no PDF; o cadastro do cliente
   (`core.cliente_endereco`) **não muda** depois do pedido editado.
6. Promotor continua sem pedido (RN-PRO-01); multi-tenant inalterado.

## 9. Premissas (para o gerente confirmar com o dono do produto, se quiser)
- **Duplicar** copia o endereço editado do pedido de origem (é o mesmo destino na maioria dos casos; o vendedor troca).
- Sem busca de CEP (offline-first; fica para quando houver serviço).
- O BKO não ganha lista de "endereços editados para cadastrar" (diferente da transportadora digitada, RN-VEN-16): a
  RN-VEN-17 diz que endereço novo no cadastro entra pelo ERP. Se o dono quiser a lista, é uma consulta sobre o jsonb.

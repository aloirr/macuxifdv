## 0. Resumo das decisões
1. **Fonte = `core.nota_erp`**, tabela do próprio Core já alimentada por `integracao.nota.atualizado@1`. Falta só a **atribuição ao
   vendedor**: duas colunas novas em `core.nota_erp` (`vendedor_external_id`, `usuario_id`) e um índice (§2). Nenhum outro evento.
2. **Lido na hora, sem read-model novo.** O Início com o Vendedor desligado conta direto das notas vivas do mês (uma consulta indexada
   por usuário e mês). Não gravo lista de clientes em `core.indicador_diario` para o ERP. Motivo: a nota já é o read-model (mesmo
   schema, mesma transação, RLS); cancelamento, inativação, troca de cliente ou de mês e reenvio do lote ficam corretos sem
   recálculo, e a idempotência vem do upsert por `external_id` que já existe. Isso **muda o critério 2 da tarefa** ("gravando
   `core.indicador_diario`"): o gerente confirma (§6, P1). Se a resposta for "gravar mesmo assim", o caminho B está em §5.
3. **Precedência: uma fonte por tenant e mês, nunca soma.** Vendedor ligado para o usuário → só a regra do pedido (RN-CORE-20, consulta
   `vendedor.pedidos_da_meta@1`), como hoje. Vendedor desligado e **fonte ERP disponível** → só as notas. Sem fonte ERP → o read-model
   de hoje (`core.positivacao_do_mes`, listas gravadas pelo Vendedor quando estava ligado) ou `null`. Como nunca se somam, o mesmo
   cliente não conta duas vezes (critério 3).
4. **Fonte ERP disponível** = Integração efetiva no tenant (`ctx.usuario.modulos.includes('integracao')`, RN-CORE-03) **e** o tenant
   tem ao menos uma nota viva com `usuario_id` preenchido. Usuário sem nota no mês = `0` (mês novo zera), não `null`.
5. **Regra no domain** (função pura, teste antes, RN-CORE-27): o SQL só estreita o volume; o domain reaplica o filtro e parte em
   "até ontem" e "hoje" no fuso do tenant, com cada cliente contado uma vez, no dia da primeira nota válida.

## 1. Fluxo
```
ERP → Conector → integracao.nota.atualizado@1 ──► Core: consumidorNotaDoErp (já existe)
                                                    upsert core.nota_erp  + vendedor_external_id + usuario_id (NOVO)
ERP → integracao.vendedor.atualizado@1 ────────► Core: consumidorVendedorDoErp (já existe)
                                                    + completa usuario_id das notas órfãs desse vendedor (NOVO)
GET /v1/core/inicio (Vendedor desligado) ──────► inicio.ts: notas do mês (SQL indexado) → domain positivacaoPorNotas → positivacao
```

### 1.1 Consumidor da nota (modulo-core, `consumidores-erp-nota.ts`)
- Grava `vendedor_external_id = r.vendedor_external_id ?? null` e `usuario_id = usuarioPorExternalId(db, r.vendedor_external_id)` (ou `null`).
- **Vendedor ausente não é erro**: não lança `ReferenciaAusenteErp` (bloquearia nota e histórico de compra do Cliente 360 por um dado
  que só serve à positivação). A nota fica com `usuario_id null` e é completada no §1.2.
- Upsert continua por `(tenant_id, external_id)`: reenviar o lote, cancelar (`cancelada = true`) ou inativar (`deleted_at`) a nota
  só muda a linha; a contagem lida depois já sai certa. Nada mais a recalcular.
- Log só com contagens (sem número de nota, cliente ou vendedor).

### 1.2 Consumidor do vendedor (modulo-core, `consumidores-erp-vendedor.ts`)
- Depois do upsert/adoção do usuário: `update core.nota_erp set usuario_id = $id where vendedor_external_id = $ext and usuario_id is null and deleted_at is null`.
  Resolve a ordem de chegada (nota antes do vendedor) sem reprocessar evento. Idempotente (só toca `usuario_id is null`).
- Vendedor inativado (`ativo = false`) **não** apaga a atribuição: as notas do mês continuam dele (histórico).

### 1.3 Início (modulo-core, `inicio.ts`)
Só no ramo "Vendedor desligado/ausente" (`!vendas`), para `paraConsultar` (mesma lista de hoje; RN-PRO-01 continua):
```sql
select usuario_id, cliente_id, min(emitida_em) as primeira_em
  from core.nota_erp
 where deleted_at is null and usuario_id = any($1::uuid[]) and ano_mes = $2
   and tipo = 'faturamento' and not cancelada
 group by usuario_id, cliente_id
```
- `fonteErp` = `ctx.usuario.modulos.includes('integracao') && exists (select 1 from core.nota_erp where deleted_at is null and usuario_id is not null limit 1)`.
- Com `fonteErp`: `positivacao = positivacaoPorNotas(linhasDoUsuario, { periodo, fuso, hoje: dia })` para todo usuário consultado
  (sem nota = `{ ate_ontem: 0, hoje: 0 }`). Sem `fonteErp`: o ramo atual de `core.positivacao_do_mes`, sem mudança.
- `venda_cents` com o Vendedor desligado **não muda** nesta tarefa (continua o read-model diário). Venda faturada pelas notas é outra
  conversa (§6, P3).
- Uma consulta a mais por requisição do Início, coberta pelo índice do §2; volume = clientes distintos por usuário no mês.

## 3. Domain (modulo-core, `modules/core/domain`, teste antes)
```ts
/** RN-CORE-27: nota que positiva = faturamento, não cancelada (a consulta já tira as inativadas). */
export function notaPositiva(n: { tipo: 'faturamento' | 'devolucao'; cancelada: boolean }): boolean;
/** RN-CORE-27 + RN-CORE-26: clientes distintos do mês, cada um no dia (fuso do tenant) da 1ª nota válida; hoje = novos hoje. */
export function positivacaoPorNotas(
  notas: readonly { cliente_id: string; emitida_em: string | Date; tipo?: 'faturamento' | 'devolucao'; cancelada?: boolean }[],
  o: { periodo: string; fuso: string; hoje: string },
): { ate_ontem: number; hoje: number; mes: number };
```
Casos mínimos de teste (todos citando RN-CORE-27):
1. Duas notas do mesmo cliente em dias diferentes → conta 1, no primeiro dia.
2. Nota às 23h30 de Manaus do último dia do mês (UTC já no mês seguinte) → fica no mês do fuso; idem `America/Sao_Paulo`.
3. Nota cancelada sozinha → cliente sai; cancelada com outra válida no mês → continua 1 (no dia da válida).
4. Devolução não positiva e não retira (§4).
5. Cliente cuja 1ª nota é hoje → `hoje = 1`; com nota ontem e hoje → `ate_ontem = 1, hoje = 0`.
6. Nota fora do período → ignorada.
Teste de banco (CI, `inicio.db.test.ts` ou novo): dois tenants (RLS), nota antes do vendedor (órfã completada), reenvio do mesmo
lote (idempotente), cancelamento posterior, Vendedor ligado ignora as notas, Integração desligada cai no ramo antigo.

## 4. RN proposta (para o gerente registrar no doc 03; premissa a confirmar com o Alexandre)
**RN-CORE-27 Positivação pelas notas do ERP (Vendedor desligado)** Com o módulo Vendedor desligado e a Integração recebendo notas,
positivado no mês = cliente com ao menos 1 **nota de faturamento** do ERP **não cancelada** e não inativada, **emitida no mês** (dia
civil no fuso do tenant), atribuída ao **vendedor da nota**. Cada cliente conta **uma vez** no mês, no dia da primeira nota válida
(RN-CORE-26: "hoje" = clientes novos hoje). Nota cancelada ou inativada depois retira o cliente se ele não tiver outra nota válida
no mês. Devolução não positiva nem retira. Nota sem vendedor conhecido não conta para ninguém até o vendedor chegar do ERP. Com o
Vendedor ligado vale só a RN-CORE-20 (pedido); as duas fontes **nunca se somam**.

## 5. Caminho B (só se P1 = "gravar no read-model")
Coluna `clientes_positivados_erp_ids uuid[]` em `core.indicador_diario` (lista separada, para não brigar com a do Vendedor no mesmo
dia), o consumidor da nota regrava o mês do usuário (novo e antigo) a cada nota, e `core.positivacao_do_mes` ganha o parâmetro
da fonte. Custa mais SQL, mais escrita por nota e uma segunda regra de recálculo; não traz ganho offline (o aparelho já guarda a
resposta do `core.inicio@1`). Por isso não recomendo.
